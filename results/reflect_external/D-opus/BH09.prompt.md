  - [E1]（BH01、BH02、BH03、BH04、BH05）【已证实】（BH01-BH05）现象：调用方部分或全部接口变慢，耗时集中在一个固定增量的整数倍附近；无500，下游日志无错误。判断：1) 定位哪一跳：按接口分组，比较调用与不调用某下游的接口耗时（不调用任何慢下游的接口只要毫秒级，就能排除调用方自身）；再取单个慢请求，对齐调用方发起、下游入口日志、调用方完成三个时间点：间隔集中在到达下游之前，下游处理和回程都很快，就说明延迟在通往该 Pod 的入向网络上；两个不同的调用方都慢、共同点只有这个下游，也指向它。2) 区分网络延迟与 CPU 节流：下游自记耗时远小于调用方看到的耗时，或者耗时差等于往返次数×同一增量，先查该 Pod veth 上的 tc/netem，不要先查 CPU limit。3) 一个下游解释了大部分耗时，不代表只有它被注入：对每个接口实际会调用的其他下游，也要逐个做入口时间对齐。K8s API 看不到 tc 规则；没有节点权限时请运维查 qdisc。Pod 配置与 last-applied 一致、没有探针失败，都不能作反证。例：清除被注入下游 veth 上的 tc 规则后，慢请求比例降到接近 0。
  - [E2]（BH01、BH02、BH03、BH07）【已证实】现象：下单等接口返回500，调用方日志出现 dial tcp 失败；或上游只看到被包装的rpc错误（某一步“报价/转换/准备失败”），首个请求耗时为秒级建连超时、之后毫秒级快速失败——都按“某一跳连不上”处理。分流：i/o timeout或首慢后快 → 把调用方配置的目标端口与Service port/targetPort、容器监听端口比较，不一致时对比调用方Deployment新旧ReplicaSet环境变量或live与last-applied注解，找出改坏的变更并改回；connection refused → 看Endpoints是否为空，比较Service selector与Pod标签，改回实际标签，并核对其他Service都有Endpoints。被调用服务日志正常处理其他调用方，说明问题在调用方配置。多症状时一次只修一处，分别看错误率和延迟分位数：500归零而慢请求比例不变，说明变慢是另一独立原因，要继续查。例：四次故障改回端口或selector后500和下单失败立即归零。
  - [E3]（BH04）【已排除】现象：多个服务每次调用都显得被抬高同一增量，容易把它们全列为源头并一起重启。判断：每个候选先看它自己有没有调用其他候选（例如服务A内部调用数据库或另一个变慢的服务B）。如果它的耗时恰好等于“它调用慢下游的次数×增量”，它只是被传染，不是源头。另外用“收到请求→返回”的自记耗时检验：自记耗时正常、只有调用方看到的耗时被抬高的，才是真正被注入的那一跳。先只处理能解释全部耗时的最小集合，然后看用户侧数字：数字回到正常，就说明没处理的其余候选都已排除。例：只清除两个最底层下游veth上的tc，被怀疑的上游服务和广告服务都没动，延迟就全部消失。
  - [E4]（BH05）【未解决】现象：修复时同时清除了多个 Pod 的 tc 规则，或者用重建 Pod 代替清除规则。判断：多个 Pod 一起处理后用户侧恢复，只能证明源头在这一组里，证明不了每个 Pod 都被注入过；诊断里没有出现的 Pod 也被一并清除时，要在清除前对它做入口时间对齐，或者查它的 qdisc 留下证据，否则它有没有被注入仍然未知。另外，“重建 Pod 会换掉 netns/veth，所以能清掉延迟”只是推断，还缺一次只重建、不清 tc，然后看用户侧数字的验证；故障也可能按控制器或 IP 重新注入。在验证之前，优先由运维直接查看并清除 veth 上的 qdisc。例：诊断只指出一个服务，实际清除了两个服务的 tc 后延迟消失，另一个服务当时是否被注入无法判断。
  - [E5]（BH06、BH07）【已排除】现象：用户侧有变慢或500/下单失败，同时调用方日志里有大量对某个下游的快速失败（connection refused、Service无Endpoints、Deployment副本为0），但这些错误被调用方吞掉、页面降级仍返回200。判断：1) 看用户侧500的错误链实际指向哪个下游：错误信息指向另一跳时，被吞掉的失败不是500的原因；失败在毫秒级返回、而慢接口多出的耗时已能被其他下游“调用次数×增量”解释时，它也不是变慢的原因。2) 修复它（恢复副本或端点）之后看用户侧：500、下单失败、慢请求比例和分位数基本不变，就排除了它对这些症状的贡献，把它作为独立故障登记，继续按E1/E2查错误链或耗时指向的那一跳。3) 用户侧数字看不出被吞掉的降级错误是否消失，要确认修好需另看调用方日志里该错误是否停止。例：恢复缩容到0的推荐或广告服务后，500、下单失败和延迟分布都不变；随后改回下单链路的目标端口或清除tc才恢复。
  - [E6]（BH08）【已证实】现象：调用方变慢、无500，慢的那一跳可能是数据库/缓存等非RPC后端。判断：1) 按接口数出每个请求对该后端的实际往返次数（命令数），不只数RPC次数；耗时增量与后端往返次数成正比（1次约1倍，2次约2倍），不调用该后端的接口不慢，说明延迟在通往该后端的那一跳。2) 区分是哪一端的veth：如果延迟加在中间服务自己的veth上，进入它的RPC也会被计入，增量按“1+往返次数”增长，比例和上面不同。3) CPU节流和网络延迟只读无法区分时，先只清除后端Pod veth上的tc，不改CPU limit，也不重建：用户侧恢复，就排除了节流，不必再扩CPU或重启。例：只清除缓存Pod veth上的tc，未动CPU限制，慢请求比例降到0。
  - [E7]（BH08）【已排除】现象：发现某服务有不在last-applied里的手工改动（多出的env、标签等），或故障前不久刚滚动更新过，容易被当成变慢的源头。判断：1) 对齐时间线：新Pod Ready之后是否还有一段正常的用户侧请求，变慢是否在那之后才阶跃出现；如果是，这次漂移大概率只是巧合。2) 改回它之后看用户侧：慢请求比例和分位数都不变，就排除了它对变慢的贡献，不要停在这里，继续按耗时分解（E1）找被注入的那一跳。只有在错误链、端口或selector确实对不上时（E2），配置漂移才是原因。例：删除调用方多出的env并滚动更新后延迟分布不变，随后清除下游veth上的tc才恢复。

**2. 把三个服务的日志按时间戳对齐后，延迟在“请求到达 shippingservice 之前”**

以一条 `GET /cart`（req `5e1b703b`）为例：

- 48.3964 `[GetQuote] completed`（**服务端处理 < 0.1ms**）
- 48.3964 前端开始逐项换算（currency 48.396/48.397），48.3984 完成（**响应回路仅 ~2ms**）

同样的对齐在 51.4046、54.4441、55.3296、55.9035 等多次重复：gap = 278–331ms，都是“请求晚到、响应秒回”。

**3. 最硬的一条证据：checkoutservice 里 Charge 与 ShipOrder 之间只隔着一次 shipping RPC**
