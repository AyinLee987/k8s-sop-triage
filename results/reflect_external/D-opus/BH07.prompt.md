【boutique-triage-overview】Online Boutique（命名空间 boutique）排查总则：服务调用关系、按症状选入口 SOP、跨服务跳转原则、怎么判断故障源头。排查这个命名空间的任何问题时先读。
  - [E1]（BH01、BH02、BH03、BH04、BH05）【已证实】（BH01-BH05）现象：调用方部分或全部接口变慢，耗时集中在一个固定增量的整数倍附近；无500，下游日志无错误。判断：1) 定位哪一跳：按接口分组，比较调用与不调用某下游的接口耗时（不调用任何慢下游的接口只要毫秒级，就能排除调用方自身）；再取单个慢请求，对齐调用方发起、下游入口日志、调用方完成三个时间点：间隔集中在到达下游之前，下游处理和回程都很快，就说明延迟在通往该 Pod 的入向网络上；两个不同的调用方都慢、共同点只有这个下游，也指向它。2) 区分网络延迟与 CPU 节流：下游自记耗时远小于调用方看到的耗时，或者耗时差等于往返次数×同一增量，先查该 Pod veth 上的 tc/netem，不要先查 CPU limit。3) 一个下游解释了大部分耗时，不代表只有它被注入：对每个接口实际会调用的其他下游，也要逐个做入口时间对齐。K8s API 看不到 tc 规则；没有节点权限时请运维查 qdisc。Pod 配置与 last-applied 一致、没有探针失败，都不能作反证。例：清除被注入下游 veth 上的 tc 规则后，慢请求比例降到接近 0。
  - [E2]（BH01、BH02、BH03）【已证实】现象：下单等接口返回500，调用方日志出现 dial tcp 失败；或上游只看到被包装的rpc错误（某一步“转换/准备失败”），首个请求耗时为秒级建连超时、之后毫秒级快速失败——都按“某一跳连不上”处理。分流：i/o timeout或首慢后快 → 把调用方配置的目标端口与Service port/targetPort、容器监听端口比较，不一致时对比调用方Deployment新旧ReplicaSet环境变量或live与last-applied注解，找出改坏的变更并改回；connection refused → 看Endpoints是否为空，比较Service selector与Pod标签，改回实际标签，并核对其他Service都有Endpoints。被调用服务日志正常处理其他调用方，说明问题在调用方配置。多症状时一次只修一处，分别看错误率和延迟分位数：500归零而慢请求比例不变，说明变慢是另一独立原因，要继续查。例：三次故障改回端口或selector后500和下单失败归零，慢请求比例不变。
  - [E3]（BH04）【已排除】现象：多个服务每次调用都显得被抬高同一增量，容易把它们全列为源头并一起重启。判断：每个候选先看它自己有没有调用其他候选（例如服务A内部调用数据库或另一个变慢的服务B）。如果它的耗时恰好等于“它调用慢下游的次数×增量”，它只是被传染，不是源头。另外用“收到请求→返回”的自记耗时检验：自记耗时正常、只有调用方看到的耗时被抬高的，才是真正被注入的那一跳。先只处理能解释全部耗时的最小集合，然后看用户侧数字：数字回到正常，就说明没处理的其余候选都已排除。例：只清除两个最底层下游veth上的tc，被怀疑的上游服务和广告服务都没动，延迟就全部消失。
  - [E4]（BH05）【未解决】现象：修复时同时清除了多个 Pod 的 tc 规则，或者用重建 Pod 代替清除规则。判断：多个 Pod 一起处理后用户侧恢复，只能证明源头在这一组里，证明不了每个 Pod 都被注入过；诊断里没有出现的 Pod 也被一并清除时，要在清除前对它做入口时间对齐，或者查它的 qdisc 留下证据，否则它有没有被注入仍然未知。另外，“重建 Pod 会换掉 netns/veth，所以能清掉延迟”只是推断，还缺一次只重建、不清 tc，然后看用户侧数字的验证；故障也可能按控制器或 IP 重新注入。在验证之前，优先由运维直接查看并清除 veth 上的 qdisc。例：诊断只指出一个服务，实际清除了两个服务的 tc 后延迟消失，另一个服务当时是否被注入无法判断。
  - [E5]（BH06）【已排除】现象：用户侧只有变慢、没有500，同时调用方日志里有大量对某个下游的快速失败（connection refused、Service 无 Endpoints、Deployment 副本为0），错误被调用方吞掉、页面降级显示。判断：1) 比较失败调用的耗时和慢接口多出来的耗时：失败在毫秒级返回，而慢接口多出的耗时已经能被其他下游的“调用次数×增量”完全解释时，这个失败的下游不是变慢的原因，要另作为独立故障登记。2) 修复它（恢复副本或端点）之后看用户侧慢请求比例和分位数：基本不变，就排除了它对延迟的贡献，继续按 E1 查剩下的那一跳。3) 用户侧数字只有延迟、500和下单，看不出被吞掉的降级错误是否消失；要确认修好，需另看调用方日志里该错误是否停止。例：恢复缩容到0的广告服务后延迟分布不变，随后只清除货币服务 Pod veth 上的 tc，慢请求归零。

### 证据链

**1. 下单失败：checkoutservice 的 `SHIPPING_SERVICE_ADDR` 指向了错误端口**

frontend 日志（`frontend-fd686dbb-dmxdc`，近 30 分钟，按 `error|failed|500` 过滤，共 178 条匹配，展示最新 100 条）中所有 `/cart/checkout` 的 500 都是同一条：

```
"failed to complete the order: rpc error: code = Internal desc = shipping quote failure:
 failed to get shipping quote: rpc error: code = Unavailable desc = connection error:
 dial tcp 10.96.50.166:50052: i/o timeout"
```

- `10.96.50.166` = Service `shippingservice` 的 ClusterIP，而该 Service **只暴露 50051**（`port 50051 → targetPort 50051`，Endpoint `10.244.0.133:50051`），shippingservice Pod 的 `PORT=50051`。
- 但运行中的 checkoutservice Deployment（gen 76 / revision 74）env 是 `SHIPPING_SERVICE_ADDR=shippingservice:50052`。
- 对比可证这是**运行态配置被改**，不是历史遗留：旧 ReplicaSet `checkoutservice-5d5f4589c5`（2026-11-15 创建）里是 `shippingservice:50051`；07:08:04 新建的 `checkoutservice-77b8f6dc84` 里变成 `50052`（事件：`Scaled up replica set checkoutservice-77b8f6dc84 from 0 to 1` + 旧 RS `Scaled down … from 1 to 0`），`last-applied-configuration` 里也仍是 50051。同一 Deployment 其它地址（productcatalog:3550 / payment:50051 / email:5000 / currency:7000 / cart:7070）都对得上各自 Service。
