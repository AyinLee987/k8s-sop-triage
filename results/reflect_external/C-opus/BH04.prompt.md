- 一次结算里 `GetQuote` 完成 32.2291 → payment 收到 Charge 32.2300（+0.9ms，含一次货币转换）

**慢的边，而且慢在“去程”：**
- 12/12 个商品页样本：adservice `received ad request` 都发生在 frontend `request complete` **之前 1.2–2.1ms**。即广告请求到达 adservice 后，1.3ms 内整页就结束了 → **返回方向 ~1ms，那 ~300ms 全在请求去程**
- checkout `order confirmation email sent` 32.512790，而 emailservice 收到时间是 **32.512252**（只早 0.54ms）→ 同样是返回快、去程 ~280ms
- 首页 623ms 里：currency 0.75ms，剩下 621ms 只能是 `ListProducts` + `GetCart` 两次调用 → **~310ms/次**
- 加购 POST /cart 886/902/912/932ms ≈ 3 次被延迟的调用；商品页 2361–2532ms ≈ 8×300ms；购物车页每多一件商品 +~300ms（多一次 getProduct）

**所以（本轮确认的事实）**：约 300ms 延迟只加在**发往 productcatalogservice、cartservice、redis-cart、recommendationservice、adservice、emailservice 的请求方向**上，返回方向正常；与调用方无关（frontend 与 checkout 各自对 cart、email 都慢，而对 currency/payment/shipping 都在 1ms 内）。这排除了节点 CPU、全局网络、客户端进程/调度问题。

### 为什么重建没用，以及还有什么没法区分

重建后**换过名字、换过 IP** 的 productcatalog/cart/recommendation/ad 依然慢，说明延迟不是“某次性打到某几个 Pod 名字/IP 上”，而是**被按标签持续重新挂上的**（重放器监视 Pod 生命周期）。同一现象还剩两种解释，我无法区分：

1. **目的端入向延迟**（最可能）：规则挂在被延迟 Pod 的 netns/ingress（ifb/netem 一类），Pod 重建后按 `app=` 标签重新注入。
2. **发送端出向延迟 + 目的 IP 集合**：规则挂在发送方 Pod（frontend、checkoutservice 等，这两个 Pod 上轮从未重建）的 netns，按目的 IP 匹配，同样持续 reconcile。

区分二者需要的证据我拿不到：`nodes`、集群级 `pods`、`networkpolicies` 被 RBAC 拒绝（`cannot list resource "nodes"/"pods"/"networkpolicies"`），没有 chaos CRD（`Unable to find resource kind 'networkchaos'`），也没有 exec/bash 进入 Pod netns 看 `tc qdisc`。上轮被我重启的 4 个目的 Pod 名字/IP 都变了延迟仍在 → 排除按名字选择，指向按标签重放。

### 为什么这一轮不提交任何操作

6 类可用操作全部落在 Kubernetes 对象层，改不到 tc/netem/iptables 层：`restart` 已实测无效（6 个 Pod）；`set_cpu_limit`/`set_env` 只换 ReplicaSet 和宿主名，**不改变 `app=` 标签**，按标签重放的选择器照样命中；`scale` 只是让更多 Pod 一起被延迟；`set_service_selector`/`set_service_target_port` 也不能改变“包发到该 Pod IP 就被延迟”这一事实（namespace 里也没有第二个可指向的 productcatalog/cart Pod，指错端口只会变成连接拒绝/500，把“只慢不报错”变成真故障）。所以我按“现有操作修不了”处理，不浪费一轮去做注定无效的变更。
