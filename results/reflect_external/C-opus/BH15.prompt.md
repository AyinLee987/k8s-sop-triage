  - [E4]（BH02、BH03、BH04、BH05、BH08）【已排除】慢请求耗时呈固定台阶，台阶数与经过某些目的服务的往返次数成正比，不经过的接口仍是毫秒级，也没有快样本时，重建 Pod 解决不了。判断方法：按请求类型列出对各下游的调用次数，下游还连存储的要数到最底层的往返（如存储命令条数），而不只数 RPC 次数，看耗时差是否等于次数差乘一个固定值。再用不同调用组合的耗时比值，区分“每次往返加一次”和“挂在某一端 Pod 的全部流量上”。把调用方与被调方日志按请求配对，看多出的延迟是否稳定；重建后看新 Pod 是否从第一个请求起就同样慢。已实测：重建被调服务及其存储；重建调用方；一次重建全部受影响的被调服务；先重建一端、再重建另一端（两端名字和 IP 都换了）。用户侧中位数和超阈值比例都不变。这排除了两端 Pod 内的运行时状态、netns 内的规则、按 Pod 名或 IP 一次性下发的规则以及应用配置。出现这种特征时不要再逐个重建做试验：重建窗口会出错，重建有状态存储会清数据。直接转入 E3。例：购物车到 redis 的每条命令；前端与推荐服务；前端、结账服务调用汇率服务。
  - [E5]（BH06、BH07、BH09）【未解决】同时存在一个快速失败的独立故障（副本为 0、Endpoints 为空、调用方日志 connection refused 且毫秒级返回）和另一个主故障时：快速失败的调用不贡献延迟，不要把它当成变慢的原因。调用方若做了降级（页面仍返回 200，只记 warning），它不会出现在 500 数里，只能靠调用方日志判断。【已证实】独立修复和主故障修复同批提交时，如果主修复无效，整批撤销会把独立修复一起还原（Service managedFields 显示 selector 在回滚时刻被改了回去）。所以应先单独提交独立修复，或只在主修复把握很高时合并提交。判断独立故障是否还在，直接看 kubectl get endpoints、Service selector 和 managedFields，不要只看调用方报错日志是否消失：已建立的连接可能让日志暂时显示成功。缺的证据：修复后降级报错是否停止，至今没有被单独检验过。例：邮件服务 selector 被改，两次随延迟修复同批提交，两次都被撤销。

  - [E7]（BH11、BH12、BH13、BH14）【已排除】间歇性尾延迟：大部分请求毫秒级，一部分多出近似固定量级的延迟（可叠加成整数倍），无500、无重启。先定位停顿在哪一跳：1) 拿调用方不调任何下游的接口做对照，始终不慢就排除调用方进程自身停顿；2) 比较调用和不调用嫌疑下游的页面各自的慢请求比例，比例相同就排除这个下游；3) 用调用方日志与各被调方入口、完成日志逐请求对齐，同一时间窗每类取几十个以上样本，小样本里出现0次不算证据。耗时呈固定台阶本身不能证明是CPU节流。已实测：调高嫌疑服务、其存储、调用方的CPU上限（同时换了新Pod），重建嫌疑服务（换了IP和netns）及其存储，扩副本，改用ClusterIP跳过DNS，之后慢请求比例和p99都不变，新Pod很快又出现探针超时。这排除了CPU配额、单个Pod或其netns、连接状态、DNS几种解释，这些改动应回退。重建有状态存储会清数据，判断是否好转只看超阈值比例和p99。与E3/E4的区别：那里每次往返都慢。例：推荐服务、汇率服务、购物车服务及其存储。
  - [E8]（BH11、BH12、BH13、BH14）【未解决】E7的间歇性尾延迟在Pod级改动都被排除后，要区分停顿是节点/整机级的，还是集中在某个目的服务上：1) 不能只凭探针超时集中在某个服务、少量慢请求落在它上面就下结论。对所有调用边逐请求对齐：用每一步都打时间戳的独立调用方，再用被调方收包时间分清延迟是在路上还是在处理；用大样本看停顿是否出现在多条互不相关、服务端也不同的边上。2) 看探针超时是否换了实例后仍只出现在该服务、其它同样超时设置的探针是否为零。3) 同一连接上的多个并发请求在同一毫秒一起放行，支持连接级重传或队头阻塞，不支持被调进程卡住。停顿随机落在多条边上，指向节点级低概率丢包或软中断、CPU争用；只集中在一条边且跨实例如此，指向该服务的入站路径。缺的证据：节点tc -s qdisc、nstat重传、softnet_stat、vmstat st、/proc/pressure/cpu、抓包，都没有经过修复检验。没有节点权限时，带逐边对齐表和已排除项上报运维，不要再改CPU、副本、env、selector，也不要再重建Pod。例：起初定位在购物车服务，扩大样本后邮件、商品目录这几条边上也出现了同样的停顿。
