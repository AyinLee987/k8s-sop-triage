【boutique-triage-overview】Online Boutique（命名空间 boutique）排查总则：服务调用关系、按症状选入口 SOP、跨服务跳转原则、怎么判断故障源头。排查这个命名空间的任何问题时先读。
  - [E1]（BH01、BH02、BH03）【已证实】调用失败，调用方日志出现 connection refused / i/o timeout，或某一步报错（如 failed to <步骤>、rpc Unavailable/Internal），而且第一次失败耗时是建连超时级别、之后都是毫秒级快速失败时，按两种配置错误逐一核对：1) kubectl get endpoints <svc> 为空：比较 Service selector 与 Pod labels，不一致就用 set_service_selector 改回 Pod 实际标签。2) Endpoints 正常：把调用方 env 里 *_ADDR 的端口与被调 Service 的 port、targetPort、容器监听端口比较；再把线上 Deployment 的 env 与它的 last-applied-configuration、旧 ReplicaSet 模板对比，看 ScalingReplicaSet 事件时间是否与故障开始吻合，然后用 set_env 改回。被调服务自身日志正常、没有报错，说明问题在调用方的地址，不要去改被调服务。验证指标：500 数和下单失败数归零。例：支付 Service 的 selector 被改；结账服务调用支付服务或汇率服务的端口被改。
  - [E2]（BH01）【已排除】页面耗时与“该页面调用某下游的次数”成严格线性关系（不调该下游的接口仍是毫秒级）时，说明是该下游每次调用固定多出一段延迟。此时不要仅凭 CPU limit 偏小就判定为 CPU 节流：先比较下游实际吞吐（日志里每秒处理的 RPC 数）与 1/单次延迟，若吞吐明显高于串行阻塞所能达到的上限，就不是进程内排队；再看新建 Pod 的第一个请求是否就慢，是则与实例状态、连接状态、负载累积无关。已实测：把 CPU 上限提高数倍后，中位数、高分位、超阈值比例基本不变，排除了 CPU 配额/节流和重启可解决这两种解释，加 CPU 的改动应回退。
  - [E3]（BH01、BH02、BH03、BH04、BH05、BH06）【未解决】按 E2、E4 排除 CPU、两端 Pod 重建、Endpoints/Service/env 之后，每次往返仍固定多出一段延迟、服务端 handler 瞬时完成时，怀疑是 Pod 之外按目的地施加的网络延迟（节点 veth/ifb 上的 tc netem、CNI 或注入 agent）。至今未验证也未恢复。先按毫秒对齐日志，逐条调用边配对“调用方发出→被调方入口日志”，判断空隙在去程还是回程（先确认日志打在 handler 入口还是末尾）；每段空隙都要用对应下游的入口日志配对，不要按估算记到已知变慢的服务上。【已排除】按 Service ClusterIP 匹配：把调用方地址改成被调 Pod IP 直连后耗时不变，说明规则不靠 ClusterIP/DNAT 前打标，剩下按目的端口或节点层条件匹配；可用同端口但不慢的服务进一步区分。缺的证据：节点 tc qdisc/filter（含 ingress、ifb）、iptables/nft 规则、注入 agent 列表、抓包。没有 nodes/exec 权限时立即带逐边耗时表上报运维，不要再改 targetPort、selector、副本数、env 或 CPU 去绕开。例：汇率服务每次调用的延迟全部出现在请求到达 handler 入口之前。
  - [E4]（BH02、BH03、BH04、BH05）【已排除】慢请求耗时呈固定台阶，台阶数与经过某些目的服务的往返次数成正比、不经过的接口仍是毫秒级、没有快样本时，重建 Pod 解决不了。判断：按请求类型列出对各下游的调用次数，看耗时差是否等于次数差乘一个固定值；把调用方与被调方日志按请求配对，看多出的延迟是否稳定；重建后看新 Pod 是否从第一个请求起就同样慢。已实测：重建被调服务及其存储；重建调用方；一次重建全部受影响的被调服务；先重建被调方、再重建它的全部调用方（两端名字和 IP 都换了）。用户侧中位数和超阈值比例都不变。这排除了两端 Pod 内的运行时状态、两端 netns 内的规则、按 Pod 名或 IP 一次性下发的规则以及应用配置。出现这种特征时不要再逐个重建做判决试验：重建窗口里会报 500，新连接要多付延迟，重建有状态存储还会清数据、扭曲指标。直接转入 E3。例：购物车与 redis；前端与推荐服务；前端、结账服务调用汇率服务。
  - [E5]（BH06）【未解决】同时存在一个快速失败的独立故障（如 Deployment 副本为 0、Endpoints 为空、调用方日志 connection refused 且毫秒级返回）和一个还没定位的变慢问题时：先看耗时，快速失败的调用不贡献延迟，不要把它当成变慢的原因。两者的修复不要放进同一批操作：一批操作只要用户侧延迟没好转就会整体撤销，独立故障的修复会被一起回滚，系统反复回到坏状态。应先单独提交独立故障的修复，再做延迟试验。缺的证据：单独恢复后失败日志是否停止、功能是否恢复，还没有在单独提交下验证过。例：广告服务被缩到 0，每轮扩容都跟着无效的延迟试验被撤销。

### 证据链

**1. 下单失败：checkoutservice 的 `SHIPPING_SERVICE_ADDR` 指向了错误端口**

frontend 日志（`frontend-fd686dbb-dmxdc`，近 30 分钟，按 `error|failed|500` 过滤，共 178 条匹配，展示最新 100 条）中所有 `/cart/checkout` 的 500 都是同一条：

```
"failed to complete the order: rpc error: code = Internal desc = shipping quote failure:
 failed to get shipping quote: rpc error: code = Unavailable desc = connection error:
 dial tcp 10.96.50.166:50052: i/o timeout"
```

- `10.96.50.166` = Service `shippingservice` 的 ClusterIP，而该 Service **只暴露 50051**（`port 50051 → targetPort 50051`，Endpoint `10.244.0.133:50051`），shippingservice Pod 的 `PORT=50051`。
- 但运行中的 checkoutservice Deployment（gen 76 / revision 74）env 是 `SHIPPING_SERVICE_ADDR=shippingservice:50052`。
- 对比可证这是**运行态配置被改**，不是历史遗留：旧 ReplicaSet `checkoutservice-5d5f4589c5`（2026-11-15 创建）里是 `shippingservice:50051`；07:08:04 新建的 `checkoutservice-77b8f6dc84` 里变成 `50052`（事件：`Scaled up replica set checkoutservice-77b8f6dc84 from 0 to 1` + 旧 RS `Scaled down … from 1 to 0`），`last-applied-configuration` 里也仍是 50051。同一 Deployment 其它地址（productcatalog:3550 / payment:50051 / email:5000 / currency:7000 / cart:7070）都对得上各自 Service。
- 结果：shipping quote 是 PlaceOrder 流程里的必经步骤，它挂 → 订单 100% 提交不了；因为失败在 shipping 这一步之前就返回，paymentservice 近 30 分钟几乎没有上游调用日志（11 条），与「下单 4 次失败 4 次」一致。

**2. 推荐服务被缩到 0（非致命，但确实是异常）**

- Deployment `recommendationservice` 现在 `spec.replicas=0`，Pod 已在 07:08:04 被删除（事件 `Scaled down replica set recommendationservice-6c88b5fb59 from 1 to 0`），其 Service `10.96.63.235` **没有任何 Endpoint**。
- frontend 每个商品页/购物车页都记录：`failed to get product recommendations … dial tcp 10.96.63.235:8080: connect: connection refused`（近 30 分钟上百条）。该错误只被 frontend 降级处理，页面仍返回 200（如 `/product/0PUK6V6EV0` → `status:200, took_ms:6`），这正好解释「其它页面还能打开」。

**3. 其余组件均正常（已检查，未见问题）**
- 全部 11 个 Pod Running、restartCount 0；adservice / cartservice / currencyservice / productcatalogservice / paymentservice / emailservice / shippingservice 日志中无 error/timeout/refused（各查近 30 分钟）。
