  - [E8]（BH11、BH12）【未解决】上一条的间歇性尾延迟在 Pod 级改动都被排除后，先区分停顿是整机级的，还是集中在某一个目的服务上：1) 统计同一时间窗内各条调用边的逐请求耗时，看是只有经过某个服务的那一跳变慢，还是各条边都变慢；2) 看 kubelet 探针连接超时是不是只出现在该服务上，换了 Pod 实例后是否仍然出现；3) 看互不相关的请求、不同连接是否在同一毫秒一起恢复。多个服务同步停顿、多个服务探针超时，支持整机调度停顿（CPU 争用或 vCPU steal）。只集中在一个服务上（跨实例都如此），指向该服务的入站网络路径（丢包后 TCP 重传）或进程自身停顿（事件循环、GC）；停顿长度是连续分布还是重传台阶可作参考。缺的证据：节点 /proc/pressure/cpu、cgroup cpu.stat 的 nr_throttled、vmstat 的 st、该 Pod veth 上的抓包和 nstat 重传计数、memory.events、事件循环延迟；两种解释都没有经过修复检验。没有 nodes/集群级权限时，带上逐边耗时表、同步时刻对齐表和已排除项上报运维，不要再改 CPU、副本数、env、selector。例：一次是多个服务同步结束；另一次只有汇率服务探针超时，其它边都是毫秒级。

### 观察到的证据

**1. 前端自身没有停顿（排除 frontend CPU 限流/调度）**
5 分钟内 2 803 条前端访问日志里，不做任何后端 RPC 的请求从不慢：

- `POST /setCurrency`：同样 **0 条** ≥10ms

而所有慢请求都在后端 RPC 路径上：`/`、`/product/*`、`/cart`、`POST /cart`、`/cart/checkout`。

**2. 一次完整结算的耗时定位（决定性证据）**
慢的结算：前端 228ms（09:01:16.53 → 16.76）。服务端时间线：
```
checkoutservice  16.532 [PlaceOrder]
checkoutservice  16.538 payment went through        ← 备货/换算/查商品/扣款 共 6ms
shippingservice  16.538 [ShipOrder] received/completed (0.05ms)
```

`payment` → `email 到达` 之间空转 **214ms**，其间 checkoutservice 只做两件事：`EmptyCart`(cartservice→redis) 和发邮件（邮件处理仅 0.4ms）。正常结算这一步是 3ms。**≈214ms 的停顿在 EmptyCart 上**（productcatalog / payment / shipping / email 均已被时间戳排除）。

对照：正常结算 09:01:06 是 `payment 06.134 → email 06.137`（3ms）。

**3. 其它路径同样是 ~200ms 固定惩罚，且都经过 cart**

- 各页处理器都会调用 cartservice 的 `GetCart`（渲染页头购物车数量），所以首页/商品页也会被命中 → 与「4.4% 均匀分布、无 500、下单 12/12 成功」一致

### 两个仍无法区分的机制（缺 cgroup / metrics 数据）
1. **CPU 限流**：Redis 8 镜像带 4 个模块 + 16 个工作线程，125m quota 下突发即被 CFS 限流，产生 100–200ms 级停顿；
2. **瞬时不响应/网络丢包**：丢包更契合「dial tcp i/o timeout >1s」（SYN 重传 1s）与「+200ms RTO」这一对现象。
两者都落在 redis-cart 上，且都能被「提高 CPU 上限 + 重建 Pod（新 sandbox，清掉阻塞/网络规则）」覆盖。

次要可能：cartservice（.NET，limit 300m/128Mi）自身 GC/线程池停顿也能造成同样 200ms，但它无法解释 kubelet→redis 的探针超时，概率较低，留作第 2 轮验证目标。
