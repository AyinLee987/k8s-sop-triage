## 结论：剩下的 +400ms 是“按往返计费”的固定网络延迟，且施加在 Pod 之外

1. **每多一次网络往返就多 ≈200ms**，与服务端工作量无关：GetCart（2 次往返级）= 400，AddItem（再多一次 redis 往返）= 598–617，checkout（两轮 cart RPC）= 782。
2. **不是 CPU 限流**：cartservice 限 300m/请求 200m、redis 125m/70m、frontend 200m/100m，全部是 microservice-demo 的原版值，没有被改动过；而 CPU 被限流的典型特征（同一 CFS 周期里刚续上配额的请求会很快返回，出现大量 10–50ms 快样本，且延迟按 100ms 周期随机分布）在这里**一次都没出现**——每个 cart 调用都 ≥370ms，台阶严格是 200ms 的倍数。
3. **不在任何一个 Pod 内部**：cartservice Pod 重建（新 IP 10.244.0.82）在第一次响应就复现，redis-cart Pod 重建（新 IP 10.244.0.83）也完全不变 → 规则不是 Pod netns 里的 tc，也不是应用配置；它按 label（app=cartservice / app=redis-cart）在 Pod 重建后被重新施加，或直接是节点 tiktok-k8s-lab-control-plane 上按 veth/端口下的规则。集群只有一个节点，两个 Pod 都在它上面。

两种具体落点都符合现有数据，我无法用只读权限区分（都写进 root_causes）：
