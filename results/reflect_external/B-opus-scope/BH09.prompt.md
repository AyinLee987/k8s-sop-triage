【boutique-triage-overview】Online Boutique（命名空间 boutique）排查总则：服务调用关系、按症状选入口 SOP、跨服务跳转原则、怎么判断故障源头。排查这个命名空间的任何问题时先读。
  - [E1]（BH01、BH02、BH03、BH06、BH07）适用：调用方日志里有指向具体 地址:端口 的连接错误（dial i/o timeout、connection refused、no such host），或错误链底层只是 Internal/Unavailable 的步骤失败，而被调用的下游自身日志无错或已没有 Pod。不适用：错误是下游已应答的业务码（如 InvalidArgument）且下游日志里有对应报错，这时查下游自身日志。做法：1）把报错里的 IP:端口与目标 Service 的 ClusterIP 和 port 列表比对：IP 对得上但端口不在 Service 里，查调用方的地址配置；端口对得上而 Endpoints 为空，查目标副本数和 selector；2）把调用方实际生效的所有 *_ADDR（Deployment 容器 env）逐个与目标 Service port/targetPort、containerPort、Endpoints 端口对照，并与 last-applied-configuration 注解、旧 ReplicaSet 模板比较，找出被单独改过的字段；3）Endpoints 为空时看目标 replicas 和事件（ScalingReplicaSet、SuccessfulDelete、Killing），再对照 selector 与 Pod 标签、Pod 是否 Ready；4）列出命名空间里所有 Endpoints 为空的 Service，确认问题有几处；5）把变更时间（新 ReplicaSet 创建、缩容事件）和报错开始时间对照；都一致再查网络策略和目标负载。例：地址端口被改错时调用方报 i/o timeout，下游缩到 0 时报 connection refused。
  - [E2]（BH01、BH04、BH08）适用：用户反馈变慢，入口服务日志按 handler 记录了耗时（如 took_ms），并且已知每个 handler 会调用哪些下游。不适用：所有 handler 都一样慢（包括不调用任何下游的 handler 和健康检查），这时查入口服务自身的 CPU/限流、节点或网络。做法：列出每个 handler 的耗时，以及它在每一跳上的调用次数，一直数到最底层（某个 RPC 会发几条存储命令，次数随商品数、购物车件数变化的也要算上）。比较各 handler 耗时增量之间的比例和每一跳调用次数之间的比例：哪一跳对得上，慢的就是哪一跳；只调用依赖 X 的快路径可以把 X 排除。每次调用都多出接近固定的一段、没有一个样本是快的，支持固定延迟；快慢混杂更像丢包重传或排队。多个下游可能同时变慢：把耗时写成“各跳次数×单次增量”之和联立估算；没有单独耗时日志的调用，用调用方相邻两条只夹着这一次调用的日志时间差估算。例：一个 RPC 发两条存储命令的 handler，增量正好是只发一条的两倍。
  - [E3]（BH01、BH02、BH03、BH05）适用：已经定位到某个服务的单次调用变慢，但它的日志里没有错误。不适用：它的日志里有超时、重试或下游报错，这时应沿着它的下游继续往下查。做法：1）先确认被调方用来对时的日志打在 handler 入口还是出口；用调用方请求起始（完成时刻减耗时）和被调方入口日志逐条配对，把一次调用拆成到达前、处理（含它调下游）、返回三段；2）增量在到达前且偏移稳定、处理和返回都快，支持入方向网络或接收排队，仍要用 throttled 指标、并发连接数排除 CPU 限流和排队；增量在处理段则查应用自身和它的下游；3）比较不同调用方（不同 Pod）调同一被调方：都变慢说明问题附着在被调方一侧，只有一个调用方慢则查该调用方的出方向；4）增量和网络往返次数成正比且稳定支持网络延迟，与往返无关、波动大或随计算量变更像 CPU 限流或应用问题；5）把变慢开始时间和 Pod 创建/Ready 时间、下游 slowlog 对照；排除不了的解释写进结论，并写清重建 Pod 无效时下一步查什么（节点流量控制规则、网络插件、限流指标）。Pod 刚启动时短暂 connection refused 自己恢复不算根因。例：被调方入口日志比调用方发起稳定晚一段，而它返回后调用方几毫秒即完成。
  - [E4]（BH02、BH06）适用：同一时间窗里既有变慢，又有失败请求或调用方日志里的错误（包括用户侧没有 500、只在日志里出现的降级调用失败）。不适用：所有失败都是超时，且失败请求的耗时和慢请求一致，这时可以先按同一条慢链路查。做法：把每类症状分开取证：失败的看错误链最底层那条错误指向哪个服务；慢的按 E2/E3 定位到具体一跳。再检查一个原因能否同时解释两类现象：取失败调用自身的耗时（日志时间差或错误类型，如 connection refused 通常是快速失败、超时则接近超时设置），与 handler 耗时比较；再看已定位慢跳的“调用次数×单次增量”能否解释完 handler 耗时，能解释完说明失败调用不贡献延迟。解释不了就当作几个独立故障，各自给出根因、修复和验证；只在日志里出现的错误也要列为独立问题。例：广告服务无端点只造成快速失败日志，页面变慢完全由另一个服务的单次增量解释。
  - [E5]（BH04）适用：按 E2/E3 估算后，有两个及以上服务的单次调用都变慢、增量相近，同一时间窗内另一些服务之间的往返仍然很快，各服务日志无错、配置和 Pod 状态无变化。不适用：只有一个服务变慢（按 E3 查该服务），或所有往返都一样慢（查节点、网络插件、入口自身）。做法：1）列出慢组和快组；2）逐项对比两组 Pod 的节点、标签、注解/sidecar、NetworkPolicy、资源 limits 与 throttled 指标、创建/Ready 时间，以及各节点上的流量控制规则，找只有慢组共有的属性；3）共同属性能解释全部慢组再定为一个根因，否则分别查；4）查不到机制而改用重建 Pod 时，事先写清预期：恢复说明问题附着在 Pod 内，不变则说明来自按标签/节点作用的外部因素，下一步查节点和集群侧策略，不要再重复重启。例：几个服务每次调用都多出相近延迟，另几个服务互调只需几毫秒。
  - [E6]（BH08）适用：排查中发现某个服务有配置漂移（容器 env 或字段不在 last-applied-configuration 注解里，或者有新 ReplicaSet、Pod 重建），而症状是变慢或报错。不适用：漂移的字段本身就和报错对得上（例如报错里的地址端口就是被改过的值），这时按 E1 查地址配置。做法：把三个时刻对齐：新 ReplicaSet 创建和新 Pod Ready 的时间、新 Pod 第一批请求的耗时和结果、症状开始的时间（最后一个正常请求和第一个异常请求）。新 Pod Ready 之后正常服务了一段时间，症状才阶跃式出现，说明这次变更不是根因，把它作为一项独立发现记下来，继续查症状开始那一刻发生了什么；症状开始的时间和 Pod 切换的时间重合，就把这次变更当作首要嫌疑，对照旧 ReplicaSet 模板逐字段比较。例：多出一个 env 的新 Pod 正常服务了几十秒之后，页面才开始变慢。

## 结论：`shippingservice` 的入站网络被加了约 300ms 延迟（请求方向），响应方向正常

### 关键证据

**1. 前端只有购物车类页面慢（frontend 日志，07:39:46–07:39:56，1450 条中看 24 条完整请求）**

| 路径 | took_ms | 状态 |
|---|---|---|
| `GET /cart` | 283 / 286 / 307 / 327 / 335 / 338 | 200 |
| `POST /cart`（302 跳 /cart） | 1–2 | 302 |
| `POST /cart/checkout` | 629 | 200 |
| `GET /product/*` | 8–13 | 200 |
| `GET /` | 37–77 | 200 |

没有任何 4xx/5xx。`/cart` 页面比正常页慢约 300ms，且与购物车条目数无关 → 是**一次调用**被延迟，不是逐条处理。

**2. 把三个服务的日志按时间戳对齐后，延迟在“请求到达 shippingservice 之前”**

以一条 `GET /cart`（req `5e1b703b`）为例：
- 48.0595 前端开始；48.0629 前端 `view user cart`
- 48.0648 recommendationservice 收到 `ListRecommendations`
- **48.3963 shippingservice 才收到 `[GetQuote] received request`（晚了 331ms）**
- 48.3964 `[GetQuote] completed`（**服务端处理 < 0.1ms**）
- 48.3964 前端开始逐项换算（currency 48.396/48.397），48.3984 完成（**响应回路仅 ~2ms**）

同样的对齐在 51.4046、54.4441、55.3296、55.9035 等多次重复：gap = 278–331ms，都是“请求晚到、响应秒回”。

**3. 最硬的一条证据：checkoutservice 里 Charge 与 ShipOrder 之间只隔着一次 shipping RPC**
- 49.4363 `[PlaceOrder]`（checkoutservice）
- 49.7457 shippingservice 收到 `GetQuote`；49.7490 paymentservice 收到 Charge；49.7499 checkoutservice `payment went through`
- **50.0570 shippingservice 才收到 `ShipOrder`（Charge 响应返回后又过了 307ms，中间只有 shipping 调用）**
- 50.0571 `[ShipOrder] completed`（服务端 <0.1ms）；50.0587 email 失败（瞬时 connection refused）；50.0653 前端完成 629ms

这条链上不存在第三种调用，所以 ~300ms 只能花在“发往 shippingservice 的请求到达服务端之前”。

**4. 排除 Pod 级 CPU/探针原因**：shippingservice 限额与同命名空间其他服务一致（limits 200m/128Mi，requests 100m/64Mi），handler 进入后 <0.1ms 就跑完，说明 CPU 充足；探针 1s 超时 > 300ms，所以 Pod 一直 Ready（无 Unhealthy 事件）——这正好解释“Pod 看起来都正常”。

**5. 顺带发现的第二个真实缺陷（不是本次延迟的原因）：`emailservice` 的 Service selector 错了**
```
emailservice  Service selector: app=emailservice-v2
emailservice  Deployment/Pod label: app=emailservice
Endpoints emailservice: subsets = null   （10.96.39.9:5000 无后端）
```
checkoutservice 从 07:37:53 起持续报（此前 07:37:33 之前是成功的）：
`failed to send order confirmation ... dial tcp 10.96.39.9:5000: connect: connection refused`（severity=warning）
订单仍然成功（email 只是 warn），所以用户侧没有 500、下单 5 次成功 0 失败——但它确实在丢订单确认邮件。emailservice Pod 在 07:37:44 被重建过（Killing old pod → 新 Pod），与改 selector 的时间吻合。

**已检查并确认正常的组件**：cartservice（checkout 里 `EmptyCart` 往返 ~1.6ms）、redis-cart、currencyservice（单次换算 <1ms）、productcatalogservice、recommendationservice（商品页 rec 收到→前端完成 5.8ms）、paymentservice（Charge 同毫秒处理）、adservice、frontend 自身。节点级指标我读不到（本诊断 SA 无权 `list nodes`/全集群 pods），所以无法直接看宿主机上的 tc/qdisc。

### 修复思路
延迟只在“进入 shippingservice 的网络路径”上，而 Pod 重建会得到新的 netns/veth/IP，因此重建 `shippingservice` 的 Pod 是当前可申请操作里唯一能清掉这条入站延迟的手段；`emailservice` 的 selector 直接改回 `app=emailservice`。

如果再造 Pod 后 `/cart` 仍然 ~300ms，那说明延迟规则被加在宿主机侧（节点上的 tc/netem），需要运维登录 `tiktok-k8s-lab-control-plane` 清理对应 veth 上的 qdisc，这不是我这份只读权限能做的。
