你维护一套按服务组织的排查 SOP，值班的排障 agent 排查时会读它。下面是一次故障的排查记录。从中提炼以后排查同类问题能直接用上的经验，写成条目加入 SOP。
规则：
1. 每条写清“看到什么现象 → 怎么判断、下一步查什么”，具体到可以照做；不要写这次故障里的 Pod 名、IP、时间。
2. 对整个系统都适用的经验写进 boutique-triage-overview；只和某个服务有关的写进那个服务的 SOP。
3. 已有条目能覆盖的，就修改那一条，不要新增重复的；发现已有条目和这次的记录矛盾，可以修改或删除它。
4. 最多 3 处改动，每条不超过 500 字；没有值得写的就让 changes 为空。
6. 条目要写成换一个服务、换一种故障也能照做的判断方法：看哪几样证据、拿什么和什么比较、什么结果支持哪种解释、怎样排除另一种解释。不要把这次测到的具体数值（例如多少毫秒、百分之几）、具体的服务组合写成判断条件；这次的情况最多放在条目末尾做一句例子。一条经验如果只在“同一个服务出同一个故障”时才用得上，就不要写。
7. 每条经验都要写清适用范围，用下面的固定结构：“适用：<看到哪些可以查到的证据时才用这一条>。不适用：<看到什么证据时不要用这一条，应该改查什么>。做法：<怎么判断>。”适用和不适用的条件必须是排查时能实际查到的东西（日志里的字段、事件、配置项、指标），不能是“当问题是 X 时”这种要先知道答案才能判断的条件。这次的记录只说明这一种情况；同样的现象可能有别的原因（例如变慢可以来自网络、CPU 限流、应用自身、下游排队），不要因为这一次是某种原因，就把这种现象直接指向这种原因，更不要写“先查 A，不要先查 B”，除非记录里有证据说明 B 已经被排除。
8. 把故障当作生产环境里自然发生的事来写：不要用“注入”“被注入”这类说法，也不要假设故障是谁故意加上去的。

【boutique-redis-cart】Online Boutique 的 redis-cart 排查 SOP：症状涉及 redis-cart，或从调用方（cartservice）查到它时读。下游：无。

【boutique-triage-overview】Online Boutique（命名空间 boutique）排查总则：服务调用关系、按症状选入口 SOP、跨服务跳转原则、怎么判断故障源头。排查这个命名空间的任何问题时先读。
  - [E1]（BH01、BH02、BH03、BH06、BH07、BH10）适用：调用方日志里有指向具体 地址:端口 的连接错误（dial i/o timeout、connection refused、no such host），或错误链底层只是 Internal/Unavailable 的步骤失败，而被调下游自身日志无错、只有启动日志没有请求日志，或已没有 Pod。不适用：错误是下游已应答的业务码（如 InvalidArgument）且下游日志里有对应报错，这时查下游自身日志。做法：1）把报错里的 IP:端口与目标 Service 的 ClusterIP 和 port 比对：端口不在 Service 里，查调用方 *_ADDR，与 last-applied-configuration 注解、旧 ReplicaSet 模板比较；2）端口对得上、Endpoints 有地址仍 connection refused，把 Service targetPort、Endpoints 端口与 containerPort、应用启动日志里的实际监听端口比对；3）Endpoints 为空：Pod 都 Ready 时比对 selector 与 Pod 标签，否则看 replicas 和事件（ScalingReplicaSet、SuccessfulDelete、Killing）；4）逐个 Service 核对 selector 和 targetPort，列出所有 Endpoints 为空或端口不符的，确认问题有几处；5）把变更时间和报错开始时间对照；都一致再查网络策略和目标负载。例：targetPort 与监听端口不一致时调用方毫秒级 connection refused；selector 对不上时被调方只有启动日志。
  - [E2]（BH01、BH04、BH08）适用：用户反馈变慢，入口服务日志按 handler 记录了耗时（如 took_ms），并且已知每个 handler 会调用哪些下游。不适用：所有 handler 都一样慢（包括不调用任何下游的 handler 和健康检查），这时查入口服务自身的 CPU/限流、节点或网络。做法：列出每个 handler 的耗时，以及它在每一跳上的调用次数，一直数到最底层（某个 RPC 会发几条存储命令，次数随商品数、购物车件数变化的也要算上）。比较各 handler 耗时增量之间的比例和每一跳调用次数之间的比例：哪一跳对得上，慢的就是哪一跳；只调用依赖 X 的快路径可以把 X 排除。每次调用都多出接近固定的一段、没有一个样本是快的，支持固定延迟；快慢混杂更像丢包重传或排队。多个下游可能同时变慢：把耗时写成“各跳次数×单次增量”之和联立估算；没有单独耗时日志的调用，用调用方相邻两条只夹着这一次调用的日志时间差估算。例：一个 RPC 发两条存储命令的 handler，增量正好是只发一条的两倍。
  - [E3]（BH01、BH02、BH03、BH05）适用：已经定位到某个服务的单次调用变慢，但它的日志里没有错误。不适用：它的日志里有超时、重试或下游报错，这时应沿着它的下游继续往下查。做法：1）先确认被调方用来对时的日志打在 handler 入口还是出口；用调用方请求起始（完成时刻减耗时）和被调方入口日志逐条配对，把一次调用拆成到达前、处理（含它调下游）、返回三段；2）增量在到达前且偏移稳定、处理和返回都快，支持入方向网络或接收排队，仍要用 throttled 指标、并发连接数排除 CPU 限流和排队；增量在处理段则查应用自身和它的下游；3）比较不同调用方（不同 Pod）调同一被调方：都变慢说明问题附着在被调方一侧，只有一个调用方慢则查该调用方的出方向；4）增量和网络往返次数成正比且稳定支持网络延迟，与往返无关、波动大或随计算量变更像 CPU 限流或应用问题；5）把变慢开始时间和 Pod 创建/Ready 时间、下游 slowlog 对照；排除不了的解释写进结论，并写清重建 Pod 无效时下一步查什么（节点流量控制规则、网络插件、限流指标）。Pod 刚启动时短暂 connection refused 自己恢复不算根因。例：被调方入口日志比调用方发起稳定晚一段，而它返回后调用方几毫秒即完成。
  - [E4]（BH02、BH06）适用：同一时间窗里既有变慢，又有失败请求或调用方日志里的错误（包括用户侧没有 500、只在日志里出现的降级调用失败）。不适用：所有失败都是超时，且失败请求的耗时和慢请求一致，这时可以先按同一条慢链路查。做法：把每类症状分开取证：失败的看错误链最底层那条错误指向哪个服务；慢的按 E2/E3 定位到具体一跳。再检查一个原因能否同时解释两类现象：取失败调用自身的耗时（日志时间差或错误类型，如 connection refused 通常是快速失败、超时则接近超时设置），与 handler 耗时比较；再看已定位慢跳的“调用次数×单次增量”能否解释完 handler 耗时，能解释完说明失败调用不贡献延迟。解释不了就当作几个独立故障，各自给出根因、修复和验证；只在日志里出现的错误也要列为独立问题。例：广告服务无端点只造成快速失败日志，页面变慢完全由另一个服务的单次增量解释。
  - [E5]（BH04）适用：按 E2/E3 估算后，有两个及以上服务的单次调用都变慢、增量相近，同一时间窗内另一些服务之间的往返仍然很快，各服务日志无错、配置和 Pod 状态无变化。不适用：只有一个服务变慢（按 E3 查该服务），或所有往返都一样慢（查节点、网络插件、入口自身）。做法：1）列出慢组和快组；2）逐项对比两组 Pod 的节点、标签、注解/sidecar、NetworkPolicy、资源 limits 与 throttled 指标、创建/Ready 时间，以及各节点上的流量控制规则，找只有慢组共有的属性；3）共同属性能解释全部慢组再定为一个根因，否则分别查；4）查不到机制而改用重建 Pod 时，事先写清预期：恢复说明问题附着在 Pod 内，不变则说明来自按标签/节点作用的外部因素，下一步查节点和集群侧策略，不要再重复重启。例：几个服务每次调用都多出相近延迟，另几个服务互调只需几毫秒。
  - [E6]（BH08）适用：排查中发现某个服务有配置漂移（容器 env 或字段不在 last-applied-configuration 注解里，或者有新 ReplicaSet、Pod 重建），而症状是变慢或报错。不适用：漂移的字段本身就和报错对得上（例如报错里的地址端口就是被改过的值），这时按 E1 查地址配置。做法：把三个时刻对齐：新 ReplicaSet 创建和新 Pod Ready 的时间、新 Pod 第一批请求的耗时和结果、症状开始的时间（最后一个正常请求和第一个异常请求）。新 Pod Ready 之后正常服务了一段时间，症状才阶跃式出现，说明这次变更不是根因，把它作为一项独立发现记下来，继续查症状开始那一刻发生了什么；症状开始的时间和 Pod 切换的时间重合，就把这次变更当作首要嫌疑，对照旧 ReplicaSet 模板逐字段比较。例：多出一个 env 的新 Pod 正常服务了几十秒之后，页面才开始变慢。
  - [E7]（BH09、BH11、BH13）适用：用户反馈变慢（含偶发慢样本），需要根据 Pod 状态、探针事件排除或认定某个服务。不适用：重启次数在增加、Pod 未 Ready 或探针持续失败，这时先按事件和探针失败原因查。做法：1）Ready 只说明探针在 timeoutSeconds 内返回了；把探针超时与按 E2/E3/E8 估算的单次增量比较，增量小于超时，Pod 一直 Ready 不能作为排除依据，要用日志对时和调用次数判断。2）有探针失败时先看探针类型和路径（kubelet 直连的 TCP/HTTP/exec 探针不经过任何调用方）：只有一个 Pod 有失败、其余 Pod 探针为零，支持问题附着在该 Pod 一侧（CPU 限流、进程阻塞或该 Pod 网络路径），而不是节点级普遍丢包；但必须同时有调用次数拟合（E8）或步骤间隔定位支持才能认定它。不调用它的 handler 也有同样慢样本，则只说明它也被同一种间歇阻塞碰到。3）探针 i/o timeout 说明停顿有时超过探针超时，偶发慢样本可能是同一停顿的较短部分。例：只有存储 Pod 的 TCP 探针偶发超时，而所有慢请求都经过它。
  - [E8]（BH11、BH12）适用：用户侧中位数正常，只有一部分请求慢且无错误；入口日志按 handler 记录耗时，慢样本集中在某个固定值或其整数倍附近，快样本仍很快。不适用：每次调用都稳定多出一段（按 E2/E3 查），或有超时、报错（按 E4 查）。做法：1）拿不调任何下游的 handler 做对照，它也慢就查入口服务自身。2）对每个候选下游分别按 handler 数出调用它的次数，看慢占比是否符合 1-(1-p)^n：只有某一个下游的次数能拟合全部 handler（调它次数相同的 handler 慢占比也应相近）才定为那一跳，否则说明所有跨 Pod 调用都会被卡。3）用另一个调用方日志里只夹着这些调用的相邻步骤间隔做独立旁证，并看不同调用方的慢样本是否在同一时刻出现，同时出现支持被调方整体停顿。4）分原因：量子与 throttled 计数、负载一起涨支持 CPU 限流（对照 limits）；接近 TCP 重传超时且与负载无关支持丢包，查重传计数；与 GC 日志对齐支持 GC 停顿。5）拿不到指标时把未排除的解释写进结论，修复按对照实验做，一次只改一项、事先写好预期。例：调某下游次数最多的页面慢占比最高，而只调另一下游一次的页面几乎不慢。

## 排查结论

**用户侧那 5.8% 的超 180ms 请求，延迟全部落在对 `cartservice` 的那一次 gRPC 调用上；再往下，`cartservice` 这个 Pod 的网络路径出现了间歇性丢包（约 5%），丢包后 TCP 最小重传超时 200ms，正好对应观测到的延迟量级。** 与 `recommendationservice` 副本数为 0 无关（它是另一个独立问题）。

### 证据链

1. **延迟可以定位到 cart 调用**（frontend 自身日志，09:29:30–09:34:00，共 4,959 行，过滤 `took_ms>=150` 命中 67 行 ≈ 请求量的 5–6%，与用户侧 5.8% 吻合）：
   - `POST /cart`（handler 只调 `cartservice.AddItem`，不调 recommendation）：207 / 209 / 210 / 211 / 270 ms；慢请求日志里 “adding to cart” 与 “request complete” 之间没有任何其它下游调用。
   - `POST /cart/checkout` 437/221/199ms：`checkoutservice` 日志证明 `[PlaceOrder]` → `payment went through` 花了 **193ms**（正常 6ms），即 PlaceOrder 最前面的 `GetCart`/`EmptyCart` 卡住。
   - `GET /`、`GET /cart`、`GET /product/*` 全部在 handler 前段调用 `getCart`，尾部 194–429ms。
   - `POST /setCurrency`（无任何下游调用）服务端 `took_ms` 恒为 0，从不为慢。

2. **不是 frontend 进程/CPU 的问题**：`frontend` 的 `/_healthz` 探针在 4,959 行日志中 **没有一次 >0ms**，说明前端进程从不冻结；frontend 自身也没有任何 `Unhealthy` 事件。

3. **矛盾点只在 cartservice 这一个 Pod 上**（namespace 事件）：
   - `09:27:39` Liveness probe failed: `timeout: failed to connect service "10.244.0.251:7070" within 1s`
   - `09:31:31` Readiness probe failed: 同上
   - 同一时段 `redis-cart` 的 tcpSocket 探针（每 5s 一次，约 336 次）**0 次失败**，frontend httpGet 探针 **0 次失败**；kubelet 连 cartservice 都连不上，说明问题在 cartservice Pod 自己的网络/接收入口，而非 node 全局。

4. **延迟是 200ms 的整数倍**（193/194/204/207/209/210/211/212/213/215/217/218/219/221/222/223/224/227，以及 400/420/437 这类双倍），这是 **TCP RTO_MIN = 200ms 的重传特征**；CPU CFS 限流只会给出 0–100ms 的随机量且应影响同窗口内所有请求，与观测的紧致 200ms 量化不符。

5. **共享连接同时解阻塞**：`09:28:13.055389652` 与 `09:28:13.055390063` 两个不同请求的 cart 调用在同一瞬间恢复；`d983b3b4`/`f0048d2` 起跑相差 117ms 却同时返回 —— 典型的 HTTP/2 单连接**队头阻塞被一次重传解除**。（`09:27:12.10–12.30` 这 200ms 内 cartservice 一条日志都没打，而 frontend 的 AddItem 正在等待。）

6. **无错误、无重启、无 OOM**：frontend 返回 200，`cartservice`/`checkoutservice`/`adservice`/`productcatalogservice` 日志无 error；所有 Pod restarts = 0。

### 另一个独立问题（不是延迟来源）

`recommendationservice` Deployment 的 `spec.replicas = 0`（Pod 于 `09:26:37` 被删除，ReplicaSet 已到 revision 27，历史上 13 次被 scale 到 0）。这是整个 namespace 里**唯一**与 `last-applied-configuration` 不一致的配置改动（其余 CPU/内存/env 全部与已应用清单一致）。后果：每个页面请求都打 `failed to get product recommendations ... connection refused 10.96.63.235:8080`（近 1 小时 212 条 warning），商品/购物车页没有推荐位。但 `POST /cart` 不调用它，所以它解释不了 200ms 尾巴。
