【boutique-triage-overview】Online Boutique（命名空间 boutique）排查总则：服务调用关系、按症状选入口 SOP、跨服务跳转原则、怎么判断故障源头。排查这个命名空间的任何问题时先读。
  - [E1]（BH01、BH02、BH03、BH06）适用：调用方日志里有指向具体 地址:端口 的连接错误（dial i/o timeout、connection refused、no such host），或错误链底层只是 Internal/Unavailable 的步骤失败、而被调用的下游自身日志无错或已没有 Pod。不适用：错误是下游已应答的业务码（如 InvalidArgument）且下游日志里有对应报错，这时应查下游自身的日志。做法：1）把调用方实际生效的 *_ADDR 等配置（Deployment 容器 env）与目标的 PORT、containerPort、Service port/targetPort、Endpoints 端口逐项对照，并与 last-applied-configuration 注解、旧 ReplicaSet 模板比较，找出被单独改过的字段；2）Endpoints 为空时，先看目标 Deployment 的 replicas 和事件（ScalingReplicaSet、SuccessfulDelete、Killing）判断是否被缩到 0，再把 selector 和 Pod 实际标签（get pod --show-labels）对照、看 Pod 是否 Ready；3）列出命名空间里所有 Endpoints 为空的 Service，确认问题有几处；4）把变更时间（新 ReplicaSet 创建、缩容事件）和报错开始时间对照；5）都一致再查网络策略和目标负载。失败耗时可作旁证：首个失败慢、之后毫秒级快速失败，支持对端不通而不是下游处理慢。例：下游被缩到 0 副本，调用方只记录 connection refused。
  - [E2]（BH01、BH04）适用：用户反馈变慢，入口服务日志按 handler 记录了耗时（如 took_ms），并且已知每个 handler 会调用哪些下游。不适用：所有 handler 都一样慢（包括不调用任何下游的 handler 和健康检查），这时应查入口服务自身的 CPU/限流、节点或网络。做法：列出每个 handler 的耗时和它调用每个下游的次数（含随商品数、购物车件数变化的次数）。耗时随某个下游的调用次数线性增长、而不调用它的 handler 很快，说明单次调用该下游变慢；用只调用依赖 X 的快路径把 X 排除。多个下游可能同时变慢：把各 handler 的耗时当成“各下游次数×单次增量”之和联立估算每个下游的增量，没有单独耗时日志的调用，用调用方相邻两条日志之间只夹着这一次调用的时间差估算。定位后再到那个服务的日志和资源配置里区分原因。例：商品页耗时约等于它调用的几个下游的单次增量之和。
  - [E3]（BH01、BH02、BH03、BH05）适用：已经定位到某个服务的单次调用变慢，但它的日志里没有错误。不适用：它的日志里有超时、重试或下游报错，这时应沿着它的下游继续往下查。做法：1）先确认被调方用来对时的日志打在 handler 入口还是出口；用调用方请求起始（完成时刻减耗时）和被调方入口日志逐条配对，把一次调用拆成到达前、处理（含它调下游）、返回三段；2）增量在到达前且偏移稳定、处理和返回都快，支持入方向网络或接收排队，仍要用 throttled 指标、并发连接数排除 CPU 限流和排队；增量在处理段则查应用自身和它的下游；3）比较不同调用方（不同 Pod）调同一被调方：都变慢说明问题附着在被调方一侧，只有一个调用方慢则查该调用方的出方向；4）增量和网络往返次数成正比且稳定支持网络延迟，与往返无关、波动大或随计算量变更像 CPU 限流或应用问题；5）把变慢开始时间和 Pod 创建/Ready 时间、下游 slowlog 对照；排除不了的解释写进结论，并写清重建 Pod 无效时下一步查什么（节点流量控制规则、网络插件、限流指标）。Pod 刚启动时短暂 connection refused 自己恢复不算根因。例：被调方入口日志比调用方发起稳定晚一段，而它返回后调用方几毫秒即完成。
  - [E4]（BH02、BH06）适用：同一时间窗里既有变慢，又有失败请求或调用方日志里的错误（包括用户侧没有 500、只在日志里出现的降级调用失败）。不适用：所有失败都是超时，且失败请求的耗时和慢请求一致，这时可以先按同一条慢链路查。做法：把每类症状分开取证：失败的看错误链最底层那条错误指向哪个服务；慢的按 E2/E3 定位到具体一跳。再检查一个原因能否同时解释两类现象：取失败调用自身的耗时（日志时间差或错误类型，如 connection refused 通常是快速失败、超时则接近超时设置），与 handler 耗时比较；再看已定位慢跳的“调用次数×单次增量”能否解释完 handler 耗时，能解释完说明失败调用不贡献延迟。解释不了就当作几个独立故障，各自给出根因、修复和验证；只在日志里出现的错误也要列为独立问题。例：广告服务无端点只造成快速失败日志，页面变慢完全由另一个服务的单次增量解释。
  - [E5]（BH04）适用：按 E2/E3 估算后，有两个及以上服务的单次调用都变慢、增量相近，同一时间窗内另一些服务之间的往返仍然很快，各服务日志无错、配置和 Pod 状态无变化。不适用：只有一个服务变慢（按 E3 查该服务），或所有往返都一样慢（查节点、网络插件、入口自身）。做法：1）列出慢组和快组；2）逐项对比两组 Pod 的节点、标签、注解/sidecar、NetworkPolicy、资源 limits 与 throttled 指标、创建/Ready 时间，以及各节点上的流量控制规则，找只有慢组共有的属性；3）共同属性能解释全部慢组再定为一个根因，否则分别查；4）查不到机制而改用重建 Pod 时，事先写清预期：恢复说明问题附着在 Pod 内，不变则说明来自按标签/节点作用的外部因素，下一步查节点和集群侧策略，不要再重复重启。例：几个服务每次调用都多出相近延迟，另几个服务互调只需几毫秒。

### 证据链

**1. 下单失败：checkoutservice 的 `SHIPPING_SERVICE_ADDR` 指向了错误端口**

frontend 日志（`frontend-fd686dbb-dmxdc`，近 30 分钟，按 `error|failed|500` 过滤，共 178 条匹配，展示最新 100 条）中所有 `/cart/checkout` 的 500 都是同一条：

```
"failed to complete the order: rpc error: code = Internal desc = shipping quote failure:
 failed to get shipping quote: rpc error: code = Unavailable desc = connection error:
 dial tcp 10.96.50.166:50052: i/o timeout"
```

- `10.96.50.166` = Service `shippingservice` 的 ClusterIP，而该 Service **只暴露 50051**（`port 50051 → targetPort 50051`，Endpoint `10.244.0.133:50051`），shippingservice Pod 的 `PORT=50051`。
- 但运行中的 checkoutservice Deployment（gen 76 / revision 74）env 是 `SHIPPING_SERVICE_ADDR=shippingservice:50052`。
- 对比可证这是**运行态配置被改**，不是历史遗留：旧 ReplicaSet `checkoutservice-5d5f4589c5`（2026-11-15 创建）里是 `shippingservice:50051`；07:08:04 新建的 `checkoutservice-77b8f6dc84` 里变成 `50052`（事件：`Scaled up replica set checkoutservice-77b8f6dc84 from 0 to 1` + 旧 RS `Scaled down … from 1 to 0`），`last-applied-configuration` 里也仍是 50051。同一 Deployment 其它地址（productcatalog:3550 / payment:50051 / email:5000 / currency:7000 / cart:7070）都对得上各自 Service。
