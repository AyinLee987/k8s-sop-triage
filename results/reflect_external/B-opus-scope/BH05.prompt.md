【boutique-triage-overview】Online Boutique（命名空间 boutique）排查总则：服务调用关系、按症状选入口 SOP、跨服务跳转原则、怎么判断故障源头。排查这个命名空间的任何问题时先读。
  - [E1]（BH01、BH02、BH03）适用：调用方日志里有指向某个具体 地址:端口 的连接错误（dial i/o timeout、connection refused、no such host），或者错误链底层只是 Internal/Unavailable 的步骤失败、而被调用的下游自身日志正常无错。不适用：错误是下游已应答的业务码（如 InvalidArgument）且下游日志里有对应报错，这时应查下游自身的日志。做法：1）把调用方实际生效的 *_ADDR 等配置（Deployment 容器 env）和目标的 PORT、containerPort、Service port/targetPort、Endpoints 端口逐项对照，同时和 last-applied-configuration 注解、旧 ReplicaSet 模板比较，找出创建后被单独改过的字段；2）查目标 Service 的 Endpoints：为空就把 selector 和 Pod 实际标签（get pod --show-labels）对照，再看 Pod 是否 Ready；3）列出命名空间里所有 Endpoints 为空的 Service，确认问题有几处；4）把新 ReplicaSet 创建时间和报错开始时间对照；5）都一致再查网络策略和目标负载。失败耗时可作旁证：首个失败慢（建连超时）、之后都是几毫秒的快速失败，支持对端地址不通，而不是下游处理慢。例：调用方的下游地址端口被改成目标未监听的端口，前端只看到“转换价格失败”的 Internal 错误。
  - [E2]（BH01、BH04）适用：用户反馈变慢，入口服务日志按 handler 记录了耗时（如 took_ms），并且已知每个 handler 会调用哪些下游。不适用：所有 handler 都一样慢（包括不调用任何下游的 handler 和健康检查），这时应查入口服务自身的 CPU/限流、节点或网络。做法：列出每个 handler 的耗时和它调用每个下游的次数（含随商品数、购物车件数变化的次数）。耗时随某个下游的调用次数线性增长、而不调用它的 handler 很快，说明单次调用该下游变慢；用只调用依赖 X 的快路径把 X 排除。多个下游可能同时变慢：把各 handler 的耗时当成“各下游次数×单次增量”之和联立估算每个下游的增量，没有单独耗时日志的调用，用调用方相邻两条日志之间只夹着这一次调用的时间差估算。定位后再到那个服务的日志和资源配置里区分原因。例：商品页耗时约等于它调用的几个下游的单次增量之和。
  - [E3]（BH01、BH02、BH03）适用：已经定位到某个服务的单次调用变慢，但它的日志里没有错误。不适用：它的日志里有超时、重试或下游报错，这时应沿着它的下游继续往下查。做法：1）用同一个请求在各服务日志里的时间戳逐跳对时，把一次调用拆成三段：调用方发起→被调方打出收到请求的日志、被调方处理（含它调下游）、被调方返回→调用方完成，看增量集中在哪段；2）增量在到达前、而处理段和它的出向调用都快，支持入方向网络或接收排队，但仍要用 throttled 指标、并发连接数排除 CPU 限流和排队；增量在处理段则查应用自身和它的下游；3）数清各接口的网络往返次数：增量和往返次数成正比且稳定，支持网络延迟；与往返无关、波动大或随计算量变，更像 CPU 限流或应用问题；4）把变慢开始时间和 Pod 创建/Ready 时间、下游 slowlog 对照；5）排除不了的解释写进结论，并写清处置（如重建 Pod）无效时下一步查什么（节点上的流量控制规则、网络插件、限流指标）。Pod 刚启动时短暂 connection refused 自己恢复不算根因。例：被调方收到请求的日志比调用方发起稳定晚一段，而它返回后调用方几毫秒即完成。
  - [E4]（BH02）适用：用户反馈或监控里同时有不止一类症状（比如变慢和请求失败/500 同时出现），或者失败请求的日志里有明确的错误，而慢请求没有报错。不适用：所有失败都是超时，并且失败请求的耗时和慢请求一样，这时可以先按同一条慢链路查。做法：把每类症状分开取证：失败的看错误链里最底层的那条错误指向哪个服务；慢的按 E2/E3 定位到具体一跳。然后检查一个原因能不能同时解释两类现象（比如失败是不是超时引起的、失败的耗时是不是由慢的那一跳决定），解释不了就当作几个独立故障，各自给出根因和修复，修复后也分别验证。例：结账失败来自支付服务的 Endpoints 为空，全站变慢来自购物车服务那一跳的延迟，两件事互不相关。
  - [E5]（BH04）适用：按 E2/E3 估算后，有两个及以上服务的单次调用都变慢、增量相近，同一时间窗内另一些服务之间的往返仍然很快，各服务日志无错、配置和 Pod 状态无变化。不适用：只有一个服务变慢（按 E3 查该服务），或所有往返都一样慢（查节点、网络插件、入口自身）。做法：1）列出慢组和快组；2）逐项对比两组 Pod 的节点、标签、注解/sidecar、NetworkPolicy、资源 limits 与 throttled 指标、创建/Ready 时间，以及各节点上的流量控制规则，找只有慢组共有的属性；3）共同属性能解释全部慢组再定为一个根因，否则分别查；4）查不到机制而改用重建 Pod 时，事先写清预期：恢复说明问题附着在 Pod 内，不变则说明来自按标签/节点作用的外部因素，下一步查节点和集群侧策略，不要再重复重启。例：几个服务每次调用都多出相近延迟，另几个服务互调只需几毫秒。

## 结论：`currencyservice` 的请求入口被添加了约 200 ms 的单向网络延迟

### 定位过程与证据

**1. 页面延迟分布（frontend 自身日志，`took_ms`，最近约 2 分钟，345 条 `request complete`）**

| 路径 | 延迟 |
|---|---|
| `GET /` (home) | 1981–2144 ms（稳定 ~2080）|
| `GET /product/*` | 377–448 ms（稳定 ~415）|
| `GET /cart` | 4 个明显分层：~700 / ~880–950 / ~1090–1190 / ~1310–1330（每个购物车条目 +~200 ms）|
| `POST /cart`（加购）| **1–2 ms** |
| `POST /setCurrency` | 0–2 ms |
| `POST /cart/checkout` | 1169–1677 ms |

`POST /cart` 只花 1 ms，这说明 `productcatalogservice`、`cartservice`、`redis-cart` 都很快，请求路径本身没有异常。

**2. 时间戳逐条对齐，发现延迟在 `currencyservice` 的入口**

把 frontend 每个页面的起始时刻（= 完成时刻 − `took_ms`）与 `currencyservice-6df4cccbb9-ltrd7` 的 `Getting supported currencies...`（该日志在 handler **入口**打印）逐条比对，06:13:00–06:13:12 窗口内 **15 个页面请求 / 15 条 GSC 日志，一一对应**，偏移分别为：

```
199, 210, 194, 188, 191, 192, 212, 210, 211, 207, 206, 209, 200, 207, 204 ms
```

即：请求发出后 **约 200 ms 才到达 currencyservice 进程**；而 handler 执行完后返回很快（例：`/product/OLJCESPC7Z` 起始 06:13:05.015 → GSC 05.225 → 转换完成日志 05.434 → frontend 完成 05.442，**响应仅 +8 ms**）。同一毫秒内多次出现 2 条转换完成日志（84.876/84.876、89.997/89.997、91.055/91.056），说明业务处理本身是瞬时的。

**3. 延迟只伴随 currency 的 RPC 数量**

- home = product + 9 次额外转换：`2080 − 415 ≈ 1665 ms ÷ 9 ≈ 185 ms/次`
- cart 每个条目 +~200 ms（每次 `Convert`）
- 服务端日志速率 ~6 次转换/s，负载很低，排除 CPU 排队/限流（且容器 CPU limit 200m/request 100m 为官方 demo 标准值）

**4. 排除的其他可能**
- 镜像全部为标准 `us-central1-docker.pkg.dev/google-samples/microservices-demo/*:v0.10.3`，无自定义镜像、无 sidecar/initContainer、无 chaos 容器。
- 所有 Deployment 的 env、资源、Service `targetPort` 与 Endpoints（`currencyservice → 10.244.0.87:7000`，唯一后端）均正确。
- adservice 正常：`received ad request` 日志与 frontend 请求**完成时刻**相差 ≤2 ms（它是 handler 最后一个调用，且很快）。
- 12 个 Pod 全部 Running、READY、0 重启；0 个 500；无相关 Event。
- **不是 frontend 单侧问题**：`checkoutservice`（另一个 Pod，10.244.0.86）也慢——`[PlaceOrder]` 06:12:44.830 → `payment went through` 06:12:45.959，前置阶段 1129 ms，与“每个条目 1 次货币转换 ×200 ms”吻合。两个不同客户端都慢，共同点只有 `currencyservice` 这一个 Pod。

### 影响面

- **受影响**：`currencyservice`（自身延迟证据：入口日志相对调用方请求起始恒定 +188~212 ms）。其调用方 `frontend`（`took_ms` 2.0–2.1 s / 377–448 ms）与 `checkoutservice`（`PlaceOrder → payment` 1129 ms）因此变慢；用户侧 75.4% 请求 >180 ms、中位 420 ms、p90 1983 ms，且 0 报错，与“只加延迟不加错误”完全一致。
