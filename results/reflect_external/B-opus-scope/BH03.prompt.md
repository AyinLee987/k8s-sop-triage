规则：
1. 每条写清“看到什么现象 → 怎么判断、下一步查什么”，具体到可以照做；不要写这次故障里的 Pod 名、IP、时间。

4. 最多 3 处改动，每条不超过 500 字；没有值得写的就让 changes 为空。
6. 条目要写成换一个服务、换一种故障也能照做的判断方法：看哪几样证据、拿什么和什么比较、什么结果支持哪种解释、怎样排除另一种解释。不要把这次测到的具体数值（例如多少毫秒、百分之几）、具体的服务组合写成判断条件；这次的情况最多放在条目末尾做一句例子。一条经验如果只在“同一个服务出同一个故障”时才用得上，就不要写。
7. 每条经验都要写清适用范围，用下面的固定结构：“适用：<看到哪些可以查到的证据时才用这一条>。不适用：<看到什么证据时不要用这一条，应该改查什么>。做法：<怎么判断>。”适用和不适用的条件必须是排查时能实际查到的东西（日志里的字段、事件、配置项、指标），不能是“当问题是 X 时”这种要先知道答案才能判断的条件。这次的记录只说明这一种情况；同样的现象可能有别的原因（例如变慢可以来自网络、CPU 限流、应用自身、下游排队），不要因为这一次是某种原因，就把这种现象直接指向这种原因，更不要写“先查 A，不要先查 B”，除非记录里有证据说明 B 已经被排除。

【boutique-triage-overview】Online Boutique（命名空间 boutique）排查总则：服务调用关系、按症状选入口 SOP、跨服务跳转原则、怎么判断故障源头。排查这个命名空间的任何问题时先读。
  - [E1]（BH01、BH02）适用：调用方日志里有指向某个具体 地址:端口 的连接错误（dial i/o timeout、connection refused、no such host）。不适用：错误是下游已应答的业务码或 gRPC 状态（如 InvalidArgument），这时应查下游自身的日志。做法：1）把错误里的地址/端口和调用方的 *_ADDR 等配置对照；2）查目标 Service 的 Endpoints：如果为空，就把 Service 的 selector 和目标 Pod 的实际标签（get pod --show-labels）逐项对照，再看 Pod 是否 Ready；如果不为空，就把 Service 的 port/targetPort 和容器的实际监听端口（PORT、containerPort）对照；3）顺手列出命名空间里所有 Endpoints 为空的 Service，确认问题只有一处还是有多处；4）比较调用方/目标的新旧 ReplicaSet 或 Service 配置，看变更时间和报错开始的时间是否对得上；5）都一致的话，再查网络策略和目标的负载。例：selector 写成了不存在的标签，Endpoints 为空，调用 ClusterIP 时报 connection refused。
  - [E2]（BH01）适用：用户反馈变慢，入口服务的日志按 handler 记录了耗时（如 took_ms），并且已知每个 handler 会调用哪些下游。不适用：所有 handler 都一样慢（包括不调用任何下游的 handler 和健康检查），这时应查入口服务自身的 CPU/限流、节点或网络。做法：列出每个 handler 的耗时，以及它调用每个下游的次数（包括随商品数、购物车件数变化的次数）。如果耗时随某个下游的调用次数线性增长，而不调用这个下游的 handler 很快，就说明单次调用这个下游变慢了；再用其他依赖的快路径（某个只调用依赖 X 的 handler 很快）把 X 排除。定位到下游以后，再到那个服务的日志和资源配置里区分原因。例：首页、商品页、购物车的耗时和调用某个服务的次数成比例。
  - [E3]（BH01、BH02）适用：已经定位到某个服务的单次调用变慢，但它的日志里没有错误。不适用：它的日志里有超时、重试或下游报错，这时应沿着它的下游继续往下查。做法：1）用同一个请求在各服务日志里的时间戳逐跳对时，两条日志之间只夹着一次调用时，这段间隔就归到那次调用上；2）数清这个服务的各个接口每次请求包含几次网络往返（调用方往返加上它调用下游的次数），比较各接口的耗时：如果耗时增量和往返次数成正比、大小稳定，就支持网络延迟在这个 Pod 上；如果和往返次数无关、波动大，或者和计算量相关，就更像 CPU 限流或应用自身的问题，要用 throttled 指标确认；3）把变慢开始的时间和这个 Pod 的创建/Ready 时间、它的下游自身的耗时（slowlog）对照；4）查不到指标、排除不了的解释，要在结论里写明，并写清处置无效时下一步查什么。Pod 刚启动时短暂出现的 connection refused 自己恢复的话，不算根因。例：两次下游往返的接口稳定比一次往返的慢一个固定量。
  - [E4]（BH02）适用：用户反馈或监控里同时有不止一类症状（比如变慢和请求失败/500 同时出现），或者失败请求的日志里有明确的错误，而慢请求没有报错。不适用：所有失败都是超时，并且失败请求的耗时和慢请求一样，这时可以先按同一条慢链路查。做法：把每类症状分开取证：失败的看错误链里最底层的那条错误指向哪个服务；慢的按 E2/E3 定位到具体一跳。然后检查一个原因能不能同时解释两类现象（比如失败是不是超时引起的、失败的耗时是不是由慢的那一跳决定），解释不了就当作几个独立故障，各自给出根因和修复，修复后也分别验证。例：结账失败来自支付服务的 Endpoints 为空，全站变慢来自购物车服务那一跳的延迟，两件事互不相关。

## 结论

有两处独立的故障，证据都在下面。

### 1) 下单全部失败：checkoutservice 的 `CURRENCY_SERVICE_ADDR` 被改成了 `currencyservice:7001`（应为 7000）

- 线上 Deployment `checkoutservice` 的容器 env 实际为 `CURRENCY_SERVICE_ADDR=currencyservice:7001`，而它自己的 `last-applied-configuration` 里是 `currencyservice:7000` —— 说明是创建后被单独 patch 的。
- 时间吻合：新 ReplicaSet `checkoutservice-d7f6755c6` 创建于 **04:17:40**（revision 68），旧 RS `checkoutservice-5d5f4589c5` 已 0 副本；新 Pod 的 env 是 7001，旧 RS 模板里是 7000。
- currencyservice 只监听 **7000**（`PORT=7000`、containerPort 7000、Service `7000→7000`、endpoint `10.244.0.199:7000`），7001 没有任何监听。
- 前端日志（近 30 分钟，共 1018 行，过滤 `err|fail|500|timeout`，命中 36 行）反复出现：
  `failed to complete the order: rpc error: code = Internal desc = failed to prepare order: failed to convert price of "2ZYFJ3GM2N" to CAD`，对应 `POST /cart/checkout` 返回 **500**。
- 首次失败耗时 **4420ms**（建连超时），后续都是 **2–3ms**（子通道快速失败），正是"对端端口不通"的特征。
- currencyservice 自身健康：日志里全是 `conversion request successful`，EUR/CAD/USD/JPY 都能换算，无错误 —— 只是 checkout 连不到它。

### 2) 变慢：`/product/*` 与 `/cart` 页面被 recommendationservice 调用拖了约 400ms

对前端日志做时间点对齐（同一时间段内）：

| 页面 | 现象 |
|---|---|
| `GET /`（首页） | 13–47ms，**不调用** recommendation |
| `POST /cart`、`/setCurrency`、`/_healthz` | 0–2ms |
| `GET /product/<id>` | 387–449ms |
| `GET /cart` | 402–449ms |

以 `/product/6E92ZMYYFZ`（req `cd962187`，04:19:27.541 开始，416ms 完成）为例：
- 04:19:27.541 前端 "serving product page"
- 04:19:27.542 currencyservice `Getting supported currencies...`（+1ms）、27.544 `conversion request successful`（+3ms）→ productcatalog/currency 都是毫秒级
- 04:19:27.953 recommendationservice 才打出 `[Recv ListRecommendations]`（**+412ms**）
- 04:19:27.957 前端完成（**recommendation 处理器返回后仅 4ms**）

同样的 ~400ms 间隔在 12 个请求上重复出现（399/404/408/408/409/412/418/419/427/431/434/435ms）。也就是说：**约 400ms 全部花在请求到达 recommendationservice 之前，而 rec 的响应本身很快**；`/product` 和 `/cart` 都调用它、首页不调用，正好解释"71.9% 请求 >180ms"（剩下 28% 是首页/健康检查/POST 这类）。

补充排查结果（都不支持其他解释）：
- 全部 12 个 Deployment 与 12 个 Service 的 selector/targetPort 均与各自 last-applied 一致，唯一被改动的就是 checkoutservice 的 env；endpoints 全部正常（每个 Service 都有健康后端）。
- 所有 Pod Running/Ready、0 重启，全命名空间仅 1 条 Warning 事件（checkoutservice 启动时 readiness 探测一次未通过，属重建过程）。
- recommendationservice Pod 配置是标准值（CPU limit 200m，与 last-applied 一致）、Ready、无探针失败；它自己调用 productcatalogservice 的那一段很快（处理器入口到响应只有 4ms）→ 更像是**入方向被注入了约 400ms 的网络延迟**，而不是该服务处理慢或 CPU 被限死。
  （若延迟来自宿主机 tc/注入器按 selector 持续下发，重启 Pod 可能无效——这是本轮唯一的不确定点。）
