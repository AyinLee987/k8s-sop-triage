规则：
1. 每条写清“看到什么现象 → 怎么判断、下一步查什么”，具体到可以照做；不要写这次故障里的 Pod 名、IP、时间。
2. 对整个系统都适用的经验写进 boutique-triage-overview；只和某个服务有关的写进那个服务的 SOP。
3. 已有条目能覆盖的，就修改那一条，不要新增重复的；发现已有条目和这次的记录矛盾，可以修改或删除它。
4. 最多 3 处改动，每条不超过 500 字；没有值得写的就让 changes 为空。
5. 记录分两部分：agent 当时的一次性诊断（只读排查，没有人验证过），以及值班工程师之后实际做的每一步操作和每一步之后的用户侧数字。工程师没有写原因，做的也不一定是 agent 建议的。你要自己对照：哪一步之后哪个数字变了、哪一步之后没有变，这说明了什么；agent 的诊断哪些和这些结果相符、哪些不符。只有被这些结果支持的内容才能写成经验：某一步之后对应的症状消失的，写成【已证实】；某一步之后数字没有变化的，写成【已排除】并说明排除了什么；这些数字无法检验的猜测，不能写成结论，最多写成【未解决】并说明还缺什么证据。每条以这三个标记之一开头。
6. 条目要写成换一个服务、换一种故障也能照做的判断方法：看哪几样证据、拿什么和什么比较、什么结果支持哪种解释、怎样排除另一种解释。不要把这次测到的具体数值（例如多少毫秒、百分之几）、具体的服务组合写成判断条件；这次的情况最多放在条目末尾做一句例子。一条经验如果只在“同一个服务出同一个故障”时才用得上，就不要写。
7. 每条经验都要写清适用范围，用下面的固定结构：“适用：<看到哪些可以查到的证据时才用这一条>。不适用：<看到什么证据时不要用这一条，应该改查什么>。做法：<怎么判断>。”适用和不适用的条件必须是排查时能实际查到的东西（日志里的字段、事件、配置项、指标），不能是“当问题是 X 时”这种要先知道答案才能判断的条件。这次的记录只说明这一种情况；同样的现象可能有别的原因（例如变慢可以来自网络、CPU 限流、应用自身、下游排队），不要因为这一次是某种原因，就把这种现象直接指向这种原因，更不要写“先查 A，不要先查 B”，除非记录里有证据说明 B 已经被排除。
8. 把故障当作生产环境里自然发生的事来写：不要用“注入”“被注入”这类说法，也不要假设故障是谁故意加上去的。

【boutique-triage-overview】Online Boutique（命名空间 boutique）排查总则：服务调用关系、按症状选入口 SOP、跨服务跳转原则、怎么判断故障源头。排查这个命名空间的任何问题时先读。
  - [E1]（BH01、BH02、BH03）【已证实】调用方连不上某个下游时，Endpoints、端口和地址配置都要核对。适用：调用方日志出现 dial tcp <地址>:<端口> connection refused 或 i/o timeout；或者上游返回 Internal/Unavailable，错误文本指出某一步下游调用失败，而该下游自身日志没有错误、仍在正常处理其他调用方的请求。不适用：下游自身日志有报错或处理耗时变大，应改查该下游的负载和它的依赖。做法：(1) 查该 Service 的 Endpoints，subsets 为空时比较 selector 和 Pod labels；(2) Endpoints 有地址时，把调用方 *_ADDR 等地址类环境变量里的端口和 Service port/targetPort、容器监听端口比较；再拿线上 Deployment 的 env 和 last-applied-configuration 注解、旧 ReplicaSet 模板比较，看新 ReplicaSet 的创建时间是否和故障开始时间吻合。修正后这类报错和对应接口的失败应归零。例：几次分别是 selector 指错标签、调用方配置里的下游端口被改成对方没有监听的端口。
  - [E2]（BH01、BH02、BH03、BH04、BH05、BH06）【已证实】变慢定位到下游后，区分应用内慢和网络路径慢。适用：调用方各接口耗时随调用某些下游的次数成比例增加，不调它们的接口和健康检查仍然很快。不适用：下游日志里单个请求从入口到返回的处理耗时同样变大，应改查它的CPU节流、负载或它的下游。做法：用调用方请求起始时刻和下游入口日志逐跳对时，发起到入口间隔大、内部处理快，说明延迟在应用之外；也可看耗时是否按往返次数成固定台阶增长、下游连续日志间隔是否变成固定步长；另一个独立调用方也按调用次数同样变慢，说明慢点在该下游一侧而不是某个调用方的连接。随后到慢接口涉及的每个下游Pod所在节点查veth tc qdisc和网络策略，逐个查，不能因一个下游已能解释全部延迟就排除其他。没有cfs throttled指标不能下CPU节流结论；没有节点权限时只能写“网络路径或进程内”，并申请节点侧检查。重建Pod能否清除这类规则仍未验证，几次都是直接清除规则后恢复。例：一次只有一个下游的veth带规则，清除后各分位数恢复正常。
  - [E3]（BH01、BH03、BH06）【已排除】多个症状同时出现时，不要默认它们是同一个根因。适用：用户侧或调用方日志同时出现错误（500、下单失败、调用下游报connection refused等）和整体变慢。不适用：只有一种症状。做法：按症状分别找证据链；每做一步修复后，分别看错误数和延迟分位数，哪个变了、哪个没变。修好报错后延迟分布不变，说明报错链路不是变慢的原因，应继续单独追查变慢；反过来也一样，去掉延迟来源不能代替修复报错。立即失败的调用（connection refused、Endpoints为空）自身耗时很短，通常不贡献延迟，可先用调用方日志里该调用的耗时核对，但仍以修复后分位数是否变化为准。例：几次先修好地址/端口配置或把副本为0的下游恢复，报错消失但慢请求占比和各分位数基本不变；之后清除另一个下游veth上的tc规则，延迟才恢复。
  - [E4]（BH04）【已证实】多个服务同时显得变慢时，先找最小源头集合，不要把每个变慢的服务都当作根因。适用：调用方日志或逐跳对时显示多个下游的调用耗时同时变大，且其中一些下游本身还会调用另一些下游。不适用：只有一个下游变慢，按E2处理。做法：对每个变慢的服务，把它自己的处理时间和它等待下游的时间分开算；只调用了其他变慢服务、自身处理并不慢的，先标为“继承”；从调用图的叶子一侧开始查源头，修复后看继承的服务是否一起恢复。仅凭“某次调用前后的时间差”给一个服务归因不可靠，这个差值可能包含了其他调用。例：只清除两个叶子下游的规则，被一并怀疑的推荐和广告服务也随之恢复。

### 证据链

**1. 下单失败：checkoutservice 的 `SHIPPING_SERVICE_ADDR` 指向了错误端口**

frontend 日志（`frontend-fd686dbb-dmxdc`，近 30 分钟，按 `error|failed|500` 过滤，共 178 条匹配，展示最新 100 条）中所有 `/cart/checkout` 的 500 都是同一条：

```
"failed to complete the order: rpc error: code = Internal desc = shipping quote failure:
 failed to get shipping quote: rpc error: code = Unavailable desc = connection error:
 dial tcp 10.96.50.166:50052: i/o timeout"
```

- `10.96.50.166` = Service `shippingservice` 的 ClusterIP，而该 Service **只暴露 50051**（`port 50051 → targetPort 50051`，Endpoint `10.244.0.133:50051`），shippingservice Pod 的 `PORT=50051`。
- 但运行中的 checkoutservice Deployment（gen 76 / revision 74）env 是 `SHIPPING_SERVICE_ADDR=shippingservice:50052`。
- 对比可证这是**运行态配置被改**，不是历史遗留：旧 ReplicaSet `checkoutservice-5d5f4589c5`（2026-11-15 创建）里是 `shippingservice:50051`；07:08:04 新建的 `checkoutservice-77b8f6dc84` 里变成 `50052`（事件：`Scaled up replica set checkoutservice-77b8f6dc84 from 0 to 1` + 旧 RS `Scaled down … from 1 to 0`），`last-applied-configuration` 里也仍是 50051。同一 Deployment 其它地址（productcatalog:3550 / payment:50051 / email:5000 / currency:7000 / cart:7070）都对得上各自 Service。
