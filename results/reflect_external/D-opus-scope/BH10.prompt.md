【boutique-triage-overview】Online Boutique（命名空间 boutique）排查总则：服务调用关系、按症状选入口 SOP、跨服务跳转原则、怎么判断故障源头。排查这个命名空间的任何问题时先读。
  - [E1]（BH01、BH02、BH03、BH07）【已证实】调用方连不上某个下游时，Endpoints、端口和地址配置都要核对。适用：调用方日志出现 dial tcp <地址>:<端口> connection refused 或 i/o timeout；或上游返回 Internal/Unavailable，错误文本指出某一步下游调用失败，而该下游自身日志无错误、仍在正常处理其他调用方的请求。不适用：下游自身日志有报错或处理耗时变大，应改查该下游的负载和它的依赖。做法：(1) 查该 Service 的 Endpoints，subsets 为空时比较 selector 和 Pod labels，并看 Deployment replicas 是否为 0；(2) Endpoints 有地址时，把错误文本里的端口和调用方 *_ADDR 等地址类环境变量、Service port/targetPort、容器监听端口比较；连 ClusterIP 上 Service 没有暴露的端口时报错可能是 i/o timeout 而不是 refused，所以超时也要先核对端口再判断是否网络路径问题；再拿线上 Deployment 的 env 和 last-applied-configuration 注解、旧 ReplicaSet 模板比较，看新 ReplicaSet 创建时间是否和故障开始吻合。修正后这类报错和对应接口的失败应归零。例：几次分别是 selector 指错标签、调用方配置里的下游端口被改成对方没有监听的端口。
  - [E2]（BH01、BH02、BH03、BH04、BH05、BH06、BH08、BH09）【已证实】变慢定位到下游后，按往返次数找到具体一跳，再区分应用内慢和网络路径慢。适用：调用方各接口耗时随调用某些下游（含缓存、数据库等非gRPC依赖）的次数成比例增加，不调它们的接口和健康检查仍然很快。不适用：下游日志里单个请求的处理耗时同样变大，应改查它的CPU节流、负载或它的下游。做法：列出每个接口对每一跳的往返次数，看耗时是否按某一跳次数成固定台阶增长，定位到具体一跳（含二级下游）；按调用方发起时刻、下游入口日志、下游完成日志、调用方拿到响应后的下一条日志逐跳对时，发起到入口间隔大而内部处理和回程都快，说明延迟在应用之外；另一独立调用方同样变慢，说明慢点在下游一侧。随后查该跳两端Pod所在节点的veth tc qdisc和网络策略。没有cfs throttled指标不能下CPU节流结论；无节点权限时只写“网络路径或进程内”并申请节点侧检查。重建Pod、调大CPU limit能否消除仍未验证，几次都是直接清除规则后恢复。例：一次是被调用服务的veth带规则。
  - [E3]（BH01、BH03、BH06、BH09）【已排除】多个症状同时出现时，不要默认它们是同一个根因。适用：用户侧或调用方日志同时出现错误（500、下单失败、调用下游报connection refused、warning级的下游调用失败等）和整体变慢。不适用：只有一种症状。做法：按症状分别找证据链；每做一步修复后，分别看错误数和延迟分位数，哪个变了、哪个没变。修好报错后延迟分布不变，说明报错链路不是变慢的原因，应继续单独追查变慢；反过来也一样，去掉延迟来源不能代替修复报错。立即失败的调用（connection refused、Endpoints为空）自身耗时很短，通常不贡献延迟，可先用调用方日志里该调用的耗时核对，但仍以修复后分位数是否变化为准。用户侧没有失败、调用方只记warning的报错也是真实缺陷，要修但不能当作变慢的解释。例：几次先修好端口配置、Service selector或副本为0的下游，报错消失但慢请求占比和各分位数不变；清除另一个下游veth上的tc规则后延迟才恢复。
  - [E4]（BH04）【已证实】多个服务同时显得变慢时，先找最小源头集合，不要把每个变慢的服务都当作根因。适用：调用方日志或逐跳对时显示多个下游的调用耗时同时变大，且其中一些下游本身还会调用另一些下游。不适用：只有一个下游变慢，按E2处理。做法：对每个变慢的服务，把它自己的处理时间和它等待下游的时间分开算；只调用了其他变慢服务、自身处理并不慢的，先标为“继承”；从调用图的叶子一侧开始查源头，修复后看继承的服务是否一起恢复。仅凭“某次调用前后的时间差”给一个服务归因不可靠，这个差值可能包含了其他调用。例：只清除两个叶子下游的规则，被一并怀疑的推荐和广告服务也随之恢复。
  - [E5]（BH07）【已排除】调用方日志里的下游报错不一定是用户侧失败的原因，要区分被降级的依赖和致命的必经步骤。适用：调用方日志同时出现多个不同下游的调用失败，且用户侧有 500 或某个操作失败。不适用：只有一个下游报错，直接按 E1 处理。做法：把每类下游报错和同一条请求日志的路径、返回状态对应起来：报错出现时请求仍返回 200 的，是被调用方降级处理的依赖，只影响页面部分内容；报错文本出现在返回 500 的请求里、且对应该操作的必经步骤的，才是失败的候选原因。还可看必经步骤之后的下游是否几乎没有来自该调用方的日志，确认流程在哪一步中断。修复时每步之后分别看 500 数和对应操作失败数：修好降级依赖后失败数不变，即排除它对失败的贡献；修好必经步骤后失败归零才算证实。例：先恢复副本为 0 的推荐服务，下单失败数不变；改正结算服务里配送服务地址的端口后下单全部成功。
  - [E6]（BH08）【已排除】故障前后出现的手工配置改动不一定是根因，要用时间线和回滚后的数字检验。适用：某Deployment的env与last-applied-configuration不一致，或新ReplicaSet创建时间接近症状开始。不适用：调用方报错文本指向地址或端口，按E1核对。做法：比较新Pod Ready时刻、新Pod上线后第一批请求的耗时和状态、症状起点；新Pod已经正常服务一段时间后症状才出现，说明该改动不是触发点，应继续按症状找证据链，不要停在这个改动上。如果仍要回滚，回滚后分别看错误数和各分位数，都没有变化即排除它。例：一次删掉调用方多出的发布标签环境变量并滚动更新后，慢请求占比和各分位数不变。
