【boutique-triage-overview】Online Boutique（命名空间 boutique）排查总则：服务调用关系、按症状选入口 SOP、跨服务跳转原则、怎么判断故障源头。排查这个命名空间的任何问题时先读。
  - [E1]（BH01、BH02、BH03）【已证实】调用方连不上某个下游时，Endpoints、端口和地址配置都要核对。适用：调用方日志出现 dial tcp <地址>:<端口> connection refused 或 i/o timeout；或者上游返回 Internal/Unavailable，错误文本指出某一步下游调用失败，而该下游自身日志没有错误、仍在正常处理其他调用方的请求。不适用：下游自身日志有报错或处理耗时变大，应改查该下游的负载和它的依赖。做法：(1) 查该 Service 的 Endpoints，subsets 为空时比较 selector 和 Pod labels；(2) Endpoints 有地址时，把调用方 *_ADDR 等地址类环境变量里的端口和 Service port/targetPort、容器监听端口比较；再拿线上 Deployment 的 env 和 last-applied-configuration 注解、旧 ReplicaSet 模板比较，看新 ReplicaSet 的创建时间是否和故障开始时间吻合。修正后这类报错和对应接口的失败应归零。例：几次分别是 selector 指错标签、调用方配置里的下游端口被改成对方没有监听的端口。
  - [E2]（BH01、BH02、BH03、BH04）【已证实】变慢定位到下游后，区分应用内慢和网络路径慢。适用：调用方各接口耗时随调用某些下游的次数成比例增加，不调它们的接口和健康检查仍然很快。不适用：下游自身日志里从入口到返回的处理耗时同样变大，应改查它的CPU节流、负载或它的下游。做法：用调用方和下游日志的时间戳逐跳对时，调用方发起到下游入口的间隔大、下游内部处理快，说明延迟在应用之外；也可以看耗时是否按往返次数成固定台阶增长。随后到每个候选下游Pod所在节点查它的veth tc qdisc（netem等非默认规则）、网络策略，同一次故障可能有多个Pod同时带有规则。没有cfs throttled指标不能下CPU节流结论。重建Pod能否清除这类规则没有验证过，几次都是直接清除规则后恢复。例：一次有两个下游的veth同时带有延迟规则。
  - [E3]（BH01、BH03）【已排除】多个症状同时出现时，不要默认它们是同一个根因。适用：用户侧同时出现错误（500、下单失败）和整体变慢。不适用：只有一种症状。做法：按症状分别找证据链；每做一步修复后，分别看错误数和延迟分位数，哪个变了、哪个没变。修好报错后延迟分布不变，说明报错链路不是变慢的原因，应该继续单独追查变慢；反过来也一样，去掉延迟来源不能代替修复报错。例：两次都是先修好结账链路上的地址或端口配置，500 和下单失败归零，但慢请求占比和各分位数基本不变；之后清除另一个下游 veth 上的 tc 规则，延迟才恢复。
  - [E4]（BH04）【已证实】多个服务同时显得变慢时，先找最小源头集合，不要把每个变慢的服务都当作根因。适用：调用方日志或逐跳对时显示多个下游的调用耗时同时变大，且其中一些下游本身还会调用另一些下游。不适用：只有一个下游变慢，按E2处理。做法：对每个变慢的服务，把它自己的处理时间和它等待下游的时间分开算；只调用了其他变慢服务、自身处理并不慢的，先标为“继承”；从调用图的叶子一侧开始查源头，修复后看继承的服务是否一起恢复。仅凭“某次调用前后的时间差”给一个服务归因不可靠，这个差值可能包含了其他调用。例：只清除两个叶子下游的规则，被一并怀疑的推荐和广告服务也随之恢复。

### 定位过程与证据

**1. 页面延迟分布（frontend 自身日志，`took_ms`，最近约 2 分钟，345 条 `request complete`）**

| 路径 | 延迟 |
|---|---|

| `GET /product/*` | 377–448 ms（稳定 ~415）|
| `GET /cart` | 4 个明显分层：~700 / ~880–950 / ~1090–1190 / ~1310–1330（每个购物车条目 +~200 ms）|

`POST /cart` 只花 1 ms，这说明 `productcatalogservice`、`cartservice`、`redis-cart` 都很快，请求路径本身没有异常。

**2. 时间戳逐条对齐，发现延迟在 `currencyservice` 的入口**

把 frontend 每个页面的起始时刻（= 完成时刻 − `took_ms`）与 `currencyservice-6df4cccbb9-ltrd7` 的 `Getting supported currencies...`（该日志在 handler **入口**打印）逐条比对，06:13:00–06:13:12 窗口内 **15 个页面请求 / 15 条 GSC 日志，一一对应**，偏移分别为：

```
199, 210, 194, 188, 191, 192, 212, 210, 211, 207, 206, 209, 200, 207, 204 ms
```

即：请求发出后 **约 200 ms 才到达 currencyservice 进程**；而 handler 执行完后返回很快（例：`/product/OLJCESPC7Z` 起始 06:13:05.015 → GSC 05.225 → 转换完成日志 05.434 → frontend 完成 05.442，**响应仅 +8 ms**）。同一毫秒内多次出现 2 条转换完成日志（84.876/84.876、89.997/89.997、91.055/91.056），说明业务处理本身是瞬时的。

**3. 延迟只伴随 currency 的 RPC 数量**

- home = product + 9 次额外转换：`2080 − 415 ≈ 1665 ms ÷ 9 ≈ 185 ms/次`
- cart 每个条目 +~200 ms（每次 `Convert`）
- 服务端日志速率 ~6 次转换/s，负载很低，排除 CPU 排队/限流（且容器 CPU limit 200m/request 100m 为官方 demo 标准值）

**4. 排除的其他可能**
- 镜像全部为标准 `us-central1-docker.pkg.dev/google-samples/microservices-demo/*:v0.10.3`，无自定义镜像、无 sidecar/initContainer、无 chaos 容器。
- 所有 Deployment 的 env、资源、Service `targetPort` 与 Endpoints（`currencyservice → 10.244.0.87:7000`，唯一后端）均正确。
- adservice 正常：`received ad request` 日志与 frontend 请求**完成时刻**相差 ≤2 ms（它是 handler 最后一个调用，且很快）。
- 12 个 Pod 全部 Running、READY、0 重启；0 个 500；无相关 Event。
- **不是 frontend 单侧问题**：`checkoutservice`（另一个 Pod，10.244.0.86）也慢——`[PlaceOrder]` 06:12:44.830 → `payment went through` 06:12:45.959，前置阶段 1129 ms，与“每个条目 1 次货币转换 ×200 ms”吻合。两个不同客户端都慢，共同点只有 `currencyservice` 这一个 Pod。
