4. 最多 3 处改动，每条不超过 500 字；没有值得写的就让 changes 为空。
5. 记录分两部分：agent 当时的一次性诊断（只读排查，没有人验证过），以及值班工程师之后实际做的每一步操作和每一步之后的用户侧数字。工程师没有写原因，做的也不一定是 agent 建议的。你要自己对照：哪一步之后哪个数字变了、哪一步之后没有变，这说明了什么；agent 的诊断哪些和这些结果相符、哪些不符。只有被这些结果支持的内容才能写成经验：某一步之后对应的症状消失的，写成【已证实】；某一步之后数字没有变化的，写成【已排除】并说明排除了什么；这些数字无法检验的猜测，不能写成结论，最多写成【未解决】并说明还缺什么证据。每条以这三个标记之一开头。

  - [E2]（BH01、BH02、BH03、BH04、BH05、BH06、BH08、BH09）【已证实】变慢定位到下游后，按往返次数找到具体一跳，再区分应用内慢和网络路径慢。适用：调用方各接口耗时随调用某些下游（含缓存、数据库等非gRPC依赖）的次数成比例增加，不调它们的接口和健康检查仍然很快。不适用：下游日志里单个请求的处理耗时同样变大，应改查它的CPU节流、负载或它的下游。做法：列出每个接口对每一跳的往返次数，看耗时是否按某一跳次数成固定台阶增长，定位到具体一跳（含二级下游）；按调用方发起时刻、下游入口日志、下游完成日志、调用方拿到响应后的下一条日志逐跳对时，发起到入口间隔大而内部处理和回程都快，说明延迟在应用之外；另一独立调用方同样变慢，说明慢点在下游一侧。随后查该跳两端Pod所在节点的veth tc qdisc和网络策略。没有cfs throttled指标不能下CPU节流结论；无节点权限时只写“网络路径或进程内”并申请节点侧检查。重建Pod、调大CPU limit能否消除仍未验证，几次都是直接清除规则后恢复。例：一次是被调用服务的veth带规则。
  - [E3]（BH01、BH03、BH06、BH09）【已排除】多个症状同时出现时，不要默认它们是同一个根因。适用：用户侧或调用方日志同时出现错误（500、下单失败、调用下游报connection refused、warning级的下游调用失败等）和整体变慢。不适用：只有一种症状。做法：按症状分别找证据链；每做一步修复后，分别看错误数和延迟分位数，哪个变了、哪个没变。修好报错后延迟分布不变，说明报错链路不是变慢的原因，应继续单独追查变慢；反过来也一样，去掉延迟来源不能代替修复报错。立即失败的调用（connection refused、Endpoints为空）自身耗时很短，通常不贡献延迟，可先用调用方日志里该调用的耗时核对，但仍以修复后分位数是否变化为准。用户侧没有失败、调用方只记warning的报错也是真实缺陷，要修但不能当作变慢的解释。例：几次先修好端口配置、Service selector或副本为0的下游，报错消失但慢请求占比和各分位数不变；清除另一个下游veth上的tc规则后延迟才恢复。
  - [E4]（BH04）【已证实】多个服务同时显得变慢时，先找最小源头集合，不要把每个变慢的服务都当作根因。适用：调用方日志或逐跳对时显示多个下游的调用耗时同时变大，且其中一些下游本身还会调用另一些下游。不适用：只有一个下游变慢，按E2处理。做法：对每个变慢的服务，把它自己的处理时间和它等待下游的时间分开算；只调用了其他变慢服务、自身处理并不慢的，先标为“继承”；从调用图的叶子一侧开始查源头，修复后看继承的服务是否一起恢复。仅凭“某次调用前后的时间差”给一个服务归因不可靠，这个差值可能包含了其他调用。例：只清除两个叶子下游的规则，被一并怀疑的推荐和广告服务也随之恢复。
  - [E5]（BH07、BH10）【已排除】调用方日志里的下游报错或某个下游的配置错误，不一定是用户侧失败的原因，要区分被降级的依赖和致命的必经步骤。适用：调用方日志或配置检查同时发现多个下游有问题（调用报错、Endpoints 为空、端口不一致等），且用户侧有 500 或某个操作失败。不适用：只有一个下游有问题，直接按 E1 处理。做法：把每类下游报错和同一条请求日志的路径、返回状态对应：报错出现时请求仍返回 200 的，是被调用方降级处理的依赖，只影响页面部分内容；报错文本出现在返回 500 的请求里、且属于该操作必经步骤的，才是失败候选。还可看必经步骤之后的下游是否几乎没有来自该调用方的日志，确认流程在哪一步中断。修复时一次只改一处，每步之后分别看 500 数和对应操作失败数：修好降级依赖后两者不变，即排除它对失败的贡献；修好必经步骤后失败归零才算证实。例：两次先恢复没有流量的推荐或广告服务，500 和下单失败都不变；改正必经下游的端口配置后全部恢复。
  - [E6]（BH08）【已排除】故障前后出现的手工配置改动不一定是根因，要用时间线和回滚后的数字检验。适用：某Deployment的env与last-applied-configuration不一致，或新ReplicaSet创建时间接近症状开始。不适用：调用方报错文本指向地址或端口，按E1核对。做法：比较新Pod Ready时刻、新Pod上线后第一批请求的耗时和状态、症状起点；新Pod已经正常服务一段时间后症状才出现，说明该改动不是触发点，应继续按症状找证据链，不要停在这个改动上。如果仍要回滚，回滚后分别看错误数和各分位数，都没有变化即排除它。例：一次删掉调用方多出的发布标签环境变量并滚动更新后，慢请求占比和各分位数不变。
  - [E7]（BH11、BH12）【已证实】只有部分请求变慢、没有报错时，按“每次调用有一定概率被加上一段固定延迟”来定位是哪一跳。适用：用户侧中位数正常、高分位很差，没有5xx；慢请求耗时集中在某个固定值或它的整数倍；不调用后端的接口始终很快。不适用：所有请求一起变慢，或下游日志里单个请求的处理耗时变大，这时按E2或查下游负载。做法：(1)按处理代码或下游入口日志数出每个接口对每个下游的调用次数，间接调用也要算，不要凭接口名估计；(2)看各接口慢请求占比是否随某个下游的调用次数单调上升、调用次数为0的接口是否始终不慢；另一个独立调用方覆盖该下游的调用段也出现同样的固定延迟，可佐证慢点在该下游一侧；(3)找只出现在某一个Pod上的异常，如kubelet探针connect timeout，它不经过其他服务，可作独立证据；(4)查该Pod两端veth上的tc qdisc。耗时落在100ms整数倍不能当作CPU节流的证据，网络路径上的固定延迟会产生同样的形状；没有cfs throttled指标时不能归因CPU节流。例：两次分别是商品目录、货币服务的veth带规则，清除后长尾消失，CPU limit都没有改。

### 两个仍无法区分的机制（缺 cgroup / metrics 数据）
1. **CPU 限流**：Redis 8 镜像带 4 个模块 + 16 个工作线程，125m quota 下突发即被 CFS 限流，产生 100–200ms 级停顿；
2. **瞬时不响应/网络丢包**：丢包更契合「dial tcp i/o timeout >1s」（SYN 重传 1s）与「+200ms RTO」这一对现象。
两者都落在 redis-cart 上，且都能被「提高 CPU 上限 + 重建 Pod（新 sandbox，清掉阻塞/网络规则）」覆盖。

次要可能：cartservice（.NET，limit 300m/128Mi）自身 GC/线程池停顿也能造成同样 200ms，但它无法解释 kubelet→redis 的探针超时，概率较低，留作第 2 轮验证目标。
