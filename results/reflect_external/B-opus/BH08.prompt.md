【boutique-triage-overview】Online Boutique（命名空间 boutique）排查总则：服务调用关系、按症状选入口 SOP、跨服务跳转原则、怎么判断故障源头。排查这个命名空间的任何问题时先读。
  - [E1]（BH01、BH06）现象：用户反馈变慢和/或请求失败，或只说“变慢、没报错”。判断：(1) 不要默认只有一个根因，也不要因用户侧 5xx 为 0 就认为没有错误：扫调用方日志里被降级吞掉的错误（可选功能调用失败、页面照常返回），它们常是同时存在的第二个故障。(2) 按接口/handler 把请求分成“报错的”和“慢但成功的”两组，各自顺调用链查：报错组看错误内容和目标地址，慢组看耗时分布。(3) 判断某个错误是否贡献延迟：看它是毫秒级快速失败还是超时失败，并检查慢 handler 的耗时是否已被其他下游“调用次数×单次增量”完全解释；已解释完则该错误只是独立故障，单独给出根因和修复。只有慢和错都卡在同一下游、同一错误上才合并。例：页面变慢来自一个下游的固定延迟，同时另一个下游缩容导致快速失败的报错日志。
  - [E2]（BH01、BH02、BH03、BH06、BH07）现象：调用方日志报 dial tcp <ClusterIP>:<端口> i/o timeout、connection refused，或 gRPC 错误链显示某下游步骤失败。判断：(0) 先按错误类型分流：对 ClusterIP 报 connection refused，优先怀疑 Service 无 Endpoints；报 i/o timeout，优先核对端口是否为 Service 实际暴露的端口。(1) 从错误确定目标下游和端口，反查 Endpoints。为空时看 Deployment 的 replicas 和 Ready Pod 数：replicas 为 0，查 ScalingReplicaSet/SuccessfulDelete 事件确认被缩容，恢复副本数；有 Ready Pod 仍为空，逐字比对 selector 与 Pod labels，修 selector。(2) Endpoints 正常时，把调用方 *_ADDR 端口与 Service port/targetPort、容器监听端口逐一比较。(3) 被调方无错、日志显示仍在服务其他调用方时，问题在调用方配置：对比线上 env 与 last-applied-configuration、新旧 ReplicaSet 模板及创建时间，修调用方配置，不动被调方。Pod 刚启动时短暂 refused 随后自愈的不算根因。例：调用方地址端口被改成 Service 没有的端口，表现为 i/o timeout，而另一个被缩到 0 的服务表现为 refused。
  - [E3]（BH01、BH02、BH03、BH05）现象：整站变慢，无错误日志。判断：(1) 找瓶颈：把各 handler 耗时与它调用了哪些下游、各几次比较。先找最快的 handler 作对照：它调用到的下游都可排除；只有调用某下游的 handler 变慢、耗时随该下游调用次数（如列表条目数）成台阶增加，瓶颈就在该下游。(2) 定位延迟在哪一段：比较调用方发起调用的时间（完成时刻减耗时）、被调方 handler 入口日志时间、被调方返回后调用方完成的时间，注意区分被调方日志是入口打印还是出口打印。耗时集中在到达被调方之前、被调方处理和出向调用都很快，支持该 Pod 入方向网络延迟；耗时在处理内部、CPU limit 低、随负载波动，支持 CFS 节流；负载很低时仍慢可排除节流。(3) 对照变慢开始时间与 Pod 创建/Ready 时间。网络延迟先重建 Pod，节流先提高 limit；修复后仍慢按 E6 转查注入源或节点。例：被调方收到请求比调用方发起晚一个稳定间隔，而处理只要几毫秒。
  - [E4]（BH03、BH07）现象：有多个嫌疑对象，或不确定最近改了什么。判断：(1) 对命名空间内所有 Deployment 和 Service，把线上 spec（env、镜像、selector、port/targetPort、replicas、resources）与 last-applied-configuration 逐项比对，并查各 Deployment 的 ReplicaSet revision、创建时间和缩扩容事件。(2) 找到一处变更后，取它的事件时间，在全命名空间事件里查同一时刻前后的其他变更（新 RS、缩容、删除）：同一时刻发生的往往是同一批改动，每一处都要单独判断影响并修复，不要找到一个就停。(3) 差异与故障开始时间吻合时，优先作为配置类根因并验证。注意网络延迟注入、节点问题不会改 spec，比对干净的服务仍异常时，按 E3 转查网络或资源，不能据此排除它。例：一个服务的 env 被改与另一个服务被缩容发生在同一秒。
  - [E5]（BH04）现象：整站变慢、无错误日志，按 E3 找到一个慢下游，但它解释不了全部耗时。判断：(1) 对每个 handler 数出它对各下游的调用次数，用调用方日志里相邻两次调用的时间戳间隔估算每个下游单次调用耗时。(2) 用“各下游单次增量×调用次数”去拼每个 handler 的总耗时（含下游的内部再调用），拼不齐说明还有被漏掉的慢下游，继续逐跳对时间戳。(3) 同一时间窗内找出往返仍正常的下游作对照：只有部分 Pod 变慢、其余正常，支持针对这些 Pod 的注入/入方向网络问题，排除节点 CPU 和全局网络。根因要列出所有被抬高的下游，修复一并覆盖。例：多个下游各被抬高相同的一段，页面耗时约等于增量乘以调用次数之和。
  - [E6]（BH04）现象：修复需要重建 Pod（尤其是用 emptyDir 等非持久存储的有状态服务，如缓存/数据库），或重建后要复核效果。判断：(1) 重建前先评估副作用：会丢失哪些数据，哪些接口会因数据变少而“假性变快”或行为变化，复核时以不受这些数据影响的接口为准。(2) 有依赖关系的先重建被依赖方，再重建调用方，确保重新建连。(3) 重建后与故障前的健康基线比较：恢复则说明问题附着在 Pod 运行期状态上；完全不变说明是按 label 持续施加的外部注入（chaos 实验、sidecar、节点 tc 规则）或节点问题，不要重复重启，转去查注入源或节点。
  - [E7]（BH05）现象：某个调用方变慢，不确定是调用方自身/其所在节点的问题，还是某个下游的问题。判断：(1) 找出另一个独立的调用方（不同 Pod、最好不同 handler 路径），看它调用同一批下游的阶段是否也变慢；用它日志里相邻步骤的时间戳间隔估算各段耗时。(2) 两个调用方都慢，取它们共同调用的下游的交集，交集里再用 E3 的对照法排除仍快的下游，剩下的就是嫌疑；只有一个调用方慢、另一个正常，转查慢调用方自身（资源、节点、出方向网络）。(3) 对嫌疑之外的下游做反证：挑一个在 handler 末尾才被调用的下游，其入口日志应与调用方完成时刻几乎重合，重合即说明该下游及调用方出向网络正常。例：前端页面和下单流程都慢，共同点只有一个被两者调用的下游 Pod。
  - [E8]（BH07）现象：某个多步骤业务流程（如下单）全部失败，其他页面正常、请求快速返回而非超时变慢。判断：(1) 取调用方返回的完整错误链，从外到内读到最内层的那一跳，确定流程卡在哪个步骤、连的是哪个下游地址。(2) 用流程的固定调用顺序反证：失败步骤之后的下游应几乎没有来自该流程的调用日志，之前的下游应有正常调用；若与之相符，后面那些服务的“安静”是流程提前中止的结果，不要当成它们的故障。(3) 失败率是该流程的 100%，且只这一流程受影响，优先查流程编排方（调用方）到该步骤下游的连接配置，按 E2 处理。例：下单在运费报价一步就失败，支付服务因此几乎没有调用日志。

**The tax is per Redis round-trip, not per request or per gRPC call** — this is the key decomposition:
- `GET /cart` = 1 cart call = **1** Redis op (`HGETALL`) → 284–340 ms (fast mode: 13 ms)
- `POST /cart` (`addToCart` = `getProduct` + `addToCart`, i.e. **2** Redis ops: `HGET`+`HSET`) → 564–631 ms = **2.0×** the above
- `POST /cart/checkout` (checkoutservice does `GetCart` + `EmptyCart` = **2** Redis ops, plus ~8 other RPCs) → 578–644 ms
- `POST /setCurrency` (no downstream RPC) → **0 ms** throughout

So each `cartservice`→`redis-cart:6379` round trip costs ~285 ms (floor 283, ceiling ~345), where it cost <1 ms at 07:13:39. The 2.0 ratio also rules out a delay attached to the cartservice pod's own network (that would give 1.5×), and rules out packet loss (every single op is ≥283 ms — nothing comes through fast).

**Everything else is provably healthy.** `GET /` renders 12+ RPCs (currency `GetSupportedCurrencies` + 10× `Convert`, catalog `ListProducts`, cart `GetCart`) in 297–346 ms — i.e. ~30 ms for all 12 non-cart RPCs plus 290 ms for the one cart op. So catalog/currency/shipping/ads/recommendations are fast; only the redis hop is slow.
Also verified and *not* the cause: all 12 Services have correct selectors and correct `targetPort`, every Endpoints object resolves to the one running pod IP (no stale endpoints), all pods Running/Ready with 0 restarts, `resources` for every deployment match upstream defaults, and no errors in frontend/cartservice/redis/ad/currency/recommendation logs. (Redis is Redis 8.10.3 with modules, AOF disabled, no BGSAVE in its log, empty dataset on a fresh `emptyDir`.)
