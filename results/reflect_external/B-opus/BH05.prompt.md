【boutique-triage-overview】Online Boutique（命名空间 boutique）排查总则：服务调用关系、按症状选入口 SOP、跨服务跳转原则、怎么判断故障源头。排查这个命名空间的任何问题时先读。
  - [E1]（BH01）现象：用户同时反馈变慢和请求失败（例如下单失败）。判断：不要默认是同一个根因。先按接口/handler 把请求分成“报错的”和“慢但成功的”两组，各自顺着调用链查。报错组看调用方错误日志里的具体错误和目标地址；慢组看各 handler 的耗时分布。两组指向不同下游时，分别给出根因和修复。只有当慢请求和失败请求都卡在同一个下游、同一种错误上时，才合并成一个根因。例：下单失败来自一个服务的配置错误，整站变慢来自另一个服务的资源瓶颈。
  - [E2]（BH01、BH02、BH03）现象：调用方日志报 dial tcp <ClusterIP>:<端口> i/o timeout、connection refused，或 gRPC 错误链显示某个下游步骤失败，且首次失败耗时为秒级（建连超时）、之后都是毫秒级快速失败。判断：(1) 从错误链和日志确定目标下游和端口，反查 Service 看 Endpoints；为空时逐字比对 selector 与 Pod labels（键名、取值、后缀），修 selector，不动 Pod 和调用方。(2) Endpoints 正常时，把调用方 *_ADDR 中的端口与 Service port/targetPort、容器实际监听端口逐一比较。(3) 被调方日志无错、仍能正常服务其他调用方时，问题在调用方配置：对比调用方线上 env 与 last-applied-configuration、新旧 ReplicaSet 模板，结合 ScalingReplicaSet 事件时间确认是刚改出来的，然后修调用方配置。Pod 刚启动时短暂 refused、随后自愈的不算根因。
  - [E3]（BH01、BH02、BH03）现象：整站变慢，无错误日志。判断：(1) 找瓶颈：把各 handler 耗时与它是否/几次调用某下游列表比较，只有调用它的 handler 变慢、不调它的仍很快，瓶颈就在该下游；再挑一个慢请求逐跳对时间戳。(2) 定位延迟在哪一段：比较调用方发起调用的时间、被调方打出“收到请求”日志的时间、被调方返回后调用方完成的时间。耗时集中在到达被调方之前、而被调方处理和其出向调用都很快，支持该 Pod 入方向网络延迟；耗时在被调方处理内部、CPU limit 低、随负载波动，支持 CFS 节流。耗时随网络往返次数呈固定台阶增加，也支持网络延迟。(3) 对照变慢开始时间与 Pod 创建/Ready 时间。网络延迟先重建 Pod，节流先提高 limit；修复后仍慢就换假设或查节点/注入源。例：被调方收到请求比调用方发起晚一个稳定间隔，而处理只要几毫秒。
  - [E4]（BH03）现象：有多个嫌疑对象，或不确定最近改了什么。判断：对命名空间内所有 Deployment 和 Service，把线上 spec（env、镜像、selector、port/targetPort、resources）与各自的 last-applied-configuration 逐项比对，并查各 Deployment 的 ReplicaSet revision 和创建时间。差异唯一且时间与故障开始吻合时，优先作为配置类根因并验证。注意网络延迟注入、节点问题等不会改 spec，比对干净的服务仍出现异常时，应转向配置之外的解释（按 E3 判断网络还是资源），不能据此排除它。
  - [E5]（BH04）现象：整站变慢、无错误日志，按 E3 找到一个慢下游，但它解释不了全部耗时。判断：(1) 对每个 handler 数出它对各下游的调用次数，用调用方日志里相邻两次调用的时间戳间隔估算每个下游单次调用耗时。(2) 用“各下游单次增量×调用次数”去拼每个 handler 的总耗时（含下游的内部再调用），拼不齐说明还有被漏掉的慢下游，继续逐跳对时间戳。(3) 同一时间窗内找出往返仍正常的下游作对照：只有部分 Pod 变慢、其余正常，支持针对这些 Pod 的注入/入方向网络问题，排除节点 CPU 和全局网络。根因要列出所有被抬高的下游，修复一并覆盖。例：多个下游各被抬高相同的一段，页面耗时约等于增量乘以调用次数之和。
  - [E6]（BH04）现象：修复需要重建 Pod（尤其是用 emptyDir 等非持久存储的有状态服务，如缓存/数据库），或重建后要复核效果。判断：(1) 重建前先评估副作用：会丢失哪些数据，哪些接口会因数据变少而“假性变快”或行为变化，复核时以不受这些数据影响的接口为准。(2) 有依赖关系的先重建被依赖方，再重建调用方，确保重新建连。(3) 重建后与故障前的健康基线比较：恢复则说明问题附着在 Pod 运行期状态上；完全不变说明是按 label 持续施加的外部注入（chaos 实验、sidecar、节点 tc 规则）或节点问题，不要重复重启，转去查注入源或节点。

## 结论：`currencyservice` 的请求入口被添加了约 200 ms 的单向网络延迟

### 定位过程与证据

**1. 页面延迟分布（frontend 自身日志，`took_ms`，最近约 2 分钟，345 条 `request complete`）**

| 路径 | 延迟 |
|---|---|
| `GET /` (home) | 1981–2144 ms（稳定 ~2080）|
| `GET /product/*` | 377–448 ms（稳定 ~415）|
| `GET /cart` | 4 个明显分层：~700 / ~880–950 / ~1090–1190 / ~1310–1330（每个购物车条目 +~200 ms）|
| `POST /cart`（加购）| **1–2 ms** |
| `POST /setCurrency` | 0–2 ms |
| `POST /cart/checkout` | 1169–1677 ms |

`POST /cart` 只花 1 ms，这说明 `productcatalogservice`、`cartservice`、`redis-cart` 都很快，请求路径本身没有异常。

**2. 时间戳逐条对齐，发现延迟在 `currencyservice` 的入口**

把 frontend 每个页面的起始时刻（= 完成时刻 − `took_ms`）与 `currencyservice-6df4cccbb9-ltrd7` 的 `Getting supported currencies...`（该日志在 handler **入口**打印）逐条比对，06:13:00–06:13:12 窗口内 **15 个页面请求 / 15 条 GSC 日志，一一对应**，偏移分别为：

```
199, 210, 194, 188, 191, 192, 212, 210, 211, 207, 206, 209, 200, 207, 204 ms
```

即：请求发出后 **约 200 ms 才到达 currencyservice 进程**；而 handler 执行完后返回很快（例：`/product/OLJCESPC7Z` 起始 06:13:05.015 → GSC 05.225 → 转换完成日志 05.434 → frontend 完成 05.442，**响应仅 +8 ms**）。同一毫秒内多次出现 2 条转换完成日志（84.876/84.876、89.997/89.997、91.055/91.056），说明业务处理本身是瞬时的。

**3. 延迟只伴随 currency 的 RPC 数量**

- home = product + 9 次额外转换：`2080 − 415 ≈ 1665 ms ÷ 9 ≈ 185 ms/次`
- cart 每个条目 +~200 ms（每次 `Convert`）
- 服务端日志速率 ~6 次转换/s，负载很低，排除 CPU 排队/限流（且容器 CPU limit 200m/request 100m 为官方 demo 标准值）

**4. 排除的其他可能**
- 镜像全部为标准 `us-central1-docker.pkg.dev/google-samples/microservices-demo/*:v0.10.3`，无自定义镜像、无 sidecar/initContainer、无 chaos 容器。
- 所有 Deployment 的 env、资源、Service `targetPort` 与 Endpoints（`currencyservice → 10.244.0.87:7000`，唯一后端）均正确。
- adservice 正常：`received ad request` 日志与 frontend 请求**完成时刻**相差 ≤2 ms（它是 handler 最后一个调用，且很快）。
- 12 个 Pod 全部 Running、READY、0 重启；0 个 500；无相关 Event。
- **不是 frontend 单侧问题**：`checkoutservice`（另一个 Pod，10.244.0.86）也慢——`[PlaceOrder]` 06:12:44.830 → `payment went through` 06:12:45.959，前置阶段 1129 ms，与“每个条目 1 次货币转换 ×200 ms”吻合。两个不同客户端都慢，共同点只有 `currencyservice` 这一个 Pod。

### 影响面

- **受影响**：`currencyservice`（自身延迟证据：入口日志相对调用方请求起始恒定 +188~212 ms）。其调用方 `frontend`（`took_ms` 2.0–2.1 s / 377–448 ms）与 `checkoutservice`（`PlaceOrder → payment` 1129 ms）因此变慢；用户侧 75.4% 请求 >180 ms、中位 420 ms、p90 1983 ms，且 0 报错，与“只加延迟不加错误”完全一致。
- **检查后为正常**：`productcatalogservice`、`cartservice`、`redis-cart`（`POST /cart` 1 ms）、`adservice`（~2 ms）、所有 Pod 状态。
- **未能精确定量**：`recommendationservice`（日志正常持续收到请求，但无完成时刻日志；home−product 差值已被货币转换完全解释）。

### 修复

延迟加在 `currencyservice` Pod 的**入向**网络路径上（请求晚到、响应及时），而 Deployment 的 env/资源/Service/Endpoints/镜像都正常，所以这是 Pod 网络命名空间/veth 级别的改动。重建该 Pod（新 netns、新 veth、很可能新 IP）应使这类规则失效，而无需改动任何配置——这也在允许的操作范围内。
