【boutique-triage-overview】Online Boutique（命名空间 boutique）排查总则：服务调用关系、按症状选入口 SOP、跨服务跳转原则、怎么判断故障源头。排查这个命名空间的任何问题时先读。
  - [E1]（BH01、BH06）现象：用户反馈变慢和/或请求失败，或只说“变慢、没报错”。判断：(1) 不要默认只有一个根因，也不要因用户侧 5xx 为 0 就认为没有错误：扫调用方日志里被降级吞掉的错误（可选功能调用失败、页面照常返回），它们常是同时存在的第二个故障。(2) 按接口/handler 把请求分成“报错的”和“慢但成功的”两组，各自顺调用链查：报错组看错误内容和目标地址，慢组看耗时分布。(3) 判断某个错误是否贡献延迟：看它是毫秒级快速失败还是超时失败，并检查慢 handler 的耗时是否已被其他下游“调用次数×单次增量”完全解释；已解释完则该错误只是独立故障，单独给出根因和修复。只有慢和错都卡在同一下游、同一错误上才合并。例：页面变慢来自一个下游的固定延迟，同时另一个下游缩容导致快速失败的报错日志。
  - [E2]（BH01、BH02、BH03、BH06、BH07）现象：调用方日志报 dial tcp <ClusterIP>:<端口> i/o timeout、connection refused，或 gRPC 错误链显示某下游步骤失败。判断：(0) 先按错误类型分流：对 ClusterIP 报 connection refused，优先怀疑 Service 无 Endpoints；报 i/o timeout，优先核对端口是否为 Service 实际暴露的端口。(1) 从错误确定目标下游和端口，反查 Endpoints。为空时看 Deployment 的 replicas 和 Ready Pod 数：replicas 为 0，查 ScalingReplicaSet/SuccessfulDelete 事件确认被缩容，恢复副本数；有 Ready Pod 仍为空，逐字比对 selector 与 Pod labels，修 selector。(2) Endpoints 正常时，把调用方 *_ADDR 端口与 Service port/targetPort、容器监听端口逐一比较。(3) 被调方无错、日志显示仍在服务其他调用方时，问题在调用方配置：对比线上 env 与 last-applied-configuration、新旧 ReplicaSet 模板及创建时间，修调用方配置，不动被调方。Pod 刚启动时短暂 refused 随后自愈的不算根因。例：调用方地址端口被改成 Service 没有的端口，表现为 i/o timeout，而另一个被缩到 0 的服务表现为 refused。
  - [E3]（BH01、BH02、BH03、BH05、BH08）现象：整站变慢，无错误日志。判断：(1) 找瓶颈：把各 handler 耗时与它调用了哪些下游、各几次比较。以最快的 handler 作对照，它调用到的下游都可排除；耗时随某下游调用次数成台阶增加，瓶颈就在该下游。(2) 定位延迟在哪一段：比较调用方发起时间（完成时刻减耗时）、被调方入口日志时间和调用方完成时间。耗时集中在到达被调方之前、处理很快，支持入方向网络延迟；耗时在处理内部、CPU limit 低、随负载波动，支持 CFS 节流。(3) 区分注入和节流：变慢是某一刻的台阶突变、每次调用都不低于同一下限、负载低时同样慢，支持固定延迟注入；节流应随负载有快有慢。没有节点指标时，同节点其他服务仍快可排除节点级问题。(4) 对照变慢开始时间与 Pod 创建/Ready 时间。网络延迟先重建 Pod，节流先提高 limit，修复后仍慢按 E6 转查注入源或节点。例：每次缓存往返都被抬高同一段时间，其他调用都很快。
  - [E4]（BH03、BH07、BH08）现象：有多个嫌疑对象，或不确定最近改了什么。判断：(1) 对命名空间内所有 Deployment 和 Service，把线上 spec（env、镜像、selector、port/targetPort、replicas、resources）与 last-applied-configuration 逐项比对，并查各 Deployment 的 ReplicaSet revision、创建时间和缩扩容事件。(2) 找到一处变更后，取它的事件时间，在全命名空间事件里查同一时刻前后的其他变更：同一时刻发生的往往是同一批改动，每一处都要单独判断影响并修复，不要找到一个就停。(3) 用时间线检验每个差异：与故障开始时间吻合时，优先作为配置类根因去验证；变更后新 Pod Ready 了还正常服务过一段时间、故障之后才突然出现，就排除它是本次根因，作为独立的配置漂移另行报告，继续找真正的根因。网络延迟注入、节点问题不会改 spec，比对干净的服务仍异常时，按 E3 转查网络或资源。例：某服务被手工加了 env 并滚动更新，但新 Pod 先正常服务了一段时间，之后才变慢。
  - [E5]（BH04、BH08）现象：整站变慢、无错误日志，按 E3 找到慢下游但它解释不了全部耗时，或慢下游本身还调用缓存/数据库。判断：(1) 对每个 handler 数出每一跳的调用次数，包括下游的内部再调用（如对缓存/数据库的命令条数），用调用方日志里相邻调用的时间戳间隔估算单次耗时。(2) 用“单次增量×次数”拼每个 handler 的总耗时，拼不齐说明漏了慢下游，继续逐跳对时间戳。用比例定位延迟附着点：耗时与某一跳的次数严格成正比，延迟就在该跳；若附着在中间服务自身的网络上，它的入向调用也会被抬高，比例会偏离；每次调用都不低于同一下限、没有快的，说明是固定延迟而非丢包。(3) 找同一时间窗内往返仍正常的下游作对照：只有部分 Pod 变慢，支持针对这些 Pod 的注入或入方向网络问题，排除节点和全局网络。根因要列出所有被抬高的跳，修复一并覆盖。例：一次缓存操作的接口与两次操作的接口耗时正好差一倍。
  - [E6]（BH04）现象：修复需要重建 Pod（尤其是用 emptyDir 等非持久存储的有状态服务，如缓存/数据库），或重建后要复核效果。判断：(1) 重建前先评估副作用：会丢失哪些数据，哪些接口会因数据变少而“假性变快”或行为变化，复核时以不受这些数据影响的接口为准。(2) 有依赖关系的先重建被依赖方，再重建调用方，确保重新建连。(3) 重建后与故障前的健康基线比较：恢复则说明问题附着在 Pod 运行期状态上；完全不变说明是按 label 持续施加的外部注入（chaos 实验、sidecar、节点 tc 规则）或节点问题，不要重复重启，转去查注入源或节点。
  - [E7]（BH05）现象：某个调用方变慢，不确定是调用方自身/其所在节点的问题，还是某个下游的问题。判断：(1) 找出另一个独立的调用方（不同 Pod、最好不同 handler 路径），看它调用同一批下游的阶段是否也变慢；用它日志里相邻步骤的时间戳间隔估算各段耗时。(2) 两个调用方都慢，取它们共同调用的下游的交集，交集里再用 E3 的对照法排除仍快的下游，剩下的就是嫌疑；只有一个调用方慢、另一个正常，转查慢调用方自身（资源、节点、出方向网络）。(3) 对嫌疑之外的下游做反证：挑一个在 handler 末尾才被调用的下游，其入口日志应与调用方完成时刻几乎重合，重合即说明该下游及调用方出向网络正常。例：前端页面和下单流程都慢，共同点只有一个被两者调用的下游 Pod。
  - [E8]（BH07）现象：某个多步骤业务流程（如下单）全部失败，其他页面正常、请求快速返回而非超时变慢。判断：(1) 取调用方返回的完整错误链，从外到内读到最内层的那一跳，确定流程卡在哪个步骤、连的是哪个下游地址。(2) 用流程的固定调用顺序反证：失败步骤之后的下游应几乎没有来自该流程的调用日志，之前的下游应有正常调用；若与之相符，后面那些服务的“安静”是流程提前中止的结果，不要当成它们的故障。(3) 失败率是该流程的 100%，且只这一流程受影响，优先查流程编排方（调用方）到该步骤下游的连接配置，按 E2 处理。例：下单在运费报价一步就失败，支付服务因此几乎没有调用日志。

## 结论：`shippingservice` 的入站网络被加了约 300ms 延迟（请求方向），响应方向正常

### 关键证据

**1. 前端只有购物车类页面慢（frontend 日志，07:39:46–07:39:56，1450 条中看 24 条完整请求）**

| 路径 | took_ms | 状态 |
|---|---|---|
| `GET /cart` | 283 / 286 / 307 / 327 / 335 / 338 | 200 |
| `POST /cart`（302 跳 /cart） | 1–2 | 302 |
| `POST /cart/checkout` | 629 | 200 |
| `GET /product/*` | 8–13 | 200 |
| `GET /` | 37–77 | 200 |

没有任何 4xx/5xx。`/cart` 页面比正常页慢约 300ms，且与购物车条目数无关 → 是**一次调用**被延迟，不是逐条处理。

**2. 把三个服务的日志按时间戳对齐后，延迟在“请求到达 shippingservice 之前”**

以一条 `GET /cart`（req `5e1b703b`）为例：
- 48.0595 前端开始；48.0629 前端 `view user cart`
- 48.0648 recommendationservice 收到 `ListRecommendations`
- **48.3963 shippingservice 才收到 `[GetQuote] received request`（晚了 331ms）**
- 48.3964 `[GetQuote] completed`（**服务端处理 < 0.1ms**）
- 48.3964 前端开始逐项换算（currency 48.396/48.397），48.3984 完成（**响应回路仅 ~2ms**）

同样的对齐在 51.4046、54.4441、55.3296、55.9035 等多次重复：gap = 278–331ms，都是“请求晚到、响应秒回”。

**3. 最硬的一条证据：checkoutservice 里 Charge 与 ShipOrder 之间只隔着一次 shipping RPC**
- 49.4363 `[PlaceOrder]`（checkoutservice）
- 49.7457 shippingservice 收到 `GetQuote`；49.7490 paymentservice 收到 Charge；49.7499 checkoutservice `payment went through`
- **50.0570 shippingservice 才收到 `ShipOrder`（Charge 响应返回后又过了 307ms，中间只有 shipping 调用）**
- 50.0571 `[ShipOrder] completed`（服务端 <0.1ms）；50.0587 email 失败（瞬时 connection refused）；50.0653 前端完成 629ms

这条链上不存在第三种调用，所以 ~300ms 只能花在“发往 shippingservice 的请求到达服务端之前”。

**4. 排除 Pod 级 CPU/探针原因**：shippingservice 限额与同命名空间其他服务一致（limits 200m/128Mi，requests 100m/64Mi），handler 进入后 <0.1ms 就跑完，说明 CPU 充足；探针 1s 超时 > 300ms，所以 Pod 一直 Ready（无 Unhealthy 事件）——这正好解释“Pod 看起来都正常”。

**5. 顺带发现的第二个真实缺陷（不是本次延迟的原因）：`emailservice` 的 Service selector 错了**
```
emailservice  Service selector: app=emailservice-v2
emailservice  Deployment/Pod label: app=emailservice
Endpoints emailservice: subsets = null   （10.96.39.9:5000 无后端）
```
checkoutservice 从 07:37:53 起持续报（此前 07:37:33 之前是成功的）：
`failed to send order confirmation ... dial tcp 10.96.39.9:5000: connect: connection refused`（severity=warning）
订单仍然成功（email 只是 warn），所以用户侧没有 500、下单 5 次成功 0 失败——但它确实在丢订单确认邮件。emailservice Pod 在 07:37:44 被重建过（Killing old pod → 新 Pod），与改 selector 的时间吻合。

**已检查并确认正常的组件**：cartservice（checkout 里 `EmptyCart` 往返 ~1.6ms）、redis-cart、currencyservice（单次换算 <1ms）、productcatalogservice、recommendationservice（商品页 rec 收到→前端完成 5.8ms）、paymentservice（Charge 同毫秒处理）、adservice、frontend 自身。节点级指标我读不到（本诊断 SA 无权 `list nodes`/全集群 pods），所以无法直接看宿主机上的 tc/qdisc。

### 修复思路
延迟只在“进入 shippingservice 的网络路径”上，而 Pod 重建会得到新的 netns/veth/IP，因此重建 `shippingservice` 的 Pod 是当前可申请操作里唯一能清掉这条入站延迟的手段；`emailservice` 的 selector 直接改回 `app=emailservice`。

如果再造 Pod 后 `/cart` 仍然 ~300ms，那说明延迟规则被加在宿主机侧（节点上的 tc/netem），需要运维登录 `tiktok-k8s-lab-control-plane` 清理对应 veth 上的 qdisc，这不是我这份只读权限能做的。
