【boutique-triage-overview】Online Boutique（命名空间 boutique）排查总则：服务调用关系、按症状选入口 SOP、跨服务跳转原则、怎么判断故障源头。排查这个命名空间的任何问题时先读。
  - [E1]（BH01）现象：用户同时反馈变慢和请求失败（例如下单失败）。判断：不要默认是同一个根因。先按接口/handler 把请求分成“报错的”和“慢但成功的”两组，各自顺着调用链查。报错组看调用方错误日志里的具体错误和目标地址；慢组看各 handler 的耗时分布。两组指向不同下游时，分别给出根因和修复。只有当慢请求和失败请求都卡在同一个下游、同一种错误上时，才合并成一个根因。例：下单失败来自一个服务的配置错误，整站变慢来自另一个服务的资源瓶颈。
  - [E2]（BH01）现象：调用方日志报 dial tcp <ClusterIP>:<端口> i/o timeout 或 connection refused。判断：(1) 用 IP 反查是哪个 Service，把日志里的端口和该 Service 的 port/targetPort、容器实际监听端口逐一比较；ClusterIP 上没有对应端口规则时，通常表现为 i/o timeout，而不是 refused。(2) 查调用方 Deployment 的 ReplicaSet 历史，对比新旧 revision 的环境变量（*_ADDR 等）和镜像，再结合 ScalingReplicaSet 事件的时间，确认是不是刚改出来的。(3) 被调方没有错误日志、Endpoints 正常时，修调用方配置，不要改 Service。另外，Pod 刚启动时短暂的 refused 或 readiness 失败、之后自己恢复的，属于启动期现象，不算根因。
  - [E3]（BH01）现象：整站变慢，但没有错误日志。判断：把调用方各 handler 的耗时，和该 handler 调用某个下游的次数列成表（例如首页按商品数、购物车按件数调用）。如果耗时随调用次数线性增加，而不调用该下游的 handler 仍然很快，瓶颈就在这个下游。再区分是资源节流还是网络延迟：查该下游日志里低负载时段是否有很快完成的批量处理，并查它的 CPU limit 和请求速率；本身处理很快、limit 又很低、负载上来才变慢，支持 CFS 节流/CPU 争抢。拿不到节点或 Pod 的 CPU 指标时，要说明不能排除节点级争抢；如果提高配额后仍然慢，再去查节点。例：货币转换服务每次调用被拖慢，首页的多次顺序调用把它放大成秒级页面耗时。

**2) 全站变慢 — 瓶颈定位在 cartservice 这一个跳上的固定延迟**

按单个请求逐跳对时（05:49:17–05:49:19 的 `/product/607e6a80…`，前端耗时 411 ms）：
- `getProduct`：handler 起 17.706 → currencyservice “Getting supported currencies” 17.707，**约 1 ms**（productcatalog 正常）
- 17.707 → convertCurrency 18.111：**中间只夹一个 `getCart`，耗掉约 404 ms**
- 之后 recommendations 18.113、adservice 18.116，都是 **2–3 ms** 级

耗时是整齐的 200 ms 台阶，而不是波动：
- `GetCart`（cartservice 内 1 次 redis 往返 + 1 次前端↔cart 往返）：375–445 ms
- `AddItem`（2 次 redis 往返）：567–639 ms，稳定比 GetCart 多约 195 ms
- 所有页面（home/product/cart）都只有一次 getCart，因此统统落在约 400 ms；checkout 也是先调 cartservice，所以失败请求也要 378–441 ms
- 同 pod 的 `/_healthz` 全程 0 ms，productcatalog/currency/ads/recommendation 全是毫秒级 → 排除前端进程（CPU 饿死）与整节点负载

拟合为“cartservice Pod 网络单向约 100 ms 延迟”：200 ms（前端↔cart 一次往返）+ 200 ms/次 redis 往返 → GetCart 400 ms、AddItem 600 ms，与观测完全吻合。备选解释“cartservice CPU 被 throttle”无法完全排除（无 cgroup throttling 指标），但 throttle 不会给出这样固定的 200 ms 台阶，故列为次要假设。
