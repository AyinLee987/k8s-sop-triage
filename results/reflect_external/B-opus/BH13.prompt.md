【boutique-triage-overview】Online Boutique（命名空间 boutique）排查总则：服务调用关系、按症状选入口 SOP、跨服务跳转原则、怎么判断故障源头。排查这个命名空间的任何问题时先读。
  - [E1]（BH01、BH06）现象：用户反馈变慢和/或请求失败，或只说“变慢、没报错”。判断：(1) 不要默认只有一个根因，也不要因用户侧 5xx 为 0 就认为没有错误：扫调用方日志里被降级吞掉的错误（可选功能调用失败、页面照常返回），它们常是同时存在的第二个故障。(2) 按接口/handler 把请求分成“报错的”和“慢但成功的”两组，各自顺调用链查：报错组看错误内容和目标地址，慢组看耗时分布。(3) 判断某个错误是否贡献延迟：看它是毫秒级快速失败还是超时失败，并检查慢 handler 的耗时是否已被其他下游“调用次数×单次增量”完全解释；已解释完则该错误只是独立故障，单独给出根因和修复。只有慢和错都卡在同一下游、同一错误上才合并。例：页面变慢来自一个下游的固定延迟，同时另一个下游缩容导致快速失败的报错日志。
  - [E2]（BH01、BH02、BH03、BH06、BH07、BH10）（BH01-03、BH06、BH07、BH10）现象：调用方日志报 dial tcp <ClusterIP>:<端口> i/o timeout、connection refused，或 gRPC 错误链显示某下游步骤失败。判断：(1) 从错误定目标下游和端口，反查 Endpoints。为空：replicas 为 0 查缩容事件并恢复副本；有 Ready Pod 仍为空，逐字比对 selector 与 Pod labels，修 selector。(2) Endpoints 有地址仍 refused 或 timeout：沿端口链逐一比较——调用方 *_ADDR 端口、Service port、targetPort（即 Endpoints 里的端口）、containerPort 与被调方启动日志里实际监听端口；refused 多为 targetPort 与监听端口不符，timeout 多为调用方端口不是 Service 暴露的端口。(3) 被调方无错且仍在服务其他调用方，问题在调用方配置：对比线上 env 与 last-applied、新旧 ReplicaSet 模板，修调用方。Pod 刚启动短暂 refused 后自愈的不算根因。例：Service targetPort 被改成容器没监听的端口，Endpoints 非空但所有调用快速 refused。
  - [E3]（BH01、BH02、BH03、BH05、BH08）现象：整站变慢，无错误日志。判断：(1) 找瓶颈：把各 handler 耗时与它调用了哪些下游、各几次比较。以最快的 handler 作对照，它调用到的下游都可排除；耗时随某下游调用次数成台阶增加，瓶颈就在该下游。(2) 定位延迟在哪一段：比较调用方发起时间（完成时刻减耗时）、被调方入口日志时间和调用方完成时间。耗时集中在到达被调方之前、处理很快，支持入方向网络延迟；耗时在处理内部、CPU limit 低、随负载波动，支持 CFS 节流。(3) 区分注入和节流：变慢是某一刻的台阶突变、每次调用都不低于同一下限、负载低时同样慢，支持固定延迟注入；节流应随负载有快有慢。没有节点指标时，同节点其他服务仍快可排除节点级问题。(4) 对照变慢开始时间与 Pod 创建/Ready 时间。网络延迟先重建 Pod，节流先提高 limit，修复后仍慢按 E6 转查注入源或节点。例：每次缓存往返都被抬高同一段时间，其他调用都很快。
  - [E4]（BH03、BH07、BH08）现象：有多个嫌疑对象，或不确定最近改了什么。判断：(1) 对命名空间内所有 Deployment 和 Service，把线上 spec（env、镜像、selector、port/targetPort、replicas、resources）与 last-applied-configuration 逐项比对，并查各 Deployment 的 ReplicaSet revision、创建时间和缩扩容事件。(2) 找到一处变更后，取它的事件时间，在全命名空间事件里查同一时刻前后的其他变更：同一时刻发生的往往是同一批改动，每一处都要单独判断影响并修复，不要找到一个就停。(3) 用时间线检验每个差异：与故障开始时间吻合时，优先作为配置类根因去验证；变更后新 Pod Ready 了还正常服务过一段时间、故障之后才突然出现，就排除它是本次根因，作为独立的配置漂移另行报告，继续找真正的根因。网络延迟注入、节点问题不会改 spec，比对干净的服务仍异常时，按 E3 转查网络或资源。例：某服务被手工加了 env 并滚动更新，但新 Pod 先正常服务了一段时间，之后才变慢。
  - [E5]（BH04、BH08）现象：整站变慢、无错误日志，按 E3 找到慢下游但它解释不了全部耗时，或慢下游本身还调用缓存/数据库。判断：(1) 对每个 handler 数出每一跳的调用次数，包括下游的内部再调用（如对缓存/数据库的命令条数），用调用方日志里相邻调用的时间戳间隔估算单次耗时。(2) 用“单次增量×次数”拼每个 handler 的总耗时，拼不齐说明漏了慢下游，继续逐跳对时间戳。用比例定位延迟附着点：耗时与某一跳的次数严格成正比，延迟就在该跳；若附着在中间服务自身的网络上，它的入向调用也会被抬高，比例会偏离；每次调用都不低于同一下限、没有快的，说明是固定延迟而非丢包。(3) 找同一时间窗内往返仍正常的下游作对照：只有部分 Pod 变慢，支持针对这些 Pod 的注入或入方向网络问题，排除节点和全局网络。根因要列出所有被抬高的跳，修复一并覆盖。例：一次缓存操作的接口与两次操作的接口耗时正好差一倍。
  - [E6]（BH04）现象：修复需要重建 Pod（尤其是用 emptyDir 等非持久存储的有状态服务，如缓存/数据库），或重建后要复核效果。判断：(1) 重建前先评估副作用：会丢失哪些数据，哪些接口会因数据变少而“假性变快”或行为变化，复核时以不受这些数据影响的接口为准。(2) 有依赖关系的先重建被依赖方，再重建调用方，确保重新建连。(3) 重建后与故障前的健康基线比较：恢复则说明问题附着在 Pod 运行期状态上；完全不变说明是按 label 持续施加的外部注入（chaos 实验、sidecar、节点 tc 规则）或节点问题，不要重复重启，转去查注入源或节点。
  - [E7]（BH05）现象：某个调用方变慢，不确定是调用方自身/其所在节点的问题，还是某个下游的问题。判断：(1) 找出另一个独立的调用方（不同 Pod、最好不同 handler 路径），看它调用同一批下游的阶段是否也变慢；用它日志里相邻步骤的时间戳间隔估算各段耗时。(2) 两个调用方都慢，取它们共同调用的下游的交集，交集里再用 E3 的对照法排除仍快的下游，剩下的就是嫌疑；只有一个调用方慢、另一个正常，转查慢调用方自身（资源、节点、出方向网络）。(3) 对嫌疑之外的下游做反证：挑一个在 handler 末尾才被调用的下游，其入口日志应与调用方完成时刻几乎重合，重合即说明该下游及调用方出向网络正常。例：前端页面和下单流程都慢，共同点只有一个被两者调用的下游 Pod。
  - [E8]（BH07）现象：某个多步骤业务流程（如下单）全部失败，其他页面正常、请求快速返回而非超时变慢。判断：(1) 取调用方返回的完整错误链，从外到内读到最内层的那一跳，确定流程卡在哪个步骤、连的是哪个下游地址。(2) 用流程的固定调用顺序反证：失败步骤之后的下游应几乎没有来自该流程的调用日志，之前的下游应有正常调用；若与之相符，后面那些服务的“安静”是流程提前中止的结果，不要当成它们的故障。(3) 失败率是该流程的 100%，且只这一流程受影响，优先查流程编排方（调用方）到该步骤下游的连接配置，按 E2 处理。例：下单在运费报价一步就失败，支付服务因此几乎没有调用日志。
  - [E9]（BH09）现象：变慢、无报错，Pod 全部 Running/Ready，看起来都正常。判断：(1) 不要因为 Pod Ready、没有 Unhealthy 事件就排除这个服务：探针超时大于注入的延迟时探针照样通过，要拿探针 timeoutSeconds 和观察到的延迟比一比。(2) 在调用方日志里找两条相邻记录之间只隔一次下游调用的片段（例如编排方在上一步返回后只调了一个下游，再记下一步），这段间隔就全是这一跳的往返时间，可以排除其他下游。(3) 把这一跳拆成三段：调用方发起→被调方入口日志（请求方向）、被调方入口→完成（处理）、被调方完成→调用方下一条日志（响应方向）。只有请求方向长，支持被调方 Pod 入向网络延迟；处理段长，转查 CPU/节流。(4) 页面耗时和条目数无关、只多出一个固定量，说明是某一次调用被抬高，不是逐条处理变慢。例：下单链路里扣款返回后到发货服务收到请求之间隔了一段固定延迟，发货服务处理和响应都是毫秒内完成。
  - [E10]（BH11、BH12）现象：时快时慢、无报错，中位数正常只有尾部慢，Pod 全部 Ready。判断：(1) 看慢请求的耗时形状：紧聚在“基线+同一固定量”及其整数倍上，支持部分调用被加了固定延迟（丢包重传或按比例注入）。CFS 节流的停顿等于当前周期剩余的时间，增量应在 0 到一个周期之间连续分布，单次停顿也不超过一个周期，不要因为数值像周期的整数倍就判节流。秒级的探针连接超时符合 SYN 丢包重传，不符合节流。(2) 按端点统计慢请求占比，对照各端点调用了哪些下游、各几次，用不调后端的端点做对照。把每个下游的单次命中概率都估算一遍，不能只和一个下游比：各下游相近，问题在公共层；集中在某一个下游，查它的 Pod。(3) 节流会冻结整个进程，同一时刻在途的多个调用方请求应一起变慢；丢包和注入是逐次独立发生的，慢请求的时刻互不重合。(4) 按 E9 用被调方入口日志拆段，延迟落在到达被调方之前，支持入向丢包或延迟。(5) 没有节流指标时，不要因为 limit 低就抬 limit，先做上面这些能区分假设的检查。例：慢请求都比正常多出同一段延迟，调用次数多的页面慢请求占比更高。

### 观察到的证据

**1. 前端自身没有停顿（排除 frontend CPU 限流/调度）**

1. **CPU 限流**：Redis 8 镜像带 4 个模块 + 16 个工作线程，125m quota 下突发即被 CFS 限流，产生 100–200ms 级停顿；
2. **瞬时不响应/网络丢包**：丢包更契合「dial tcp i/o timeout >1s」（SYN 重传 1s）与「+200ms RTO」这一对现象。
两者都落在 redis-cart 上，且都能被「提高 CPU 上限 + 重建 Pod（新 sandbox，清掉阻塞/网络规则）」覆盖。
