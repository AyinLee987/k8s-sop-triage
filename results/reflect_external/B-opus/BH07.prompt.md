【boutique-triage-overview】Online Boutique（命名空间 boutique）排查总则：服务调用关系、按症状选入口 SOP、跨服务跳转原则、怎么判断故障源头。排查这个命名空间的任何问题时先读。
  - [E1]（BH01、BH06）现象：用户反馈变慢和/或请求失败，或只说“变慢、没报错”。判断：(1) 不要默认只有一个根因，也不要因用户侧 5xx 为 0 就认为没有错误：扫调用方日志里被降级吞掉的错误（可选功能调用失败、页面照常返回），它们常是同时存在的第二个故障。(2) 按接口/handler 把请求分成“报错的”和“慢但成功的”两组，各自顺调用链查：报错组看错误内容和目标地址，慢组看耗时分布。(3) 判断某个错误是否贡献延迟：看它是毫秒级快速失败还是超时失败，并检查慢 handler 的耗时是否已被其他下游“调用次数×单次增量”完全解释；已解释完则该错误只是独立故障，单独给出根因和修复。只有慢和错都卡在同一下游、同一错误上才合并。例：页面变慢来自一个下游的固定延迟，同时另一个下游缩容导致快速失败的报错日志。
  - [E2]（BH01、BH02、BH03、BH06）现象：调用方日志报 dial tcp <ClusterIP>:<端口> i/o timeout、connection refused，或 gRPC 错误链显示某下游步骤失败，首次失败秒级、之后毫秒级快速失败。判断：(1) 从错误确定目标下游和端口，反查 Service 的 Endpoints。为空时先看对应 Deployment 的 replicas 和 Ready Pod 数：replicas 为 0 或无 Pod，查 ScalingReplicaSet/SuccessfulDelete/Killing 事件确认是被缩容或删除，恢复副本数；有 Ready Pod 仍为空，再逐字比对 selector 与 Pod labels（键名、取值、后缀），修 selector，不动 Pod 和调用方。(2) Endpoints 正常时，把调用方 *_ADDR 端口与 Service port/targetPort、容器监听端口逐一比较。(3) 被调方无错且能服务其他调用方时，问题在调用方配置：对比线上 env 与 last-applied-configuration、新旧 ReplicaSet 模板及事件时间，修调用方配置。Pod 刚启动时短暂 refused 随后自愈的不算根因。
  - [E3]（BH01、BH02、BH03、BH05）现象：整站变慢，无错误日志。判断：(1) 找瓶颈：把各 handler 耗时与它调用了哪些下游、各几次比较。先找最快的 handler 作对照：它调用到的下游都可排除；只有调用某下游的 handler 变慢、耗时随该下游调用次数（如列表条目数）成台阶增加，瓶颈就在该下游。(2) 定位延迟在哪一段：比较调用方发起调用的时间（完成时刻减耗时）、被调方 handler 入口日志时间、被调方返回后调用方完成的时间，注意区分被调方日志是入口打印还是出口打印。耗时集中在到达被调方之前、被调方处理和出向调用都很快，支持该 Pod 入方向网络延迟；耗时在处理内部、CPU limit 低、随负载波动，支持 CFS 节流；负载很低时仍慢可排除节流。(3) 对照变慢开始时间与 Pod 创建/Ready 时间。网络延迟先重建 Pod，节流先提高 limit；修复后仍慢按 E6 转查注入源或节点。例：被调方收到请求比调用方发起晚一个稳定间隔，而处理只要几毫秒。
  - [E4]（BH03）现象：有多个嫌疑对象，或不确定最近改了什么。判断：对命名空间内所有 Deployment 和 Service，把线上 spec（env、镜像、selector、port/targetPort、resources）与各自的 last-applied-configuration 逐项比对，并查各 Deployment 的 ReplicaSet revision 和创建时间。差异唯一且时间与故障开始吻合时，优先作为配置类根因并验证。注意网络延迟注入、节点问题等不会改 spec，比对干净的服务仍出现异常时，应转向配置之外的解释（按 E3 判断网络还是资源），不能据此排除它。
  - [E5]（BH04）现象：整站变慢、无错误日志，按 E3 找到一个慢下游，但它解释不了全部耗时。判断：(1) 对每个 handler 数出它对各下游的调用次数，用调用方日志里相邻两次调用的时间戳间隔估算每个下游单次调用耗时。(2) 用“各下游单次增量×调用次数”去拼每个 handler 的总耗时（含下游的内部再调用），拼不齐说明还有被漏掉的慢下游，继续逐跳对时间戳。(3) 同一时间窗内找出往返仍正常的下游作对照：只有部分 Pod 变慢、其余正常，支持针对这些 Pod 的注入/入方向网络问题，排除节点 CPU 和全局网络。根因要列出所有被抬高的下游，修复一并覆盖。例：多个下游各被抬高相同的一段，页面耗时约等于增量乘以调用次数之和。
  - [E6]（BH04）现象：修复需要重建 Pod（尤其是用 emptyDir 等非持久存储的有状态服务，如缓存/数据库），或重建后要复核效果。判断：(1) 重建前先评估副作用：会丢失哪些数据，哪些接口会因数据变少而“假性变快”或行为变化，复核时以不受这些数据影响的接口为准。(2) 有依赖关系的先重建被依赖方，再重建调用方，确保重新建连。(3) 重建后与故障前的健康基线比较：恢复则说明问题附着在 Pod 运行期状态上；完全不变说明是按 label 持续施加的外部注入（chaos 实验、sidecar、节点 tc 规则）或节点问题，不要重复重启，转去查注入源或节点。
  - [E7]（BH05）现象：某个调用方变慢，不确定是调用方自身/其所在节点的问题，还是某个下游的问题。判断：(1) 找出另一个独立的调用方（不同 Pod、最好不同 handler 路径），看它调用同一批下游的阶段是否也变慢；用它日志里相邻步骤的时间戳间隔估算各段耗时。(2) 两个调用方都慢，取它们共同调用的下游的交集，交集里再用 E3 的对照法排除仍快的下游，剩下的就是嫌疑；只有一个调用方慢、另一个正常，转查慢调用方自身（资源、节点、出方向网络）。(3) 对嫌疑之外的下游做反证：挑一个在 handler 末尾才被调用的下游，其入口日志应与调用方完成时刻几乎重合，重合即说明该下游及调用方出向网络正常。例：前端页面和下单流程都慢，共同点只有一个被两者调用的下游 Pod。

### 证据链

**1. 下单失败：checkoutservice 的 `SHIPPING_SERVICE_ADDR` 指向了错误端口**

frontend 日志（`frontend-fd686dbb-dmxdc`，近 30 分钟，按 `error|failed|500` 过滤，共 178 条匹配，展示最新 100 条）中所有 `/cart/checkout` 的 500 都是同一条：

```
"failed to complete the order: rpc error: code = Internal desc = shipping quote failure:
 failed to get shipping quote: rpc error: code = Unavailable desc = connection error:
 dial tcp 10.96.50.166:50052: i/o timeout"
```

- `10.96.50.166` = Service `shippingservice` 的 ClusterIP，而该 Service **只暴露 50051**（`port 50051 → targetPort 50051`，Endpoint `10.244.0.133:50051`），shippingservice Pod 的 `PORT=50051`。
- 但运行中的 checkoutservice Deployment（gen 76 / revision 74）env 是 `SHIPPING_SERVICE_ADDR=shippingservice:50052`。
- 对比可证这是**运行态配置被改**，不是历史遗留：旧 ReplicaSet `checkoutservice-5d5f4589c5`（2026-11-15 创建）里是 `shippingservice:50051`；07:08:04 新建的 `checkoutservice-77b8f6dc84` 里变成 `50052`（事件：`Scaled up replica set checkoutservice-77b8f6dc84 from 0 to 1` + 旧 RS `Scaled down … from 1 to 0`），`last-applied-configuration` 里也仍是 50051。同一 Deployment 其它地址（productcatalog:3550 / payment:50051 / email:5000 / currency:7000 / cart:7070）都对得上各自 Service。
- 结果：shipping quote 是 PlaceOrder 流程里的必经步骤，它挂 → 订单 100% 提交不了；因为失败在 shipping 这一步之前就返回，paymentservice 近 30 分钟几乎没有上游调用日志（11 条），与「下单 4 次失败 4 次」一致。

**2. 推荐服务被缩到 0（非致命，但确实是异常）**

- Deployment `recommendationservice` 现在 `spec.replicas=0`，Pod 已在 07:08:04 被删除（事件 `Scaled down replica set recommendationservice-6c88b5fb59 from 1 to 0`），其 Service `10.96.63.235` **没有任何 Endpoint**。
- frontend 每个商品页/购物车页都记录：`failed to get product recommendations … dial tcp 10.96.63.235:8080: connect: connection refused`（近 30 分钟上百条）。该错误只被 frontend 降级处理，页面仍返回 200（如 `/product/0PUK6V6EV0` → `status:200, took_ms:6`），这正好解释「其它页面还能打开」。

**3. 其余组件均正常（已检查，未见问题）**
- 全部 11 个 Pod Running、restartCount 0；adservice / cartservice / currencyservice / productcatalogservice / paymentservice / emailservice / shippingservice 日志中无 error/timeout/refused（各查近 30 分钟）。
- 所有 Service selector 都能匹配到 Pod、Endpoint 齐全（仅 recommendationservice 为空）。shippingservice Pod 近 10 分钟有 171 行日志，说明 50051 上服务本身是健康的、只是 checkout 连的不是这个口。
