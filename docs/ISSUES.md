# 工程问题记录

只记工程问题：设计缺陷、实验方法上的坑、代码 bug、和外部系统集成时的技术限制。
账号权限、网络、文件名、工具渲染这类配置和环境问题不记。

每条写清楚：现象、原因、怎么处理的、现在的状态。新问题加在最上面。

状态说明：**已解决** / **已规避**（绕开了但根因还在）/ **待验证**（要在真集群或真模型上确认）/ **未解决**

---

## E-020 环境里一条真实的旧告警成了 L05 的干扰项；按"原因名"去重会删掉同一原因的不同表现
- 现象一：笔记本上的 Redis 在 2026-11-12 04:52 打过一条 `Asynchronous AOF fsync is taking too long (disk is busy?)`，只出现过一次。此后 L05（Redis 的 Pod 网络延迟）答错的运行大多把它当成主因。注入的延迟让每次 Redis 往返固定多出约 200 毫秒，这条告警解释不了。
- 处理：标准答案不改；评分分两档（定位到 Redis 这一层 / 原因是网络延迟）；这一轮不清掉它，以保持和已有结果可比，换集群或本轮结束后补一组干净的对照。和 R07 的 Redis 残留是同一类问题：长期运行的环境会自己积累"真实但无关"的线索。
- 现象二：把 50 条经验按故障原因去重成 23 条后，L05 从 2/3 变成 0/3。被删掉的第 14 条和留下的第 2 条同属"Pod 网络延迟"，但第 2 条写的是"只有一个副本慢"，第 14 条写的是"共享的上游 Pod 慢、所有调用方一起慢"，后者才对应 L05。
- 经验：判断两条经验是否重复，要比较适用的表现，不能只比较原因的名字。（每格只有 3 次，L05 又受现象一干扰，这一条是迹象，不是结论。）
- 状态：现象一未解决（已记录为已知干扰）；现象二作为准入检查的设计约束

## E-019 "变慢"在服务端日志里只看得到一部分；云端节点会自动删掉没在用的镜像
- 现象一：把 api 的 CPU limit 压到 60m 后，20 个并发的客户端看到每个请求约 0.8 秒，但 api 自己记的处理耗时（elapsed_ms）中位数只有约 300 毫秒，第一次按"600 毫秒以上"确认注入时是 0/90。
- 原因：被限流时，一部分等待发生在请求进入应用之前（排队等 CPU），应用自己的计时看不到这一段。→ 确认条件改成"超过 200 毫秒的请求占多数"（正常是几毫秒），压测并发从 6 提到 20。
- 现象二：云端 k3s 上导入的 v3 / v3.1 镜像几分钟后消失，场景注入时报 `ErrImageNeverPull`。
- 原因：云主机磁盘使用率超过 kubelet 的镜像回收阈值，kubelet 每 5 分钟删一次"当前没有容器在用"的镜像，而变体镜像只在注入期间才被用到。→ 云端每次验证前重新导入；笔记本上磁盘充足，没有出现。
- 状态：已解决（云端为绕过）

## E-018 干扰项的标签把"我是干扰"写在了脸上；发布版本号泄漏运行历史
- 现象一：干扰用的 Pod 带标签 `triage/noise=true`，HolmesGPT 在一次回答里直接写"该 Deployment 带 triage/noise=true 标签，属于已知噪音"。→ 改成普通标签 `app.kubernetes.io/part-of: ops-tooling`。
- 现象二：Deployment 的 revision 已经到 160–220（每次注入和复位都会加一），HolmesGPT 据此推断"模板被反复改了几百次，有人一直在手工折腾"。这是我们反复跑实验留下的痕迹，真实环境里不会这样。
- 影响：现象一让那一次干扰失效；现象二没有改变结论，但给了 agent 一条不属于故障的线索。
- 状态：现象一已解决；现象二未解决（可选做法：每轮开始前删除并重建 Deployment，让版本号归零）

## E-017 第一版干扰项被 agent 一眼看穿
- 现象：第一版干扰项用 shell 一行命令实现（`tail /dev/zero` 制造 OOM、`echo ERROR; exit 1` 制造任务失败）。HolmesGPT 读了 Pod 定义后直接指出"这个任务是硬编码脚本，从未真正发起连接"，干扰不成立。
- 另一个坑：`tail /dev/zero` 作为子进程被 OOM 杀掉时，容器的 1 号进程（sh）还活着，容器不会重启，也就留不下 OOMKilled 记录。分配内存的进程必须是 1 号进程。
- 处理：改成两个正常的小程序（挂在 ConfigMap 里的 Python 脚本）：报表任务真的去连一个不存在的外部数据仓库；日志采集器第一次启动没有检查点时把全部积压读进内存而被 OOM，重启后有检查点就正常。它们是"无关服务的真实小毛病"，不是摆拍。
- 经验：干扰项必须是真实发生的无关问题；agent 会读配置和脚本，假的会被识破。
- 状态：已解决（效果待笔记本上的批量结果确认）

## E-016 重复注入同一个故障，agent 能看到之前几次留下的"答案"
- 现象：HolmesGPT 第一次诊断 R06 时说"这是第二次踩同一个坑"，并列出了之前几次注入 v1.1 镜像失败的时间。
- 原因：两条历史渠道。一是 Kubernetes 事件默认保留约 1 小时，之前 smoke 和验证留下的事件都还在；我们自己的工具会按注入时间过滤事件，HolmesGPT 不会。二是 Deployment 默认保留最近 10 个旧版本的 ReplicaSet，从里面能读出"这个镜像以前也发布失败过"。
- 影响：等于提前看到了答案；而且同一场景重复跑时，第 2、3 次看到的历史比第 1 次多，重复之间不再独立。
- 处理：执行器在每次注入前清空命名空间里的事件，并删掉副本数为 0 的旧 ReplicaSet。复跑 R06，HolmesGPT 不再提到历史，诊断依然正确。
- 遗留：已退出容器的旧日志（`--previous`）里也可能带着上一轮的痕迹，例如 Redis 上次启动时加载的数据量。目前看不构成答案泄漏，先记下。
- 状态：已解决

## E-015 接入 HolmesGPT 时的三个坑
- 卡死：用子进程启动 `holmes ask` 时，如果不关闭标准输入，它会一直等输入，直到超时（第一次跑了 600 秒没有任何输出）。→ 标准输入接 `/dev/null`。
- kubectl 崩溃：HolmesGPT 用 `ulimit -v` 限制工具进程的虚拟内存，默认值下 Go 写的 kubectl 一启动就报内存不足。它们自己的 CI 也遇到过（限制设为 800 MB 时约 20% 的 kubectl 调用会崩），用的是 1536 MB。→ 设 `TOOL_MEMORY_LIMIT_MB=1536`。
- 费用记成 0：LiteLLM 的价格表里没有 `deepseek-flash`，HolmesGPT 输出里 `total_cost` 一直是 0。→ 费用要用我们自己的单价，按它输出的 token 数来算（输出里有输入、输出、缓存命中的 token 数）。
- 状态：前两条已解决，第三条在写适配层时处理

## E-014 agent 只读每个工作负载的一个 Pod，漏掉了只出现在另一个副本上的报错
- 现象：真集群上第一次跑规则基线，开发集 9 个场景错了 1 个（R01，Redis 内存写满），结论是"无故障"。
- 原因：SOP 第 4 步读应用日志时，每个工作负载只读第一个 Pod。api 有 2 个副本，而失败的写请求只打到了其中一个，报错全在另一个 Pod 里。假集群里两个副本写了同样的报错，所以离线测试测不出来。HolmesGPT 的提示词里专门有一条"每个 Deployment 抽查最多 3 个 Pod"，处理的就是这个问题。
- 处理：每个工作负载最多读 3 个 Pod 的日志，日志行前标上 Pod 名；假集群的 R01 改成只有接流量的那个副本有报错。复跑 R01 两次都正确，开发集变为 9/9。
- 说明：这是开发集上的发现，按规则可以据此改 agent；保留集还没跑过任何诊断。
- 状态：已解决

## E-013 真集群验证发现的六个场景问题（离线测试全部没测出来）
- 背景：16 个场景在假集群上的离线测试全部通过，第一次在真集群（k3s）上注入就发现了下面这些问题。工具是新写的 `scripts/validate_injection.py`：注入后拍一份现场快照（Pod、事件、日志），对照场景答案里的关键证据，不运行任何诊断 agent，所以对保留集也能用。
- R09 注入命令写错：JSON Patch 的 `move` 操作，目标字段应该叫 `path`，我写成了 `to`。JSON 本身合法，所以离线测试通过，但 API server 拒绝执行。→ 修正，并加了测试 `test_json_patch_ops_follow_rfc6902`，检查每个 Patch 操作的字段。
- R09 事件文本和预期不同：Kubernetes 1.33 的挂载失败事件是 `references non-existent secret key: redis-auth.conf`，**不带 Secret 名字**；我按旧版文本 `couldn't find key ... in Secret ns/name` 写了解析。→ SOP 代码改为两种格式都认，新格式通过卷名去工作负载的卷定义里查 Secret 名字；假集群的事件文本也改成实测的样子。
- R05 内存限制不够低：worker 常驻内存约 19–20 MiB，24Mi 根本不会 OOM。改成 16Mi 后确认触发。另外，新 Pod 一直崩溃时，滚动发布会卡住，旧 Pod 继续处理事件，所以真实症状是"发布卡住"，不是原来写的"事件积压"。→ 改限制值，按实测改症状。
- R15 "假确认"：确认条件只检查 api 日志里有没有 `redis_unavailable`，结果被"改 CPU 限制导致 Redis 重建"那几秒的 `ConnectionError` 满足了，其实 CPU 限流根本没造成超时。另外 20m 太狠，Redis 连启动探针都过不了，永远到不了 Ready。→ 实测 100m / 50m / 20m 三档，选 50m（Redis 就绪状态反复切换，43% 请求 503，出现 `TimeoutError`），确认条件改为必须出现 `TimeoutError`。
- StatefulSet 不替换坏掉的 Pod：Pod 已经坏了（CrashLoopBackOff）时，把规格改回去，控制器也不会自动用新规格重建它，复位卡住。→ 涉及 Redis 规格的场景，复位步骤里显式删除 redis-0。
- `validated` 标记名不副实：R04、R08、R10、R11、R12、R16 当初标了"已验证"，其实只是推理后觉得有把握，从没在集群上跑过。→ 补测，并约定以后 `validated: true` 只表示真的在集群上跑过，实测结果写在 `realism.validation` 里。
- 状态：已解决（R04 等 6 个场景的补测结果见各场景的 `realism.validation`）

## E-012 实验环境从 kind 移植到云端时的四个兼容问题
- 背景：云端会话是一台 Firecracker 虚拟机（cgroup v1、root），原来的 kind 方案跑不起来，改成直接在虚拟机上跑 k3s。过程中遇到四个问题，都已写进 `scripts/setup_cloud_k3s.sh`，重建环境时会自动处理。
- 问题 1：kind 节点里嵌套起容器失败（`runc create failed: can't get final child's PID from pipe`）。k3s 自带的 runc 1.3.1 也是同样的错误，而系统里 Docker 用的 runc 1.5.2 正常。→ 把 k3s 用的 runc 换成系统的 1.5.2。
- 问题 2：换了 runc 之后，Pod 沙箱仍然起不来，报 `failed to update /proc/self/oom_score_adj: Permission denied`。原因是 kubelet 会把系统 Pod 的 OOM 优先级调低到 -998，这台虚拟机不允许。→ containerd 打开 `restrict_oom_score_adj`（专为嵌套或 rootless 环境准备的开关）。
- 问题 3：k3s 进程继承了云端的 `HTTPS_PROXY` 环境变量，API server 连本机 kubelet 时也走外部代理，`kubectl logs` 一律返回 EOF。→ 启动 k3s 时去掉代理变量；系统镜像用 GitHub 上的离线包，k3s 本身不需要联网。
- 问题 4：应用镜像的构建容器不信任云端代理的证书，镜像里的 pip 装不了依赖；另外源码从 Windows 打包过来后丢了读权限，镜像里的非 root 用户读不了源码，api 和 worker 启动即崩溃。→ 在宿主机上先下载好依赖包，用派生的 Dockerfile 离线安装（基础镜像和安装步骤与原 Dockerfile 相同），构建前统一 `chmod a+rX`。
- 另外，部署清单是按 kind 写的，Redis 的存储卷申请名叫 `standard` 的存储类，k3s 里叫 `local-path`。→ 加一个指向 local-path 的 `standard` 存储类，清单本身不改。
- 对实验的影响：k3s 和 kind 都是标准的 Kubernetes，但两者的事件文本、探针时序和存储实现可能有细微差别。在 k3s 上验证过的注入行为，换回 kind（例如新的 Ubuntu 台式机）后最好再跑一遍 smoke。
- 状态：已解决

## E-008 规则基线在假集群上几乎满分，保留集失去意义
- 现象：v2 场景写完后，规则基线在 16 个场景里答对 15 个。

- 遗留：假集群上的高分不代表真集群上的表现，真集群上的噪声和间歇性现象（R03、R13、R15）才是检验点。
- 状态：已规避
