结论先行：**34 道题（学习 FL01–10、验证 FV01–08、检验 FT01–16）、后台服务清单（`boutique/ambient-v4.yaml`）、判分规则（`boutique/eval_grades_v4.json`）和 v4 提示词均已生成，离线测试全过；集群逐题验证和小规模试跑还没做。**
2026-11-25 按用户要求加难：每道题的发布里多了一个带 log-shipper sidecar 的服务，指标表里它的 Pod 被限流，但它不是原因（第 2 节最后一行、第 6 节）。
检验题 FT01–16 在方法定稿前不跑 Agent（脚本会拒绝，必须加 `--finalize`）。第四版还没有任何一次运行，所以这次改题、改判分规则都在"运行之前"。

## 1. 为什么要第四版

第三版小规模试跑（20 次，`docs/V3.md` 第 8 节）暴露出四个问题：

1. **命名空间太干净，且故障刚发生就排查**：日志里除了正常请求行几乎没有任何告警，Agent 一搜 warning 就是故障；同时每次运行在故障注入后立刻开始，故障起点就在第一屏日志里。
2. **指标表里只有真故障 Pod 被限流**：无害的 CPU 调整基本不触发限流，指标表里一扫就能定位唯一被限流的服务。
3. **300ms 级别的延迟会让 gRPC 探针超时**：v3 把 `productcatalogservice`（315ms）标成“机制分不清”，但试跑中 Agent 用健康探针间歇超时（1 秒超时、每次新建连接需要 3 个包依次进入 Pod）合理区分了网络和进程内卡顿；而 230–280ms 之间探针是否超时全看运气。
4. **v3 格式把较小的原因挤进了 `not_causes`**：EV02 上 v3 提示词两次都把 `frontend` 的 CPU 限流放进 `not_causes`（写“不是主因”），导致按原口径被判错。

## 4. 判分规则（`boutique/eval_grades_v4.json`）与提示词（`--prompt v4`）

- 位置判定：把正确对象写成主因或次因，或在正文里提到该对象的该问题并承认对本次症状有影响（哪怕写影响小、不是主因），都算“对”；仅当未提到或明确称毫无影响时算“错”。
- 机制判定：`decidable=true` 必须表态且大类正确；`decidable=false` 表态正确或“如实未定”（候选 ≤2 大类、含正确答案、写出能区分的观察）都算对。
- 多报判定：`root_causes` 中出现无害改动（包括带 log-shipper sidecar 的服务，哪怕标成次要、写影响小）、后台服务（`promo-feed-sync`、`uptime-checker`、`catalog-crawler`）、被拖累但自身无问题的上游服务或不存在的问题，均记多报。
- 提示词：`scripts/holmes_pilot.py` 在 `bank >= 4` 时默认启用 `v4`（沿用 `holmes/prompts/system-v3.md` 和两步逐条核对，输出格式换成带 `role` 的 `FORMAT_V4`）。

## 6. 被限流的 sidecar（2026-11-25 加难）

**为什么**：第三版试跑里 CPU 和配置的原因 8 次全部找对。无害的 CPU 改动（调低但够用的上限）从不被限流，`promo-feed-sync` 又不在任何请求路径上，所以"指标表里被限流的商城服务就是原因"这条捷径一直有效。

**做法**（`boutique/make_v4_scenarios.py` 的 `SIDECAR`、`add_sidecar()`；脚本在 `ambient-v4.yaml` 的 Secret 里）：

- 每道题的发布给一个商城服务加一个 `log-shipper` 容器：CPU 上限 `20m`，每隔 4 到 8 秒处理一批日志，每批烧 18 到 28 毫秒 CPU（按 CPU 时间算，不按次数，换机器也一样）。在 20m 的配额下，每批要排一秒左右，所以它一直被限流。
- Agent 的指标表按 Pod 合计，这个服务的 Pod 会显示明显的限流。按以前验证的数（商城容器 60 秒里约 200 到 250 个有任务的周期），预计 Pod 合计的限流占比在 30% 左右，和真 CPU 故障（9% 到 54%）在同一量级，光看大小分不出来。
- CPU 配额按容器算：业务容器不受影响，没有请求要等 sidecar，所以它**不是原因**，写成原因（哪怕标次要）算多报。
- 能分出来的证据，全在 Agent 自己的工具里：这个 Pod 的 CPU 用量远低于业务容器的上限（真被限流的业务容器，平均用量占自己上限的比例高得多：FV01/FL01 实测四到五成，限流发生在请求成批到来、用完每 100ms 配额的时候；sidecar 所在 Pod 只用 Pod 上限的几个百分点）；指标表的上限一列比 Deployment 里业务容器的上限多 20m；Pod 里多了一个容器；sidecar 自己的日志里每批耗时一秒左右。

**放在哪**（34 道题见第 3 节最后一列）：在症状对应的请求路径上（让"不在路径上"这条捷径排除不掉它）；不是真实原因；不是网络故障服务的直接调用方（不和二级依赖的陷阱叠在一起）；不是工单猜的那个服务；不放在 frontend（用户侧数据和确认步骤读它的日志）和 redis-cart 上；成对的题放在同一个服务上。发布里已有的成员优先，没有合适的就把它加进发布（16 道题），所以这 16 道题的无害改动数多了 1。

**配套改动**：

- 复位第一步先删掉 sidecar（`kubectl set resources` / `set env` 不带 `-c` 会连 sidecar 一起改）。
- 健康检查会发现残留的 sidecar（`extra_containers`），`remediate.recover` 会先删掉它。
- 验证脚本额外按容器记录限流（`throttling_by_container`），确认被限流的是 sidecar、不是业务容器；"Pod 没就绪"的判断改成认 2/2。Agent 的指标工具不变，仍按 Pod 合计。

**这道陷阱是不是公平**：在真实生产里，Pod 级的监控看板把 istio-proxy、日志采集这类 sidecar 的限流算到业务 Pod 头上，是常见的误导。能不能想到"配额按容器算"，正是这里要考的。

**验证时要确认**（不花钱）：

1. 每道题的 sidecar 2/2 就绪、不重启；按容器看只有 `log-shipper` 被限流；Pod 合计的窗口限流占比在 15% 到 45% 之间。不在这个范围就调每批的 CPU 量，先报给用户。
2. Agent 的日志工具（HolmesGPT 的 `fetch_pod_logs`）在两个容器的 Pod 上能读到业务容器的日志，也能读到 sidecar 的日志。Docker 开着时可以直接查镜像里 HolmesGPT 的源码。读不到的话，这个陷阱就从"能分清"变成"分不清"，要先报给用户。
