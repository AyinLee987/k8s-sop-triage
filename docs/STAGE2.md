# 阶段 2：换更强的模型重写经验（2026-11-22）

结论先行：**条目确实从"这次故障的结论"变成了"可迁移的判断方法"，但材料自带的偏向没有消失。**
学习材料（BH01–15）里变慢的原因全是网络，新条目仍然把"变慢"往网络上引，有的直接写了"先查网络，不要先查 CPU limit"。
换模型解决的是"写得具体还是通用"，解决不了"材料只见过一种原因"。这一步没有跑评估，以上只是读条目得出的判断。

## 条目对照（节选）

同一批题目（BH01–05 一带的"整体变慢"）在新旧库里对应的条目：

| | 旧 | 新 |
| --- | --- | --- |
| B | 延迟类：看耗时是否与"调用次数"成比例……（后面列的是 `*_SERVICE_ADDR`、2–3ms、数秒超时等这几道题里的具体值） | 找瓶颈：把各 handler 耗时与它调用了哪些下游、各几次比较。以最快的 handler 作对照，它调用到的下游都可排除；耗时随某下游调用次数成台阶增加，瓶颈就在该下游。再比较调用方发起时间、被调方入口日志时间和调用方完成时间，看耗时集中在哪一段。 |
| D | 两种形态都指向某下游 Pod 的 veth netem：(a) 整体台阶——耗时随调用次数以 200–300ms 台阶增长；(b) 尾部弥散——中位数正常、约 10% 请求 >180ms…… | 取单个慢请求，对齐调用方发起、下游入口日志、调用方完成三个时间点：间隔集中在到达下游之前，下游处理和回程都很快，就说明延迟在通往该 Pod 的入向网络上……下游自记耗时远小于调用方看到的耗时，先查该 Pod veth 上的 tc/netem，**不要先查 CPU limit**。 |

新库里出现、旧库里没有的方法（各举一条）：

- B 新：CFS 限流和网络延迟的区分——"慢请求紧聚在'基线 + 同一固定量'及其整数倍上，支持被加了固定延迟；CFS 节流的增量应在 0 到一个周期之间连续分布"。
- B 新：下游日志里两条记录之间有空档，不能当作它停顿的证据，要先看它每个请求自己的"入口到完成"耗时。
- C 新：修复后失败没有归零时，先对齐"统计窗口、改动提交时刻、最后一条错误的时刻"，再判断是不是生效滞后。
- D 新：多个候选服务都显得变慢时，耗时恰好等于"调用慢下游次数 × 增量"的只是被传染，先处理能解释全部耗时的最小集合。

完整条目在 `holmes/skills/xinc-{B,C,D}-opus/*/SKILL.md` 的"经验条目"一节；每一步的改动在同名的 `.log.json`。

## 判断

1. **"具体结论 → 可迁移的方法"：是。** 三个库都从"某服务约 200ms 就是它的 veth 上有 netem"变成了"对齐三个时间点""按调用次数拼耗时""拿不调用任何下游的接口做对照"这类换个服务也能照做的做法。
2. **材料的偏向还在，D 最明显。** D 新有 4 条把"只读无法区分 CPU 和网络"的情况导向"先清除 tc，恢复了就排除节流"。在学习材料里这永远是对的，因为没有一道题是 CPU。到了有 CPU 限流的新题上，这几条很可能帮倒忙。这正是"准入检查"要拦的东西，也说明阶段 4 给学习集加 CPU 题（CL01–07）是必要的。
3. **C 新的条目里"未解决"占比高（3 条；B 新 0 条、D 新 1 条）。** C 的材料是 agent 自己修、自己验证的记录，网络故障它修不了（没有清除 tc 的操作），所以很多轮以"没修好"收场，写出来的是"还缺什么证据"。内容诚实，但对下一次排查的指导最弱。
4. **新条目里出现了"被注入"这样的说法**（条目里 B 新 9 处、C 新 3 处、D 新 6 处）。材料里 agent 自己的分析就用了这个词，写作模型沿用了。它暗示"这是人为故障"，以后的提示词里应该要求不用这个词。这次没有改，因为改了就要重写。
