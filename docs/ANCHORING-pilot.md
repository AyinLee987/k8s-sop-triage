# 锚定问题的小规模试验：设计（2026-11-23，运行前写下）

起因：`docs/STAGE6-partial.md` 的轨迹分析显示，Agent 找到一个真实原因后，会把后面看到的异常都归给它，漏掉第二个独立原因。
调研报告（桌面"K8s排障Agent测试平台方案"文件夹里的《Agent单一原因锚定问题_调研报告》）列了六条改进建议，用户选第 2、5、6 条先试。

## 原论文里读到了什么

| 方法 | 出处 | 读到的程度 | 我们照着做的部分 |
| --- | --- | --- | --- |
| 2 逐条核对症状覆盖 | Sonoda et al., Jpn J Radiol 2024（两步提示） | 读到了提示词的开头和结构：第一步"把病例按类别整理成要点"，第二步"根据整理好的信息"给出最可能的诊断和另外两个鉴别诊断。322 个病例，首选诊断 60.6% 对 56.5% | "先整理发现、不下结论，再诊断"的两步顺序 |
| 6 约束输出格式 | IBM ITBench SRE agent 的提示词（GitHub），ITBench-AA 的评分说明 | 读到了输出结构：`entities`（含 `contributing_factor`、`reasoning`、`evidence`）、`propagations`（`source`、`target`、`condition`、`effect`）、`alerts_explained`（含 `explained`）；规则"不要把原因和它派生的症状都标成原因"；评分是漏掉任何一个根因记 0 分，否则按精确率 | 三个字段的结构、`explained` 标记、"最小的一组独立根因" |
| 5 干净上下文的独立审查 | Ke et al., JMIR 2024（arXiv 2401.14589） | **只读到角色描述，没有提示词原文**（原文在图里）。四个角色：初诊的住院医师；唱反调的同事，"严格审视初步诊断，指出不一致之处，为其他诊断辩护"；资深医生，"指出初步诊断里的认知偏差，引导得到更细致的诊断"；记录员。讨论后由初诊者重新给出最可能的诊断加一个备选 | 角色分工和顺序。措辞是我们自己写的 |

两处要说明：调研报告引的那篇评论说两步提示"减少了锚定"，但 Sonoda 的原文只测了准确率，没有测锚定。
另外"单靠提示词不够"有出处：Handler et al.（arXiv 2605.15000）加了强调安全的提示后，过早定论只是减少，原文结论是 "prompt-level interventions alone are insufficient"。
AWS DevOps Agent 的博客正文没有抓到，没有参考。

## 四种问法

实现在 `scripts/anchoring_pilot.py`，提示词全文见该文件。排查用的 Agent、模型、工具、基础 SOP 都不变。

| 代号 | 改了什么 | 没改什么 |
| --- | --- | --- |
| base | 无，和 `holmes_pilot.py` 的提示词完全相同 | |
| m2 | 提示词里加两步：先只整理症状清单（每类请求现在和健康时的耗时、调了哪些下游各几次、各 Pod 的异常），不写原因；再诊断，并逐条写出每个症状由哪个原因解释、能解释多大一部分，没解释完的标"未解释"并继续查 | 回答格式 |
| m6 | 回答格式换成三个字段：`entities`（每个对象标是否独立根因、机制大类）、`propagations`（谁拖累了谁）、`symptoms_explained`（每条症状是否已解释） | 排查的做法 |
| m5 | 先按 base 得到初步诊断；一个只看到故障描述和这份报告的"同事"唱反调；一个"资深工程师"指出偏差并决定是否认可；不认可时，一个全新的 Agent 会话带着初步结论和质疑重新排查 | 第一次排查和 base 相同 |

m5 的两个审查角色没有工具，看不到工具调用记录，用的是和 Agent 相同的模型，所以这一组改的是流程，不是模型。

## 用例

只用学习题和验证题（脚本会拒绝检验题）。

| 题 | 故障 | 之前的表现 |
| --- | --- | --- |
| CV05 | 前端 CPU 限流 + 货币服务网络延迟 | 基础 SOP 5 次里 4 次只报 CPU 限流 |
| CL02 | 购物车服务 CPU 限流 + 推荐服务网络延迟 | 阶段 4 的诊断只报了 CPU 限流 |
| CL04 | 货币服务 CPU 限流 + 购物车服务网络延迟 | 同上，而且只用了 14 次工具调用就收工 |
| CV02（对照） | 只有购物车服务 CPU 限流 | 一直全对。用来看新做法会不会硬报出第二个原因 |

## 看什么

- 双故障题：第二个原因的去向（漏掉、位置没定、机制没定、找到）。只报一个原因的比例就是"单因归并率"。
- 对照题：有没有多报不存在的原因（过度拆分）。
- 是否通过（规则同 `boutique/eval_grades_v2.json`）、每次的 token 和耗时。m5 另记审查的结论和是否触发重查。

判分：base、m2 和 m5 的最终回答格式相同，混在一起遮住做法后判；m6 的格式不同，遮不住，单独判并在报告里注明。

## 事先知道的局限

- 规模很小，只能看出很大的差别；结果是线索，不是结论。
- m5 触发重查时相当于两次排查，更贵也更久，比较时要把成本算进去。
- 基础提示词里有一句"两个解释都说得通而无法区分就都写出来"，它本身会鼓励不表态。这次不动它，四种问法都带着。

# 结果（方案 A：每格 1 次，共 16 次，2026-11-23 至 24）

结论先行：**每格只有 1 次，下面都是线索，不是结论。** 能看到的是：只换回答格式（m6）不管用，三道双故障题漏了两道；
"先整理症状再逐条核对"（m2）三道都找到了第二个原因，对照题上没有多花钱也没有乱报；
独立审查（m5）把一次漏报救了回来，但审查者四次全判"重查"，连答对的对照题也不放过，所以每次都要付两倍多的成本。
另外这批运行里拉低通过率的主要不是漏报，而是"找到了却不表态"，这三种方法都不管这件事。

实际花费 5.93 元（估 5 到 9 元），余额 246.35 → 240.42。记录在 `results/anchoring/anch-A/`，判分在其中的 `grades.json`。

## 看到了什么

1. **基线这次自己就找到了 2/3。** 之前 CV05 的基线是 5 次里 1 次找到。同一种做法前后差这么多，说明每格 1 次的结果受运气影响很大，下面几条都要带着这个前提看。
2. **只换回答格式（m6）不够。** 漏掉的两次里，Agent 照样填了症状表，但把每条症状都写成"已被那个原因解释"。格式要求它表态，它就表了一个错的态。
3. **m2 的额外成本只出现在有东西可查的时候。** 双故障题上它多用了约 1.4 倍的 token，对照题上和基线一样（72 万对 71 万），也没有硬报第二个原因。
4. **m5 的审查不会分辨。** 四次全判"重查"，四次都说初步诊断"锚定"了，包括答对的对照题。CV05 上它还指错了方向：初步诊断把货币服务当主因是对的，审查却批评这是锚定、怀疑前端限流才是主因。
   它的作用来自"逼着再查一遍"，不是来自批评得准。CL04 那次是真救回来了：第一次只报限流，审查点出"发现 33% 限流就把所有延迟都归给它"，重查后找到了购物车的网络延迟。
5. **拉低通过率的主要是不表态。** 9 次找到第二个原因的运行里，有 5 次写的是"网络还是进程内，分不开"，按规则不算通过。这三种方法都不针对这一点。
   基础提示词里还有一句"两个解释都说得通而无法区分就都写出来"，它在鼓励这种写法。

## 建议（等用户决定）

- m6 不单独用。结构化的回答格式对判分有好处，可以留，但要和 m2 的做法配在一起。
- m2 值得放大样本再测：它便宜、不乱报，方向是对的，但 0/3 通过说明单靠它过不了"表态"这一关。
- m5 现在的样子太贵。要用的话应该改成有条件触发：只有当 m2 的核对里确实留下未解释的症状时才重查，而不是每次都查。
- "不表态"是另一个独立的问题，要单独处理：把基础提示词里那句话改成"写出首要判断，再列不能排除的备选"，并在同一批题上看它的效果。

# 放大样本前的检查（2026-11-24）

用户要求每组跑 3 次，并在此之前检查实验有没有不合理的地方。查了审查环节、用例线索、注入的副作用、环境残留四个方面。

## 确定的缺陷（已修，有测试）

1. **m5 里"唱反调的同事"四次输出都是空的。** 这个模型先思考再回答，给它的输出上限是 8000 token，全被思考用掉，正文一个字没有。
   资深工程师收到的"质疑"是空白。所以方案 A 的 m5 实际是"只有资深工程师一个人审"，上面"结果"一节里 m5 的数字要按这个理解。
   修法：上限提到 20000；正文为空就重试一次，仍为空则这次运行记为失败、之后重跑。
2. **两个审查角色不知道 Agent 只有只读权限。** 资深工程师提的检查里有"临时把 CPU 上限恢复做对照""加链路追踪""进 Pod 里直接调用"，都做不到。
   修法：在两个角色的提示词里写明 Agent 能看什么（命名空间里的对象、Pod 日志、资源指标表）、不能做什么（改配置、进容器、看节点、链路追踪）。

## 用例线索

3. **网络故障的机制没有正面证据。** 延迟加在节点上，Agent 看不到；"是网络还是进程内"只能靠排除法推。所以"通过"这个指标有一部分在考敢不敢表态，不是在考有没有漏。
   这一轮的主要指标定为"第二个原因找到没有"，"通过"作为次要指标。
4. **三道题的线索强度不一样。** 货币服务的日志带毫秒时间戳，能直接看出请求晚到（CV05）；推荐服务的日志打在处理末尾，分不清是进来慢还是它调下游慢（CL02）；
   购物车服务的日志没有时间戳，只能从"加购接口变慢"反推（CL04）。不算缺陷，但比较三道题时要知道。
5. **对照题 CV02 症状很弱。** 工单写"明显变慢"，监控给的是 3% 到 9% 的请求超过 180 毫秒，中位数 8 到 10 毫秒，题面和数字对不上。
   可以再加一道症状明显的单故障对照题 CV01（只有推荐服务网络延迟，约 67% 的请求变慢），顺便看这些做法在"只有一个网络原因"时会不会乱报。

## 注入的副作用

6. **购物车服务的 CPU 压到 30m 后，新 Pod 启动时探针超时，有约 40 秒没人服务。** 产生的 500 和几秒长的请求有时落进给 Agent 的监控摘要：
   CL02 四次运行的 99 分位分别是 0.9、5.5、5.6、9.1 秒。这是 CPU 故障的真实后果，但每次落不落进窗口看运气，是运行之间波动的来源之一，也让 CPU 这个原因更抢眼。
7. **两个故障不是同时生效的。** 先改 CPU 并等滚动更新完成，几十秒后才加网络延迟。Agent 有时会用到这个时间差（"限流生效时页面还是快的"）。线索是真实的，但永远是 CPU 在前。

## 环境残留

8. **每次运行前会重建全部 Pod，然后立刻注入。** 这是为了清掉上一题的日志，但后果是：日志里几乎没有健康时的流量可比（m2 恰恰要求写"健康时的水平"）；
   启动噪声（连接被拒、.NET 启动吃 CPU 被限流）就在一两分钟前；"全部 Pod 两分钟前刚重启"本身是个显眼的异常。
   做了一个开关 `--settle N`：重建后先跑 N 秒健康流量再注入。默认 0，和以前一样。
9. **版本号和事件计数会露出反复改动。** frontend 的 revision 已到 238；同一个改动的事件会显示累计次数（控制器内存里的计数，清事件清不掉）。运行前已清事件和旧 ReplicaSet。影响小，各组相同，留到 v3 处理。

## 检查后没发现问题的

基础 SOP、指标工具、步数上限、模型四组一致；16 次运行的监控摘要窗口都是 45 到 60 秒，500 基本为 0（唯一的 1 个是支付服务拒收卡种，提示词里有说明）；没有运行超时；注入和恢复都成功。

## 新增的对照组

`re`：第一次排查和基线相同，然后让一个全新的 Agent 会话"重新排查一遍并核实"，不给任何审查意见。用来分清 m5 的作用来自审查内容，还是仅仅来自多查了一遍。

## 方案乙（用户 2026-11-24 同意，运行前写下）

- 5 种问法（base、m2、m6、m5、re）× 4 道题（CV05、CL02、CL04、对照 CV02）× 3 次，共 60 次注入；`--settle 120`；其余同方案 A。结果在 `results/anchoring/anch-B/`。
- 同一道题的 5 种问法挨着跑，跑完一轮再跑下一轮。出错的运行（含审查没有产出）整批结束后重跑。
- 主要指标：三道双故障题上"第二个原因找到没有"（答案把网络那个服务列为原因或候选），每种问法 9 次。
  次要指标：通过数；对照题上有没有报出不存在的第二个原因；每次的 token 和耗时；m5 的审查结论和两个角色是否有产出。
- 判分：base、m2、m5、re 的最终回答混在一起遮住做法后判；m6 格式不同，单独判。判分人 Fable 5.2。
- 方案 A 的结果不合并（审查环节和等待时间都变了）。
- 估价 21 到 30 元，超过 36 元先停。

### 运行中的一次修正（2026-11-24 02:20）

跑到第 5 次时例行检查发现：m5 里唱反调的角色这次有输出，但只有 314 个字，在表格开头被截断。20000 的上限仍然不够（思考加回答合计）。

改动：上限提到 64000；被上限截断的回复和空回复一样处理（重试一次，仍不完整则这次运行记为失败）。
受影响的只有 CV05 的 m5 第 1 次，已作废并重跑，原文件留在 `results/anchoring/anch-B/_void/`；被打断的 CV05 re 第 1 次也重跑。之前完成的 base、m2、m6 三次不受影响。
