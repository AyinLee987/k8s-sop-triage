# 第三版题库（v3）：设计、判分规则、提示词（2026-11-24）

结论先行：**34 道题（学习 EL01–10、验证 EV01–08、检验 ET01–16）已生成，离线测试全过；集群上的逐题验证和小规模试跑还没做。**
同时做了两处方法上的改动：判分规则改成"能分清的必须表态，分不清的如实说也算对"；HolmesGPT 自带提示词里要求"没直接证实就别下结论"的三句换掉了。
检验题在方法定稿前不跑 Agent（脚本会拒绝，必须加 `--finalize`）。

## 1. 为什么要第三版

第二版的 CPU 和配置题被 Agent 用"找唯一改动"的办法全部答对：比对 last-applied 注解或上一版 ReplicaSet，哪个 Deployment 的配置变了就是谁。
CV02/06/08 三道题 75 次运行里 72 次引用了这类痕迹。另外"找到原因后不表态"的分析（`docs/HEDGING-analysis.md`）表明，
判分规则和提示词互相矛盾：提示词要求分不清就都写出来，判分却要求表态。

## 2. 题库层的改动

| 改动 | 做法 | 针对什么 |
| --- | --- | --- |
| 发布批次 | 每道题在同一分钟里滚动发布 2 到 4 个 Deployment，带同一个 RELEASE_TAG；有配置类故障时，故障就在这批改动里 | "哪个变了就是谁" |
| 无害的相似改动 | 部分批次成员带一个看着像原因、其实无害的改动：地址改写成完整域名（指向同一个 Service）、CPU 上限调低但仍远高于用量 | 同上：凡是有 Deployment 级故障的题，"标签之外的改动"都不止一处 |
| 去掉 last-applied | 第三版的每次运行开始前删掉所有 Deployment 和 Service 的 last-applied 注解；上一版 ReplicaSet 保留（真实的发布历史） | "注解和实际配置不一致" |
| 工单里的猜测 | 10 道题的工单带报告人的猜测，从不指向真实原因 | 锚定在工单上 |
| 二级依赖上的网络故障 | paymentservice、emailservice、redis-cart、productcatalogservice（推荐服务背后）上的网络故障共 9 处 | 把被拖累的调用方当成原因 |
| 成对的题 | 同一个 CPU 故障，一道单独出现、一道再加一个网络故障（EV01/EV02、ET05/ET16、ET06/ET11、EV08/EL08） | "总多报一个网络原因"也能得分 |
| 健康流量 | 新 Pod 起来后先跑 2 分钟正常流量再注入故障 | 日志里没有健康基线、启动噪声太近 |
| 证据链和"能否分清" | 每个原因写出 Agent 用自己的工具能看到的证据链，并标 decidable | 判分要求表态的依据 |

另外：新题号用 EL/EV/ET（B 是第一版，C 是第二版；跳过 D，因为"D 组"已经指一种经验）。第二版的生成脚本和题库原样保留。

### 没做的

- **标签撞车（部分流量误路由）**：每个调用方只开一条长连接的 gRPC，每个服务只有一个副本，被误路由的比例会随机地是 0% 或 100%，不是稳定的"一部分失败"，不符合"现象每次都稳定出现"。要做得加副本数，留到第三档。
- 第三档的其它改进（每跳延迟指标、NetworkPolicy、多节点、修复评估）：仍在待办里。

### 还剩的泄露

- Deployment 的 revision 号：经常出题的服务（frontend、cartservice、currencyservice）revision 号大得多。旧的 ReplicaSet 每次运行前已经删掉，只剩号码本身。
- 所有 Pod 都是两三分钟前新建的（每次运行开始时为了清空旧日志而重建）。
- Service 选错 Pod 的故障，selector 上直接写着另一个服务的名字。这是这类故障本身的样子，不改。

## 4. 网络故障的机制什么时候算"能分清"

网络故障加在 Pod 的网卡上，进入这个 Pod 的每个包都晚一点。

| 出故障的服务 | 能不能分清 | 依据 |
| --- | --- | --- |
| 不调用别的服务的（currencyservice、productcatalogservice、paymentservice、emailservice、shippingservice、redis-cart） | 不能 | 请求晚到、处理很快，和"进程在处理前卡住"在日志和指标上一模一样 |
| recommendationservice | 不能 | 每个请求都一样（进来一次、收一次商品目录的回包），没有次数不同的操作可比 |
| cartservice、checkoutservice、frontend | 能 | 不同操作经过它网卡的回包次数不同，多出来的时间和这个次数成正比，进程内卡顿解释不了；限流为 0 排除 CPU |

CPU、配置、应用延迟都标"能"：限流指标、Deployment 里的配置值都看得到。

这些标签是按题目结构定的，还要在试跑里核对：标"能"的原因如果试跑里没有任何一次运行分清，或者标"不能"的被稳定分清了，在正式运行之前改标签。

## 5. 判分规则（`boutique/eval_grades_v3.json`）

和第二版相比只改了机制这一项，以及多报的口径：

| 原因的类型 | 表态且对 | 如实说分不开 | 表态但错 |
| --- | --- | --- | --- |
| 能分清 | 通过 | 不通过 | 不通过 |
| 分不清 | 通过 | 通过 | 不通过 |

"如实说分不开"要同时满足：候选不超过两个大类、正确的在里面、写出了哪条观察能把它们分开。
多报：回答 JSON 的 root_causes 里写了就算报了，同一批发布里的无害改动被写成原因也算。
固定报告三个数之外，加报：分不清的原因里"表态对"和"如实未定"各多少（看经验是不是只让它敢猜）、无害改动被报成原因的比例、按题目设计特征分层的通过率、两个原因的题的第二个原因去向。

## 6. 提示词（第三版题库默认使用，`--prompt v3`）

| 改动 | 做法 |
| --- | --- |
| HolmesGPT 自带的系统提示词 | 用它自己的开关 `ENABLED_PROMPTS` 关掉 general_instructions 和 style_guide 两块，换成 `holmes/prompts/system-v3.md`。新文件和原文逐行相同，只改了三行（测试会比对） |
| 我们自己的开场白 | 去掉"两个解释都说得通就都写出来"；改成"证据能分开就下结论并给出把握程度，分不开才说分不开，并说明哪条观察能分开" |
| 逐条核对 | 锚定试验里的做法 m2：先列症状清单，再逐条说明由哪个原因解释、解释了多少 |
| 回答格式 | JSON 每个原因带 mechanism（network/cpu/config/app/unknown）、confidence、evidence、explains、alternatives；另有 not_causes 和 unexplained |
| 用户侧数字 | 多给一个"下单请求耗时中位数"（有几道题只让下单变慢，下单只占约 5% 的流量） |

HolmesGPT 原文被换掉的三行：

| 原文 | 改成 |
| --- | --- |
| If there are multiple possible causes, list them in a numbered list. | 几个独立的问题都有贡献就都报；几种解释争同一个症状时，说哪个最可能、为什么，其它作为备选 |
| Use hedging language ("possible", "likely", "may") for anything not directly confirmed; if the analysis is inconclusive, say so. | 区分观察和推断；推断和观察吻合、和其它解释矛盾时就是结论，写出把握程度；只有在拿得到的数据下几种解释预测的现象一样时，才说分不开，并说出能分开它们的观察 |
| Distinguish confirmed facts from hypotheses ("possible cause", "might be"). | 观察和结论分开写，每个结论给出把握程度，而不是含糊其辞 |
