Partial Service Unreachability Differential Diagnosis
Candidate A: caller-side downstream address mismatch (wrong configured host:port; misspelled or nonexistent DNS name).
Confirms A: only one caller path fails; error shows DNS failure for a name no Service defines; other callers resolve/reach the same dependency normally; correcting the caller address restores resolution/reachability.
Rules out A: dependency pods/Services/Endpoints healthy; configured name resolves to a defined Service and port; multiple callers fail; no policy/CNI/DNS infrastructure or application error.
Candidate B: node-local dataplane failure (per-node packet-forwarding agent).
Confirms B: connectivity failure confined to clients on one node; same service/port succeeds from other nodes; that node's networking agent is inactive/dead/killed, not a config or crash-loop error.
Rules out B: pods Running/Ready and endpoints correctly populated; control plane/apiserver healthy; no DNS, policy, application, node NotReady/taint/pressure issue; failure is not localized to one node.
Check order (cheapest, most discriminating first):
1. Run same dependency/port from other callers and other nodes; this scopes caller-only vs one-node-only failure.
2. For caller-only, compare failing caller's configured downstream host:port with actual Service name/port and inspect DNS error.
3. For one-node-only, check affected node's packet-forwarding agent status for inactive/dead/killed.
4. Before either conclusion, rule out pod crash/readiness, Service selector/port/endpoint gaps, DNS/CNI/NetworkPolicy infrastructure faults, control-plane/apiserver degradation, node NotReady/taints/resource pressure, and application errors.
5. Correct caller address or recover node datapath; verify resolution/reachability.
6. Apply the same dependency-address check to any service-to-service dependency.
