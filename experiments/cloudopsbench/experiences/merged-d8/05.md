Partial Unreachability: Differential Diagnosis
Candidate: backend/dependency unavailability. Confirms: target 5xx/timeouts. Rules out: route-specific 404 while other routes work, healthy target pods, populated endpoints, other callers resolve/reach the same dependency normally.
Candidate: gateway/ingress misrouting. Confirms: route-specific 404/Not Found while other routes work, healthy target pods, populated endpoints, failing path matches gateway route definitions; compare successful vs failing routes. Rules out: backend 5xx/timeouts, pod crashes/readiness failures, empty/mismatched endpoints, DNS/discovery gaps, unrelated network-policy/ingress faults.
Candidate: caller-side downstream address mismatch. Confirms: only one caller path fails while dependency pods/Services/Endpoints are healthy; caller host:port differs from actual Service name/port; DNS error for a name no Service defines while other callers resolve/reach the same dependency normally; correcting caller env/config restores resolution/reachability. Rules out: dependency outage, cluster DNS, pod readiness/restarts, Service selector/endpoint gaps, resolvable port mismatches, NetworkPolicy/CNI/DNS infrastructure faults, target application errors.
Check order: first inspect the failing caller’s configured downstream host:port and error text for misspelled/nonexistent DNS (cheapest, most discriminating).
Then check target 5xx/timeouts and pod readiness/restarts.
Then check Service selector/endpoints.
Then check DNS/registration.
Then check gateway/ingress route config and access logs for route-specific 404/Not Found; compare successful vs failing routes.
