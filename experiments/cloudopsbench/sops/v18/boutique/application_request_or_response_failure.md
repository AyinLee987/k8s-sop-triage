# SOP: application_request_or_response_failure

Symptom: An application request reaches a service but returns an HTTP, RPC, or business-level error while basic service connectivity remains available.

Signals:
- HTTP 400, HTTP 500, or HTTP 503 is observed while downstream connectivity succeeds
- RPC request returns an application or business-semantics error
- downstream Service is reachable but the operation still fails
- logs show nil, missing, misplaced, semantically invalid request values, or an error response for valid request input
- application returns an incorrect response or status despite healthy pods and routing
- repeated 400 or 5xx responses occur on valid user paths, with handler logs such as 'id not specified' even though the path segment is present
- an entry-service handler logs 'product id not specified' for GET /product/<id> while the same request path contains a valid product ID
- a handler extracts a valid path/query/body parameter and then overwrites it with an empty string, nil, or a default value before constructing an outgoing downstream RPC/HTTP request, producing a downstream empty-value error, NotFound, or 'no product with ID ' while the request itself contains a valid value
- a downstream RPC receives an empty argument even though the caller's request path contained a valid value
- a handler sets a required value to nil, an empty string, or a default before building an outgoing RPC/HTTP request, so the downstream receives a nil/empty required field even though no request-path value is involved (for example, money = nil followed by From: money)
- the downstream callee logs a null/undefined field error such as 'Cannot read properties of null (reading units)' or 'Cannot use in operator to search for message in ...' while the caller returns HTTP 500; this is a missing required parameter sent by the caller, not an error-branch defect
- caller and callee both show the same null-field error chain (caller sends nil required field, callee throws TypeError reading that field) for an otherwise healthy request
- a handler extracts a valid path/query/body parameter and then, through handler-side logic or a defective local error branch, resets, clears, or ignores it and returns a local HTTP 400 or 500 such as 'product id not specified' without sending a downstream request whose empty required field explains the failure; this local rejection of valid input is code_wrong_return
- source review distinguishes caller-side nil/empty assignment or omission of a required request field before an outgoing call (code_missing_parameter) from an inverted guard, wrong error branch, or defective return/response path that rejects or misreports an otherwise valid, extracted, non-absent value (code_wrong_return)

Start at: locate_request_failure_owner

## Steps

### Step: locate_request_failure_owner
Goal: Localize the service, operation, and caller/callee ownership of HTTP, RPC, or business request errors after basic service connectivity remains available. Keep two leading branches: code_missing_parameter when a required value is absent or is cleared before an outgoing RPC/HTTP request so the downstream receives nil/empty or throws a null/undefined read; and code_wrong_return when a valid request parameter is present but a local handler return, error branch, guard, or response-construction defect rejects or misreports it, including HTTP 400/500. When a valid path value is present and the handler logs 'product id not specified' or 'id not specified', do not conclude missing parameter from the message alone; determine whether an outgoing downstream call received an empty required field or whether the local error branch itself wrongly rejected the valid request. When a downstream callee logs a null/undefined read on a required field and caller source shows a nil/empty assignment feeding the outgoing request field, keep code_missing_parameter. When an alert names a downstream service but caller logs show valid requests failing at the entry service, keep the caller handler response/status defect as the leading branch and treat the downstream availability alert as a secondary symptom. When a request contains a valid parameter but a downstream call carries an empty value, suspect handler-side parameter clearing as code_missing_parameter rather than assuming wrong_return. When a downstream callee logs a null/undefined read on a required field and the caller returns HTTP 500, treat this as a caller sending a nil/empty required field and keep code_missing_parameter as the leading branch unless source shows valid, non-emptied inputs reaching a defective return/error branch.

Next: triage_request_source

### Step: triage_request_source
Goal: Locate and inspect the likely code owner's relevant request-handling and request-construction source files once before selecting missing-parameter, wrong-argument-order, or wrong-return confirmation. Inspect the handler's local return/error branch separately from outgoing request construction. If the handler extracts a valid path/query/body value and then, before any outgoing request, resets or clears it and immediately selects a local 400 'not specified' branch, treat this as code_wrong_return: the defect is the erroneous local return/error branch, not an absent downstream parameter. If instead the handler clears, omits, resets, or assigns nil/empty/default to the value while building an outgoing RPC/HTTP request and the callee receives an empty or nil required field, keep code_missing_parameter. Do not classify from the error message alone; a message saying 'not specified', 'no product with ID', or a downstream empty-ID RPC can be emitted after the handler extracts a present path value and then either clears it locally or clears it before a downstream call, with different root causes. If source shows a valid request parameter is extracted and handler-side logic then clears, resets, assigns an empty string/nil, or replaces it with a default before a downstream request, keep code_missing_parameter as the leading branch when the downstream receives that empty value. Keep code_wrong_return for the case where the extracted parameter or otherwise valid input remains present to the handler and a defective return statement, inverted guard, wrong error branch, local rejection path, or wrong response construction rejects or misreports it, including a handler that clears the value and then returns a local 400 absent-parameter message without a downstream empty-field failure.

### Step: confirm_missing_parameter_code
Goal: Confirm code_missing_parameter when required request data is made absent before a downstream use: omitted from the incoming request, extraction returns no value, or the value is assigned nil, overwritten with an empty string, replaced by an empty/default value, or cleared before building an outgoing RPC/HTTP request so the downstream receives a nil/empty required field. This includes code such as currency = '', productID = '', or money = nil when the empty or nil value propagates into a downstream request, error response caused by that downstream empty value, NotFound, or 'no product with ID '. It also includes values not sourced from the request path: a handler that assigns nil/empty/default to an internal value and then passes it into a required field of an outgoing RPC/HTTP request, so the downstream receives a nil/empty required field and returns a null/undefined read error. Do not confirm missing parameter merely because the handler emits an error message such as 'id not specified' or because a local variable was emptied. If the incoming path, query, or body contains a valid value and the handler extracts it but then, without sending it downstream as an empty required field, uses a defective local error branch to return HTTP 400 or 500, reject code_missing_parameter and use confirm_wrong_return_code. Likewise, if a downstream callee reports 'Cannot read properties of null' or 'Cannot use in operator ...' and caller source shows a nil/empty assignment feeding the outgoing request field, confirm code_missing_parameter and reject code_wrong_return. Require an actual swap of existing meaningful values before considering wrong argument order.

### Step: confirm_wrong_argument_order_code
Goal: Confirm code_wrong_argument_order only when two or more existing meaningful values are supplied to the wrong parameter or request-field positions, such as value A being passed where B belongs and value B where A belongs. A value merely cleared, omitted, nil, empty, or defaulted is code_missing_parameter when it is sent downstream as an empty required field; a local defective error branch that rejects a valid extracted value is code_wrong_return.

### Step: confirm_wrong_return_code
Goal: Confirm code_wrong_return when valid, non-absent request input reaches the function or handler but the function returns an error, wrong status, or wrong response object because of a defective return statement, response construction, status or error-branch selection, inverted guard, unconditional error return, or a local handler path that rejects or misreports valid input. This includes the local-error-branch pattern where a handler extracts a valid path/query/body parameter such as /product/0PUK6V6EV0, then through handler-side logic resets, clears, or ignores the extracted value and returns HTTP 400 with 'product id not specified' without any downstream request receiving an empty required field. In that pattern the handler had valid input and wrongly reported it absent; confirm code_wrong_return and reject code_missing_parameter. However, if the handler clears, omits, or assigns nil/empty/default to a value that is then sent as a required field of an outgoing RPC/HTTP request and the downstream callee receives the empty/nil field, such as money = nil then From: money causing a null/undefined read error, use confirm_missing_parameter_code instead. If request data is genuinely absent before handler use, use confirm_missing_parameter_code; if existing meaningful values are swapped, use confirm_wrong_argument_order_code.
