# SOP: service_latency_or_io_degradation

Symptom: An application service shows sustained response latency, throughput degradation, or abnormal filesystem-I/O activity.

Signals:
- application service has severe latency or slow response
- service latency degradation is reported
- downstream timeout appears in service logs
- FILESYSTEM_WRITE_SURGE or abnormal fs_write_bytes is reported
- filesystem-write surge co-occurs with CPU elevation or HTTP 503s
- request-path code creates or writes a file per request
- request-path code repeatedly opens and reads the same file per request, such as productcatalogservice ListProducts reading /src/log.csv 15 times per request
- healthy pods with severe fixed-duration latency and no application error logs
- shared downstream service and its callers show latency matching a fixed request-path delay
- Node.js or JavaScript service logs show business logic completing quickly while the RPC response is delayed
- a gRPC or HTTP handler defers its response with setTimeout, Promise-wrapped setTimeout, or a delayed callback after the business logic
- a leaf service handlers log received/completed within microseconds while its p90 latency is seconds and its upstream callers are slow
- shippingservice GetQuote p90 latency rises to seconds while ShipOrder and GetQuote business logs complete instantly
- checkoutservice PlaceOrder latency rises to seconds while checkoutservice logs show successful payment and email and no application error logs
- a retrieved shippingservice quote.go excerpt ends at the Quote struct before CreateQuoteFromCount or CreateQuoteFromFloat bodies
- an agent claims a checkoutservice getUserCart time.Sleep without that call appearing in the retrieved checkoutservice source
- the only helper source retrieved is a truncated excerpt that ends before the request-path helper functions
- productcatalogservice latency rises to roughly seconds while pods are Running and startup logs are clean
- productcatalogservice ListProducts source contains a fixed-count repeated read of /src/log.csv while EXTRA_LATENCY is unset or zero
- deployment YAML does not set EXTRA_LATENCY so a time.Sleep(extraLatency) hook is dormant

Start at: locate_service_latency_io_scope

## Steps

### Step: locate_service_latency_io_scope
Goal: Identify the service and pods affected by observable latency degradation or filesystem-I/O anomaly without assigning network or code ownership.
Actions:

Next: inspect_latency_io_service_context

### Step: inspect_latency_io_service_context
Goal: Inspect the latency- or I/O-affected service pod health, logs, dependency context, and relevant configuration once to distinguish pod-network delay, artificial delay, file I/O code patterns, and ordinary application failure. When a filesystem-write surge co-occurs with CPU saturation or HTTP 503s, keep request-path file writing as a leading candidate even if pods are healthy and some request logs still show successful responses. When healthy pods show severe fixed-duration latency and a shared downstream service plus its callers are affected, keep a request-path fixed sleep or delay as a leading code candidate. When a Node.js service logs successful fast business processing but the observed RPC latency is seconds, keep an asynchronous response-path timer such as setTimeout in the server handler as a leading candidate; fast business logs do not prove network delay. When a leaf service handlers log received/completed within microseconds but its p90 latency is seconds, keep request-path CPU or file work, including a per-request temp-file write in a quote/pricing helper, as a leading candidate and do not treat no downstream as evidence of a network fault. When checkoutservice PlaceOrder shows severe latency with healthy pods, successful payment and email logs, and no error logs, keep shippingservice GetQuote per-request file-write work as a leading candidate. A checkoutservice getUserCart time.Sleep is not established unless the retrieved checkoutservice source visibly contains it; do not accept a summary claim when the source excerpt ends at imports. When productcatalogservice shows severe latency with Running pods, clean startup logs, and no application errors, keep repeated request-path file reads in ListProducts as a leading candidate; a time.Sleep(extraLatency) hook is not an active artificial delay when the deployment does not set EXTRA_LATENCY or the parsed duration is zero.

### Step: triage_performance_source
Goal: Locate the affected service relevant source files and inspect the primary candidate code once before selecting a specific artificial-delay, busy-loop, excessive-read, or excessive-write confirmation. When a filesystem-write surge is present, look specifically for request handlers that create temporary files, serialize or export CSV or JSON, or write large batches such as tens of thousands of rows on the request path; this file-write-heavy work can also raise CPU and cause latency or 503 responses. When latency is severe, fixed-duration, and pods are healthy, inspect request-handler, helper, and RPC server files as well as main.go for an explicit blocking sleep, active spin-wait, asynchronous response deferral, or repeated file read. In Node.js or JavaScript services, check for setTimeout, setTimeout wrapped in a Promise, await new Promise(resolve => setTimeout(resolve, ms)), and response callbacks invoked after a timer delay. Do not assume main.go contains the delay and do not stop at blocking-sleep checks for a JavaScript service. When the service is a leaf whose business logs complete instantly, do not stop after main.go plus a partial helper excerpt: fully retrieve the quote/pricing and other request-path helper files, including lower portions of the file beyond the type definitions, and look for per-request temp-file creation or bulk row writes such as shippingservice quote.go where CreateQuoteFromCount -> CreateQuoteFromFloat creates /tmp/tmp.csv and writes 30000 CSV rows on every GetQuote call. A source response that ends before the helper functions is not evidence that no code defect exists. When productcatalogservice latency is the symptom, inspect product_catalog.go and server.go fully enough to locate request-path ListProducts work; a fixed-count loop that opens and ReadAll-s /src/log.csv many times per request is an excessive-file-read candidate even when the count is bounded. Read deployment YAML at the same time: if EXTRA_LATENCY is absent or empty, treat a time.Sleep(extraLatency) hook as dormant and do not present code_artificial_delay as a top prediction when repeated reads explain the latency. When checkoutservice PlaceOrder latency is the symptom and checkoutservice calls shippingservice, retrieve the full shippingservice quote.go body and do not treat a truncated excerpt ending at the Quote struct as clean. If checkoutservice source is retrieved only through its imports, do not treat an unsupported getUserCart time.Sleep claim as a confirmed artificial delay.

### Step: confirm_artificial_delay_code
Goal: Confirm code_artificial_delay only when an explicit delay operation is active with a meaningful non-zero duration on the failing request path. This includes blocking delays such as Go time.Sleep and non-blocking asynchronous delays such as JavaScript setTimeout, Promise-wrapped setTimeout, await new Promise(resolve => setTimeout(resolve, ms)), setInterval, or a response callback invoked only after a timer. A dormant, zero-valued, or unreachable delay hook is insufficient. Inspect the request-handler or helper file and the RPC server handler identified during source triage, not only main.go; a fixed sleep or timer in a handler or helper such as productcatalogservice ListProducts or a paymentservice Charge RPC callback is a valid artificial-delay site only when the delay is actually active. In a Node.js gRPC service, a setTimeout that defers callback(null, response) after charge.js has already logged successful business processing is code_artificial_delay even though the business logs are fast and the event loop is not blocked. Corroborate that the delay duration matches the observed p50 or p90 latency and that the delay is on the failing execution path. Active spin or busy-wait code remains code_busy_loop even if a sleep expression also exists; a plain blocking sleep that does not consume CPU is code_artificial_delay. Finding no sleep in main.go or in a partially retrieved helper file does not establish that no request-path delay or file-work exists; complete the helper inspection before excluding code. A code_artificial_delay confirmation for checkoutservice PlaceOrder requires the retrieved checkoutservice source to visibly contain a sleep or timer on that path. An unverified statement that getUserCart contains time.Sleep, while the retrieved source ends at imports, is insufficient. Before confirming checkoutservice artificial delay, fully retrieve shippingservice quote.go and rule out its per-request file-write latency when checkoutservice only calls shippingservice GetQuote and logs downstream success. For productcatalogservice ListProducts, a time.Sleep(extraLatency) hook is dormant and must not be confirmed as code_artificial_delay when EXTRA_LATENCY is absent, empty, or parses to zero; if repeated /src/log.csv reads are present and explain the observed latency, use confirm_excessive_file_reads_code and do not keep code_artificial_delay as a competing top prediction.

- GetAppYAML(app_name=<service_name>)

### Step: confirm_busy_loop_code
Goal: Confirm code_busy_loop when an active CPU-intensive loop or busy-wait explains the observed CPU saturation or latency. Concrete active-spin evidence remains a busy loop even if the same path also contains a sleep expression; a genuinely blocking delay without active spinning belongs to code_artificial_delay. Do not use this branch merely because CPU is elevated when the concrete CPU-consuming mechanism is writing or serializing a large per-request file, or when the concrete mechanism is repeated request-path file reads such as productcatalogservice ListProducts reading /src/log.csv 15 times per request; use confirm_excessive_file_reads_code or confirm_excessive_file_writes_code instead.

### Step: confirm_excessive_file_reads_code
Goal: Confirm code_excessive_file_reads when retrieved source shows a repeated or unbounded request-path file-read path whose allocated, parsed, or retained data explains the observed latency, filesystem-I/O anomaly, CPU saturation, throttling, or throughput degradation after resource configuration is not independently explanatory. A fixed large or repeated per-request read is sufficient when source and latency or I/O evidence align; do not require unbounded growth. This includes productcatalogservice ListProducts opening and reading /src/log.csv 15 times per request, even when the function also contains a dormant time.Sleep(extraLatency) whose environment variable is unset. Once repeated request-path file reads are confirmed as the concrete mechanism, conclude code_excessive_file_reads as the single leading root cause and do not present code_artificial_delay, code_busy_loop, pod_cpu_overload, or pod_network_delay as competing top predictions for the same incident. Downstream frontend errors, recommendationservice latency, and productcatalogservice restarts are secondary when the file-read site and latency evidence align. When the concrete mechanism is creating or writing a file rather than reading it, use confirm_excessive_file_writes_code.

### Step: confirm_excessive_file_writes_code
Goal: Confirm code_excessive_file_writes when retrieved source shows repeated, unbounded, or large per-request file writes that explain the observed FILESYSTEM_WRITE_SURGE or abnormal fs_write_bytes and may also explain CPU elevation, latency, throughput collapse, or 503s. This includes request-path code that creates a temporary file and writes tens of thousands of rows per request before flushing or deleting it, such as shippingservice quote.go where CreateQuoteFromCount -> CreateQuoteFromFloat creates /tmp/tmp.csv and writes 30000 CSV rows on every GetQuote call. Do not require unbounded growth: a fixed large write repeated by request traffic is sufficient when the source and write-surge evidence align. Do not require a latency-dominant or timeout-bearing symptom, and do not treat instant received/completed business logs or a healthy 2/2 pod with zero restarts as evidence against this branch; a per-request bulk write site plus file-work-scaled latency on a leaf service is enough. When file creation or bulk serialization is the concrete mechanism, classify code_excessive_file_writes rather than code_busy_loop even if CPU rises as a side effect of the file work. If the source shows repeated reads rather than writes, use confirm_excessive_file_reads_code instead. When the affected service is a leaf with no downstream callee whose handlers log completion in microseconds yet clients see seconds of latency, this branch is preferred over pod_network_delay, and pod_network_delay must not be concluded until the quote/pricing helper file has been retrieved in full and its write site excluded; a partial excerpt ending at the Quote struct does not satisfy that exclusion. For checkoutservice PlaceOrder latency with healthy pods and successful downstream logs, a truncated shippingservice quote.go response that ends at the Quote struct is not an exclusion. Re-retrieve the lower portion with CreateQuoteFromCount and CreateQuoteFromFloat and confirm the per-request /tmp/tmp.csv 30000-row write site before accepting any checkoutservice artificial-delay conclusion. Inspect quote/pricing helpers reachable from the hot RPC, not only main.go.

### Step: attribute_pod_network_delay_after_code_exclusion
Goal: Attribute remaining service latency to pod_network_delay only after source inspection has explicitly excluded blocking sleeps, non-blocking asynchronous response-path delays, repeated request-path file reads, and per-request or bulk file writes, and after positive pod-level network evidence has been collected. A leaf service and fast business logs are not sufficient by themselves; they are expected when a request-path temp-file write or repeated file read inflates latency while the handler logging stays instant. The exclusion is not complete until quote, pricing, and other request-path helper files have been retrieved in full, including sections below type definitions; a helper source that cuts off before its functions leaves code_excessive_file_writes open and pod_network_delay unconfirmed. For productcatalogservice latency, a ListProducts loop that opens and reads /src/log.csv many times per request is a code_excessive_file_reads mechanism; pod_network_delay must not be concluded or retained as a competing top prediction once that source site and latency evidence align. If the only exclusion evidence is an unverified checkoutservice time.Sleep or a truncated shippingservice quote.go, pod_network_delay is not confirmed and code_excessive_file_writes remains open. Compare co-located pods and services on the same node to rule out node_network_delay; if only absence of a code defect is available and no positive pod-level network evidence exists, report pod_network_delay as unconfirmed rather than concluding it.
