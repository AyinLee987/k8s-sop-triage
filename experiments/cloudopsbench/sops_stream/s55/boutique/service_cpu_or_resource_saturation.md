# SOP: service_cpu_or_resource_saturation
Symptom: An application service or downstream backend datastore shows sustained CPU saturation or throttling with associated performance degradation, including request-path spin-wait, repeated file reads, bulk per-request file writes, or a datastore such as redis-cart throttling while its callers show latency. This includes frontend CPU saturation co-occurring with a filesystem-write surge while home-page and product-detail requests return HTTP 503 and all pods remain Running and Ready with no application error logs. This also includes productcatalogservice CPU CFS throttling and latency degradation while pods are Running and Ready with no application errors, caused by ListProducts repeatedly reading /src/log.csv per request. This also includes productcatalogservice CPU saturation and a filesystem-write surge while pods are Running and Ready, where a product_catalog.go excerpt ends at imports and does not show a write site; the known productcatalogservice request-path defect is repeated /src/log.csv reads in ListProducts, not a 30,000-row temp CSV write.

Signals:
- service has CPU throttling alert
- application service has CPU saturation
- pod CPU usage or throttling is abnormally high
- service performance degradation is dominated by CPU pressure
- reported symptom is a generic service performance degradation while the alert shows CPU saturation plus a filesystem-write surge on the same healthy service
- source code repeatedly reads or parses files on the request path and produces CPU-heavy work
- request-path code repeatedly opens and reads the same file per request despite healthy pods and a normal CPU limit
- request-path helper or ad-selection code spins/busy-waits until a fixed elapsed duration before returning
- request-path order or PlaceOrder code busy-waits until a fixed elapsed duration such as 500ms before returning
- checkoutservice PlaceOrder repeatedly opens and ReadAll-s /src/log.csv ten times per request while checkoutservice shows CPU saturation, CFS throttling, and p50 or p90 latency in seconds
- checkoutservice CPU saturation and severe latency coexist with a 200m CPU limit, healthy pods, no restarts, and essentially clean error logs
- p50 latency rises to roughly the fixed request-path spin duration while CPU CFS throttling also rises
- frontend/home-product latency and downstream DeadlineExceeded logs accompany caller CPU throttling
- frontend CPU throttling and latency degradation accompany downstream adservice DeadlineExceeded warnings
- frontend request handler setCurrencyHandler opens and ReadAll-s /src/log.csv ten times per request
- request-path currency or handler helper repeatedly reads /src/log.csv a fixed number of times per request
- FILESYSTEM_WRITE_SURGE or abnormal fs_write_bytes co-occurs with service CPU saturation or throttling
- request-path code creates a temporary file or writes a large batch such as tens of thousands of rows per request
- request-path quote or helper code creates a temporary CSV and writes a large fixed row count such as 30000 rows on every quote request
- CPU saturation and a filesystem-write surge appear on the same healthy service with no application error logs and fast per-request completion logs
- request-path code repeatedly opens and ReadAll-s the same file such as /src/log.csv a fixed number of times per request
- productcatalogservice shows CPU saturation or CFS throttling with p95 latency increase while pods are Running and Ready and no application errors
- productcatalogservice ListProducts source contains a fixed-count loop that opens and ReadAll-s /src/log.csv 15 times per request
- productcatalogservice product_catalog.go or server.go source excerpt ends at imports or package before the ListProducts body, so a repeated-read exclusion is unsupported
- productcatalogservice shows CPU saturation and FILESYSTEM_WRITE_SURGE while pods are Running and Ready
- product_catalog.go source excerpt ends at imports or package and does not contain ListProducts
- a conclusion claims productcatalogservice ListProducts creates /tmp/tmp.csv and writes 30000 CSV rows even though the retrieved excerpt ends at imports
- productcatalogservice known request-path code repeatedly opens and ReadAll-s /src/log.csv in ListProducts
- productcatalogservice filesystem-write surge must not be attributed to code_excessive_file_writes without a full ListProducts body showing a write
- frontend shows RESOURCE_SATURATION [cpu] plus FILESYSTEM_WRITE_SURGE [fs_write_bytes] while Browse home page and View product detail return HTTP 503 and all pods are 2/2 Running with zero restarts and no frontend error logs
- frontend handlers.go chooseAd creates /tmp/tmp.csv and writes 30000 CSV rows on every home page or product-detail request before flushing and deleting it
- frontend per-request temp CSV write co-occurs with frontend fs_write_bytes peak in the hundreds of KB/s and no application error logs
- latency degradation appears across a dependency chain (cartservice, checkoutservice, frontend) while only a downstream datastore such as redis-cart shows CPU increase and CPU CFS throttling
- redis-cart CPU throttling is observed together with cartservice, checkoutservice, and frontend p95 latency increases and healthy application pods
- all application pods are Running and Ready with no application errors while a backend datastore pod shows CPU saturation
- downstream datastore CPU throttling co-occurs with upstream caller latency and no application error logs

Start at: locate_service_cpu_scope

## Steps

### Step: locate_service_cpu_scope
Goal: Identify the service or backend datastore and pods affected by observable CPU throttling or CPU saturation, and note the surrounding latency chain, without assigning resource-limit or code ownership. For productcatalogservice, record CPU CFS throttling, p95 latency increase, and any filesystem-write surge while noting that pods are Running and Ready and logs have no application errors; the known request-path code defect is repeated /src/log.csv reads, and a filesystem-write surge alone does not establish a productcatalogservice write site.

### Step: inspect_cpu_service_context
Goal: Inspect the CPU-affected component pod health, application logs, and resource configuration once to distinguish CPU-limit pressure, code-driven CPU usage, and ordinary application failure. A configured CPU limit together with cpu_cfs throttling proves quota pressure only; it does not establish that the limit configuration or pod_cpu_overload is the root cause, because code-driven demand such as a busy loop, repeated file reads, or bulk per-request file writes can produce the same evidence. A simultaneous CPU rise plus latency degradation with a normal limit and no application errors is a strong signal to inspect source. A fixed-duration request-path busy-wait that raises p50 latency to roughly the spin duration, with healthy pods, no application errors, and a normal CPU limit, is a code-driven CPU-demand signal; proceed to source triage rather than attributing it to pod_cpu_overload. A fixed count of repeated file reads, such as opening and ReadAll-ing the same file ten times per request, is sufficient source-level demand evidence; do not require an unbounded read or an extremely small CPU limit. For checkoutservice, when CPU saturation and CFS throttling coexist with multi-second p50 or p90 latency, a 200m CPU limit, healthy pods, no restarts, and essentially clean error logs, proceed to request-path source triage for repeated file reads or spin work; do not attribute the incident to pod_cpu_overload before source inspection. When CPU saturation co-occurs with a filesystem-write surge, treat request-path file creation or bulk writes as a leading code-level CPU-demand candidate and do not attribute the issue to pod_cpu_overload before source inspection; a generic performance-degradation symptom with fast request-completion logs does not make this a latency or network case. When the filesystem-write surge is on frontend and home-page or product-detail requests return HTTP 503 while every frontend pod is Running and Ready with zero restarts and no error logs, keep a frontend request-path temp-file create/bulk-write site (for example chooseAd writing a large CSV batch per request) as the leading candidate and inspect frontend handlers.go before any overload attribution. When downstream timeout or DeadlineExceeded logs appear alongside the caller own CPU throttling and latency, do not attribute the symptom to the downstream callee until the caller request-path source is inspected for active spin-wait or file work; downstream timeouts can be secondary. When frontend logs show adservice DeadlineExceeded alongside frontend CPU throttling and high latency, keep frontend request-path file work as the leading candidate and treat the adservice timeout as secondary until frontend handlers are inspected. When the CPU-throttled component is a downstream backend datastore such as redis-cart (for example a Redis pod) whose application callers (cartservice, checkoutservice, frontend) show matching latency, and all application pods are healthy with no application errors, treat the datastore CPU saturation as the leading root-cause candidate and do not force application-source triage on the datastore. Read the datastore Deployment to record its CPU requests/limits and confirm whether demand is at or above an ordinary finite limit (genuine overload) versus an anomalously tiny limit. Do not promote an upstream caller pod_cpu_overload when that caller shows no CPU anomaly, and do not promote node_network_delay without node-aligned retransmission or latency evidence. For productcatalogservice, when CPU saturation and CFS throttling coexist with p95 latency increase, healthy Running pods, no restarts, and no application errors, proceed to source triage of product_catalog.go and server.go; do not attribute the incident to pod_cpu_overload before the ListProducts body is retrieved and inspected. A product_catalog.go or server.go excerpt that ends at imports or package is not evidence of a productcatalogservice write site; do not claim ListProducts creates /tmp/tmp.csv or writes 30000 rows unless that code is visibly retrieved. If productcatalogservice CPU saturation or filesystem-write surge co-occurs with only an imports-only source excerpt, retrieve the full product_catalog.go and server.go and keep repeated /src/log.csv reads as the leading known candidate; report the root cause as unconfirmed if the body is unavailable.

### Step: triage_performance_source
Goal: Locate the affected service relevant source files and inspect the primary candidate code once before selecting a specific busy-loop, excessive-read, excessive-write, or observed-overload conclusion. When the CPU-affected component is a downstream datastore such as redis-cart with no application source path, skip source triage and proceed to confirm_datastore_cpu_overload; do not attempt code inspection of the datastore. When the component is an application service, look for CPU-consuming constructs on the request path, including active-spin busy-waits that check an elapsed-time condition and repeated or unbounded file reads. A per-request loop that opens and ReadAll-s the same log file multiple times, such as /src/log.csv ten times in PlaceOrder or frontend setCurrencyHandler, is a repeated-file-read candidate even when the count is fixed and not unbounded. For checkoutservice, inspect main.go PlaceOrder for a fixed-count loop that opens and ReadAll-s /src/log.csv ten times per request; classify this as a repeated-file-read candidate, not as a busy-loop candidate merely because it is written as a loop. When CPU saturation co-occurs with a filesystem-write surge, also inspect request handlers that create temporary files, serialize or export CSV/JSON, or write large batches such as tens of thousands of rows on the request path; inspect quote, pricing, ad-selection, and helper files used by the hot RPC as well as main.go, since a helper reached from a handler can be the file-writing site. For frontend, open handlers.go and read the ad-selection / home-page handler body that constructs the response; a per-request temp file such as /tmp/tmp.csv written with a large fixed row count (for example 30000 CSV rows) is an excessive-file-write site. A retrieved handlers.go excerpt that stops at the import block or otherwise ends before the handler functions is not evidence that no write site exists and must not be used to confirm or exclude a frontend write defect; retrieve the body containing the write loop. Inspect ad-selection, helper, request-handler, order, and PlaceOrder files as well as main.go; a loop that checks elapsed time until a fixed interval such as 500ms or 800ms is an active spin-wait candidate. A handler that opens and reads the same file a fixed number of times per request is a repeated-file-read candidate even when the count is not unbounded. A handler that creates and writes a large per-request file is an excessive-file-write candidate even when the writes are bounded. In frontend, inspect handlers.go rather than only main.go; setCurrencyHandler opening and ReadAll-ing /src/log.csv ten times per request is a repeated-file-read candidate, while chooseAd creating /tmp/tmp.csv and writing 30000 CSV rows per home or product request is an excessive-file-write candidate that explains the fs_write_bytes surge, CPU throttling, and 503s while pods remain healthy. For productcatalogservice, retrieve product_catalog.go and server.go fully enough to locate ListProducts. A fixed-count loop that opens and ReadAll-s /src/log.csv 15 times per request is a code_excessive_file_reads candidate even when the count is bounded. A product_catalog.go or server.go excerpt that ends at imports or package, or otherwise ends before ListProducts, is not evidence that no repeated-read defect exists; retrieve the full function body before excluding code_excessive_file_reads or attributing the incident to pod_cpu_overload. A productcatalogservice excerpt ending at imports is also not evidence of a write site; do not confirm code_excessive_file_writes or claim ListProducts creates /tmp/tmp.csv and writes 30000 rows from the alert alone. Only confirm productcatalogservice code_excessive_file_writes if the retrieved ListProducts body visibly creates a temp file and writes a large row batch; if the body shows repeated /src/log.csv reads instead, route to confirm_excessive_file_reads_code and do not keep code_excessive_file_writes as a competing top prediction.

### Step: confirm_busy_loop_code
Goal: Confirm code_busy_loop when retrieved source shows an active CPU-consuming loop or busy-wait on the request path, including a loop that repeatedly spins or checks an elapsed-time condition (for example chooseAd spinning until about 800ms have passed or checkoutservice PlaceOrder spinning until about 500ms have passed) instead of blocking, and that explains the observed CPU saturation, CFS throttling, or latency. Active spinning consumes CPU and remains a busy loop even when it is expressed via a duration or timeout or accompanied by a sleep expression. A genuinely blocking wait such as a plain time.Sleep that does not consume CPU is not a CPU-saturation cause and must not be classified here; treat that as an artificial delay under the latency or IO degradation SOP instead. A checkoutservice PlaceOrder loop such as for { if time.Since(start) > 500*time.Millisecond { break } } is an active spin-wait and must be confirmed as code_busy_loop when CPU throttling and latency align; do not classify it as code_artificial_delay merely because it waits a fixed duration, and once active spinning is confirmed do not present code_artificial_delay or pod_cpu_overload as competing top predictions for the same incident. A fixed-count loop that opens and reads /src/log.csv ten times per request is file-read work, not code_busy_loop; do not confirm code_busy_loop when the concrete CPU-consuming work is repeated file reads. A productcatalogservice ListProducts loop that opens and reads /src/log.csv 15 times per request is file-read work, not code_busy_loop; do not confirm code_busy_loop when that repeated-read site is the concrete CPU-consuming mechanism. A frontend chooseAd that creates /tmp/tmp.csv and writes 30000 CSV rows per request is file-write work, not code_busy_loop; when that write site is the concrete mechanism, do not confirm or rank code_busy_loop. When the concrete CPU-consuming work is repeated file reads or parsing, use confirm_excessive_file_reads_code rather than this branch. When the concrete CPU-consuming work is creating or writing a large per-request file, use confirm_excessive_file_writes_code rather than this branch, and do not retain code_busy_loop as a competing top prediction once that write mechanism is confirmed. Inspect the request-handler or helper file identified during source triage when that is where the spin is located; do not assume the busy loop must be in main.go. Downstream DeadlineExceeded or timeout logs are secondary when the caller source contains an active request-path spin and should not cause reattribution to pod_cpu_overload or code_artificial_delay. Corroborate the confirmation with the observed CPU rise and CPU-CFS throttling and with the loop sitting on the failing execution path. If the concrete mechanism is repeated file reads such as frontend setCurrencyHandler reading /src/log.csv ten times per request, checkoutservice PlaceOrder reading /src/log.csv ten times per request, or productcatalogservice ListProducts reading /src/log.csv 15 times per request, do not confirm code_busy_loop. This branch does not apply to a source-less backend datastore; use confirm_datastore_cpu_overload for that case.

### Step: confirm_excessive_file_reads_code

### Step: confirm_excessive_file_writes_code
Goal: Confirm code_excessive_file_writes when retrieved source shows repeated, unbounded, or large per-request file writes that explain the observed CPU saturation, CFS throttling, filesystem-write surge, or latency after resource configuration is not independently explanatory. When file creation or bulk serialization is the concrete mechanism, classify code_excessive_file_writes as the single leading root cause and do not retain code_busy_loop or pod_cpu_overload as competing top predictions: the CPU rise, CFS throttling, and 503s are side effects of the file work, and busy-loop attribution would need its own active-spin evidence. Do not list pod_cpu_overload or code_busy_loop at rank 2 or rank 3 after the write site is confirmed; the top prediction list must be code_excessive_file_writes alone. Inspect quote/pricing and ad-selection helpers reachable from the hot RPC, not only main.go. Do not use this branch for productcatalogservice when the only source retrieved ends at imports. A productcatalogservice ListProducts /tmp/tmp.csv 30000-row write must be visibly present in the retrieved function body before this branch can be confirmed; an alert showing FILESYSTEM_WRITE_SURGE on productcatalogservice is not proof of a write defect. If full productcatalogservice source shows repeated /src/log.csv reads instead, use confirm_excessive_file_reads_code. This branch does not apply to a source-less backend datastore; use confirm_datastore_cpu_overload for that case.
