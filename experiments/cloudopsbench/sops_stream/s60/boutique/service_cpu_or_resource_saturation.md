# SOP: service_cpu_or_resource_saturation
Symptom: An application service or backend datastore shows sustained CPU saturation or throttling with associated performance degradation, including request-path spin-wait, repeated file reads, bulk per-request file writes, or a datastore such as redis-cart throttling while callers show latency. This includes productcatalogservice CPU saturation and FILESYSTEM_WRITE_SURGE while pods are Running and Ready where a product_catalog.go excerpt ends at imports and does not show a write site; the known productcatalogservice request-path defect is repeated /src/log.csv reads in ListProducts, not a 30000-row temp CSV write. It also includes checkoutservice PlaceOrder repeated /src/log.csv reads, frontend money/money.go MultiplySlow busy-loop, frontend handlers.go chooseAd temp-CSV write, and shippingservice quote.go per-request temp-CSV write.

Signals:
- service has CPU throttling alert
- application service has CPU saturation
- pod CPU usage or throttling is abnormally high
- service performance degradation is dominated by CPU pressure
- reported symptom is a generic service performance degradation while the alert shows CPU saturation plus a filesystem-write surge on the same healthy service
- source code repeatedly reads or parses files on the request path and produces CPU-heavy work
- request-path code repeatedly opens and reads the same file per request despite healthy pods and a normal CPU limit
- request-path helper or ad-selection code spins/busy-waits until a fixed elapsed duration before returning
- checkoutservice PlaceOrder repeatedly opens and ReadAll-s /src/log.csv ten times per request while checkoutservice shows CPU saturation, CFS throttling, and p50 or p90 latency in seconds
- checkoutservice CPU saturation and severe latency coexist with a 200m CPU limit, healthy pods, no restarts, and essentially clean error logs
- frontend CPU CFS throttling and p50/p95 latency degradation while frontend pods are Running and Ready and error logs are clean
- frontend money/money.go MultiplySlow contains an active CPU busy-loop or spin on the cart or checkout request path
- frontend CPU throttling and latency degradation accompany downstream adservice DeadlineExceeded warnings
- FILESYSTEM_WRITE_SURGE or abnormal fs_write_bytes co-occurs with service CPU saturation or throttling
- request-path code creates a temporary file or writes a large batch such as tens of thousands of rows per request
- productcatalogservice shows CPU saturation or CFS throttling with p95 latency increase while pods are Running and Ready and no application errors
- productcatalogservice ListProducts source contains a fixed-count loop that opens and ReadAll-s /src/log.csv 15 times per request
- productcatalogservice product_catalog.go or server.go source excerpt ends at imports or package before the ListProducts body, so a repeated-read exclusion is unsupported
- productcatalogservice shows CPU saturation and FILESYSTEM_WRITE_SURGE while pods are Running and Ready
- product_catalog.go source excerpt ends at imports or package and does not contain ListProducts
- a conclusion claims productcatalogservice ListProducts creates /tmp/tmp.csv and writes 30000 CSV rows even though the retrieved excerpt ends at imports
- productcatalogservice filesystem-write surge must not be attributed to code_excessive_file_writes without a full ListProducts body showing a write
- shippingservice GetQuote CPU saturation and CPU CFS throttling with p50 latency around 775-800ms while the pod is Running and Ready with clean logs
- shippingservice quote.go source excerpt ends at the Quote struct before CreateQuoteFromCount or CreateQuoteFromFloat bodies
- frontend CPU CFS throttling and p50/p95 latency degradation while frontend pods are Running and Ready with zero restarts and no application error logs
- a GetSourceCode excerpt for frontend handlers.go, rpc.go, main.go, middleware.go, money/money.go, validator/validator.go, or deployment_details.go ends at imports or package and does not include the function body
- an agent treats imports-only frontend source excerpts as evidence that the frontend request-path code is clean

Start at: locate_service_cpu_scope

### Step: locate_service_cpu_scope

Goal: Inspect the CPU-affected component pod health, application logs, and resource configuration once to distinguish CPU-limit pressure, code-driven CPU usage, and ordinary application failure. ### Step: confirm_busy_loop_code
Goal: Confirm code_busy_loop when retrieved source shows an active CPU-consuming loop or busy-wait on the request path, including a loop that repeatedly spins or checks an elapsed-time condition, and that explains the observed CPU saturation, CFS throttling, or latency. Active spinning consumes CPU and remains a busy loop even when expressed via a duration or timeout or accompanied by a sleep expression. A genuinely blocking wait such as a plain time.Sleep that does not consume CPU is not a CPU-saturation cause and must not be classified here; treat that as an artificial delay under the latency or IO degradation SOP instead. A fixed-count loop that opens and reads /src/log.csv ten times per request is file-read work, not code_busy_loop. A productcatalogservice ListProducts loop that opens and reads /src/log.csv 15 times per request is file-read work, not code_busy_loop; do not confirm code_busy_loop when that repeated-read site is the concrete CPU-consuming mechanism. A frontend chooseAd that creates /tmp/tmp.csv and writes 30000 CSV rows per request is file-write work, not code_busy_loop. For shippingservice, do not confirm code_busy_loop from a quote.go excerpt that ends at the Quote struct; retrieve CreateQuoteFromCount and CreateQuoteFromFloat fully. If the full body shows CreateQuoteFromFloat creating /tmp/tmp.csv and writing 30000 CSV rows per GetQuote, use confirm_excessive_file_writes_code and do not confirm code_busy_loop. If the full body visibly shows an active elapsed-time spin-wait on the GetQuote path, code_busy_loop may be confirmed; even then do not list pod_cpu_overload or code_artificial_delay as competing top predictions. When the concrete CPU-consuming work is repeated file reads or parsing, use confirm_excessive_file_reads_code rather than this branch. When the concrete CPU-consuming work is creating or writing a large per-request file, use confirm_excessive_file_writes_code rather than this branch. Downstream DeadlineExceeded or timeout logs are secondary when the caller source contains an active request-path spin and should not cause reattribution to pod_cpu_overload or code_artificial_delay.

### Step: confirm_datastore_cpu_overload
Goal: Confirm pod_cpu_overload on a downstream backend datastore or infrastructure component, such as redis-cart, that has no application source path, when that component shows sustained CPU saturation and CPU CFS throttling, it sits on the shared request path of callers that show matching latency, and all application pods remain Running and Ready with no application errors. Do not retain an upstream caller pod_cpu_overload or node_network_delay as competing top predictions. Conclude pod_cpu_overload on the datastore as the single leading root cause, with upstream latency as propagation. This branch is not for frontend, productcatalogservice, shippingservice, or any application service with source; use the source branches for those.
