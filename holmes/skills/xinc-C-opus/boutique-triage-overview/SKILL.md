# Online Boutique 排查总则

## 经验条目

以下条目来自过去的排查记录，括号里是来源。

- [E1]（BH01、BH02、BH03、BH07、BH10）【已证实】一个或多个页面报 500，调用方日志出现 connection refused / i/o timeout、failed to <步骤>、rpc Unavailable/Internal，且失败是毫秒级快速返回时：顺着错误链找到第一个失败步骤和它连的地址（ClusterIP:端口对应哪个 Service）；多个页面共用同一下游时，500 会覆盖所有用到它的页面。按三种配置错误核对：1) kubectl get endpoints <svc> 为空：比较 Service selector 与 Pod labels，用 set_service_selector 改回。2) Endpoints 有地址但端口与容器实际监听端口（containerPort、启动日志 listening on）不同：Service targetPort 被改，用 set_service_target_port 改回。3) Endpoints 正常：把调用方 env 中 *_ADDR 端口与 Service port、容器端口比较，对照 last-applied-configuration 和旧 ReplicaSet 模板，用 set_env 改回。被调服务日志正常说明不要改被调服务。验证：500 数和该功能失败数归零。例：支付 selector 被改；结账调用下游端口被改；购物车 targetPort 被改。
- [E2]（BH01、BH08）【已排除】页面耗时与“该页面调用某下游（或其存储）的次数”成严格线性关系，不调该下游的接口仍是毫秒级时，说明该下游每次调用固定多出一段延迟。这时不要仅凭 CPU limit 偏小就判定为 CPU 节流。先比较下游实际吞吐（日志里每秒处理的请求数）与 1/单次延迟：吞吐明显高于串行阻塞能达到的上限，就不是进程内排队。再看新建 Pod 的第一个请求是否就慢：是，则与实例状态、连接状态、负载累积无关。已实测：把被调服务或其存储的 CPU 上限提高数倍（同时重建）后，中位数、高分位、超阈值比例基本不变。这排除了 CPU 配额/节流和重启可解决这两种解释，加 CPU 的改动应回退。例：被调服务与 redis 存储各试过一次。
- [E3]（BH01、BH02、BH03、BH04、BH05、BH06、BH08、BH09）【未解决】按 E2、E4 排除了 CPU、两端 Pod 重建、Endpoints/Service/env 后，每次往返仍固定多出一段延迟，服务端处理瞬时完成，全程无报错时：怀疑 Pod 之外按目的地施加了网络延迟，可能是节点 veth/ifb 上的 tc netem 或 eBPF、按目的端口匹配的规则，或者按 label 给新 Pod 重新注入规则的控制器。判断去程还是回程：在调用方找紧挨该调用之前、中间没有其它 RPC 的日志行（如上一个下游调用返回）作为发出时刻，与被调方入口日志配对；再拿被调方完成日志与调用方下一行配对，得到回程。多组样本都是“晚到、秒回”，就是单向入站延迟。被调方偶发的就绪探针连接超时可作旁证。【已排除】按 ClusterIP 匹配、规则绑在客户端 Pod 上：调用方改为直连 Pod IP 并重建后，耗时不变。缺的证据：新 Pod netns 内和节点上的 tc qdisc/filter（含 ingress、ifb）、iptables/nft 规则、集群级注入对象、抓包；要区分节点规则和重新注入，看新 Pod 内是否刚出现 qdisc。没有 nodes/exec/集群级权限时，立即带逐边耗时表上报运维，不要再改 targetPort、selector、副本数、env 或 CPU。例：汇率服务；redis 命令；运费服务入站。
- [E4]（BH02、BH03、BH04、BH05、BH08）【已排除】慢请求耗时呈固定台阶，台阶数与经过某些目的服务的往返次数成正比，不经过的接口仍是毫秒级，也没有快样本时，重建 Pod 解决不了。判断方法：按请求类型列出对各下游的调用次数，下游还连存储的要数到最底层的往返（如存储命令条数），而不只数 RPC 次数，看耗时差是否等于次数差乘一个固定值。再用不同调用组合的耗时比值，区分“每次往返加一次”和“挂在某一端 Pod 的全部流量上”。把调用方与被调方日志按请求配对，看多出的延迟是否稳定；重建后看新 Pod 是否从第一个请求起就同样慢。已实测：重建被调服务及其存储；重建调用方；一次重建全部受影响的被调服务；先重建一端、再重建另一端（两端名字和 IP 都换了）。用户侧中位数和超阈值比例都不变。这排除了两端 Pod 内的运行时状态、netns 内的规则、按 Pod 名或 IP 一次性下发的规则以及应用配置。出现这种特征时不要再逐个重建做试验：重建窗口会出错，重建有状态存储会清数据。直接转入 E3。例：购物车到 redis 的每条命令；前端与推荐服务；前端、结账服务调用汇率服务。
- [E5]（BH06、BH07、BH09、BH15）【已证实】同时存在快速失败的独立故障（副本为0、Endpoints为空、调用方日志connection refused且毫秒级返回）和另一个主故障时：快速失败的调用不贡献延迟，不要把它当成变慢的原因。调用方若做了降级（页面仍返回200，只记warning），它不会出现在500数里，只能靠调用方日志和Endpoints判断。修复（如副本恢复）后，Endpoints出现地址、调用方的降级warning随即停止，可以拿这两点验证。独立修复和主修复同批提交时，若主修复无效、整批被撤销，独立修复也会被一起还原（managedFields可见回滚时刻被改回）。所以要先单独提交独立修复，或只和把握高、已验证的修复同批。判断独立故障是否还在，看kubectl get endpoints、selector和managedFields，不要只看报错是否消失：已建立的连接可能让日志暂时显示成功。例：邮件服务selector被改，两次随延迟修复同批提交，两次都被撤销；广告服务被缩到0，扩回1后warning停止。
- [E6]（BH10）【未解决】修复后用户侧有好转但失败没有归零（如下单全部成功、500 仍占一部分）时，不能仅凭自己在日志里看到“某时刻之后不再报错”就断定剩余失败是改动生效滞后的尾巴并停止申请操作。先对齐三个时间：用户侧统计窗口的起止、改动提交时刻、调用方日志里最后一条同类错误的时刻。窗口有一部分在提交前或生效前，就要等一个完全落在修复之后的窗口再下结论；若那个窗口仍有 500，按错误内容分组：仍是同一地址被拒，复查 Endpoints/EndpointSlice 端口是否已更新；是别的错误，当成新故障从 E1 重新查。缺的证据：这次没有拿到修复后完整窗口的数据，“滞后尾巴”的解释没有被检验，最终用户侧也没有恢复。例：购物车 targetPort 修复后仍有部分 500。
- [E7]（BH11、BH12、BH13、BH14、BH15）【已排除】间歇性尾延迟：大部分请求毫秒级，一部分多出近似固定量级的延迟（可叠加成整数倍），无500、无重启。先定位停顿在哪一跳：1) 拿调用方不调任何下游的接口做对照，始终不慢只能排除调用方进程自身停顿，不能证明问题在调用方出向网络或某个下游；2) 比较调用和不调用嫌疑下游的页面的慢请求比例，比例相同就排除该下游；3) 调用方与各被调方日志逐请求对齐，同一时间窗每类取几十个以上样本，小样本里出现0次不算证据。耗时呈固定台阶不能证明是CPU节流。已实测：调高嫌疑服务、其存储、调用方的CPU上限，重建嫌疑服务及其存储，重建调用方（换了IP和netns），扩副本，改用ClusterIP跳过DNS，之后慢请求比例和p99都不变，新Pod很快又出现探针超时。这排除了CPU配额、任一端单个Pod或其netns、连接状态、DNS这几种解释，相应改动应回退。重建有状态存储会清数据。与E3/E4的区别：那里每次往返都慢。例：推荐、汇率、购物车及其存储、商品目录都重建过，重建前端同样无效。
- [E8]（BH11、BH12、BH13、BH14、BH15）【未解决】E7的间歇性尾延迟在Pod级改动都被排除后，要区分停顿是节点级的，还是集中在某个目的服务上：1) 不能凭探针超时集中在某个服务、少量慢请求落在它上面就下结论，也不能凭另几条边上少量快样本排除节点级。对所有调用边逐请求对齐，用被调方收包时间分清延迟是在路上还是在处理，再用大样本看停顿是否出现在多条互不相关的边上。2) 看换了实例后探针超时是否仍只出现在该服务、新Pod是否刚创建就超时、其它探针设置相同的服务是否为零。3) 多出的耗时若约为200ms的1/2/4倍，且同一时刻有多个并发请求一起放行，支持丢包后TCP重传，不支持进程卡住或固定延迟。停顿随机落在多条边上，指向节点级丢包、软中断或CPU争用；只集中在一条边且跨实例都如此，指向该服务的入站路径（是按Pod还是按目的端口施加，靠重建区分不了）。缺的证据：节点tc -s qdisc、nstat重传、softnet_stat、/proc/pressure、抓包。没有节点权限时，带逐边对齐表和已排除项上报运维，不要再改CPU、副本、env、selector，也不要再重建Pod。例：停顿多落在商品目录调用上，购物车等边也偶有出现。

## 1. 权限与证据边界

- 只在命名空间 `boutique` 内排查，使用只读权限。
- 可查看：Pod、Pod 日志、事件、Service、EndpointSlice、Deployment、ReplicaSet、ConfigMap、ResourceQuota。
- 不可用：进入容器执行命令、查看节点、查看监控指标；系统没有 CPU、内存、延迟指标。
- 结论必须来自上述可见证据。无法验证的内容写成“先确认……”或“现有权限内无法确认”，不要根据服务名、调用关系或常见经验直接下根因。
- 不要编造日志格式、接口、配置项；日志字段含义先确认。

## 2. 调用关系

- 用户从 `frontend` 进入。
- `loadgenerator` 持续产生访问流量；其具体访问目标先确认，不纳入下列服务调用图，也不假设存在 `boutique-loadgenerator`。
- `frontend` -> `productcatalogservice`、`currencyservice`、`cartservice`、`recommendationservice`、`shippingservice`、`checkoutservice`、`adservice`
- `checkoutservice` -> `productcatalogservice`、`shippingservice`、`paymentservice`、`emailservice`、`currencyservice`、`cartservice`
- `recommendationservice` -> `productcatalogservice`
- `cartservice` -> `redis-cart`
- 不调用其他服务：`emailservice`、`paymentservice`、`productcatalogservice`、`currencyservice`、`shippingservice`、`adservice`、`redis-cart`

调用关系只表示依赖方向，不等于故障传播方向。

## 3. 入口 SOP 选择

先固定用户症状：发生时间、频率、影响的功能/操作、是否持续、是否与 `loadgenerator` 流量相关。不要先假定某个服务故障。

默认规则：

- 用户可见问题且无法明确指向某个后端服务：从 `boutique-frontend` 进入。
- 症状或已有证据明确指向某个服务及其对应操作：可直接进入该服务 SOP；仍要按第 4 节确认证据，不要跳过入口症状。
- 只有 `loadgenerator` 报错：先确认其访问目标和错误内容；若指向 `frontend` 或用户访问路径，从 `boutique-frontend` 进入。不要假设存在 `loadgenerator` 的 SOP。
- 不明确时回退到 `boutique-frontend`。

| 症状/已有证据明确指向 | 入口 skill |
|---|---|
| `frontend` 页面、入口、多个功能同时异常，或无法判断后端 | `boutique-frontend` |
| 商品目录、商品信息 | `boutique-productcatalogservice` |
| 币种、换算 | `boutique-currencyservice` |
| 购物车操作 | `boutique-cartservice` |
| 推荐内容 | `boutique-recommendationservice` |
| 运费、配送 | `boutique-shippingservice` |
| 下单、结账编排 | `boutique-checkoutservice` |
| 支付 | `boutique-paymentservice` |
| 邮件通知 | `boutique-emailservice` |
| 广告 | `boutique-adservice` |
| 已有证据指向购物车存储 `redis-cart`，或从 `cartservice` SOP 转入 | `boutique-redis-cart` |

## 4. 跨服务跳转原则

1. 只沿调用方向向下游跳，且必须带当前服务侧证据。可跳的证据包括：当前服务的日志、事件或状态显示对某个下游的调用失败、超时、连接失败、返回异常，并能定位到具体下游和操作；或当前服务自身已排除，请求路径明确只可能落在下游。仅凭“它是下游”“它也可能异常”不跳。
2. 跳转前记录：时间、当前服务对象、症状、指向下游的证据、已排除项。到下游后先核对同一时间窗、同一症状是否出现；对不上则回到当前服务，不能把无关异常归因给下游。
3. 反向查看调用方，只在当前服务有证据表明请求来源异常、请求内容异常或流量异常时进行；否则停在当前服务。
4. 结论归属：根因结论写在直接证据所在的最小服务上。调用方只写“受影响/依赖疑似异常”，不替下游下结论。若根因是调用方发出异常请求导致下游报错，结论写在调用方。多个服务受影响时，在源头服务写根因，在其他服务写影响并引用源头结论。
5. 停止条件：已定位到最小责任服务并有直接证据；或可见证据均不支持继续；或下一步需要进入容器、查看节点、查看监控指标、访问其他命名空间等无权限操作。停止时写明已排除项、未确认项、所需权限或补充信息，不要猜。

## 5. 多个服务同时异常时判断源头

- 先列出受影响服务、症状和最早异常时间，再按调用图找共同下游或共同依赖。共同依赖只是候选，不是根因。
- 看时序和错误形状：下游先异常、多个上游随后报同类依赖错误，优先查下游；上游先异常且下游日志或事件显示来自上游的异常请求/流量，优先查上游；只是同时异常不能定源。日志字段含义先确认。
- 对候选源头查直接证据：Pod 状态、日志、事件、Service、EndpointSlice、Deployment、ReplicaSet、ConfigMap、ResourceQuota。候选源头自身没有直接异常证据时，不把共同依赖写成源头，回到调用方或入口继续。
- 多个互不依赖分支同时异常：考虑共同入口 `frontend`、共同流量源 `loadgenerator`（先确认其目标和错误）、命名空间级限制如 ResourceQuota 等；仍须有可见证据。无法证明共同原因时，按多个独立故障记录，不要强行归并。
- 若所有下游均无直接异常，而入口持续报依赖错误，停止向下游跳转，回到入口检查其自身可见状态、端点和服务配置；仍无法确认则按权限边界交接。
