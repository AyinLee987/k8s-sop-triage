# Online Boutique 排查总则

## 经验条目

以下条目来自过去的排查记录，括号里是来源。

- [E1]（BH01、BH02、BH03、BH07、BH10）【已证实】调用方连不上某个下游时，Endpoints、端口和地址配置都要核对。适用：调用方日志出现 dial tcp <地址>:<端口> connection refused 或 i/o timeout；或上游返回 Internal/Unavailable，错误文本指出某一步下游调用失败，而该下游自身日志无错误（仍在处理其他请求，或根本没收到请求）。不适用：下游自身日志有报错或处理耗时变大，应改查该下游的负载和它的依赖。做法：(1) 查该 Service 的 Endpoints，subsets 为空时比较 selector 和 Pod labels，并看 replicas 是否为 0；(2) Endpoints 有地址时逐段比较端口链：错误文本端口、调用方 *_ADDR 等地址环境变量、Service port、targetPort 与 Endpoints 端口、containerPort 及下游启动日志里的实际监听端口。错误端口等于 Service port 不代表没问题，targetPort 指向未监听端口同样会立即 refused；连 Service 未暴露的端口可能表现为 i/o timeout，超时也要先核对端口；(3) 拿线上配置与 last-applied-configuration、旧 ReplicaSet 模板比较，看改动时间是否和症状起点吻合。修正后这类报错和对应接口的失败应归零。例：几次分别是 selector 指错标签、调用方地址里的端口错误、Service targetPort 与容器监听端口不一致。
- [E2]（BH01、BH02、BH03、BH04、BH05、BH06、BH08、BH09）【已证实】变慢定位到下游后，按往返次数找到具体一跳，再区分应用内慢和网络路径慢。适用：调用方各接口耗时随调用某些下游（含缓存、数据库等非gRPC依赖）的次数成比例增加，不调它们的接口和健康检查仍然很快。不适用：下游日志里单个请求的处理耗时同样变大，应改查它的CPU节流、负载或它的下游。做法：列出每个接口对每一跳的往返次数，看耗时是否按某一跳次数成固定台阶增长，定位到具体一跳（含二级下游）；按调用方发起时刻、下游入口日志、下游完成日志、调用方拿到响应后的下一条日志逐跳对时，发起到入口间隔大而内部处理和回程都快，说明延迟在应用之外；另一独立调用方同样变慢，说明慢点在下游一侧。随后查该跳两端Pod所在节点的veth tc qdisc和网络策略。没有cfs throttled指标不能下CPU节流结论；无节点权限时只写“网络路径或进程内”并申请节点侧检查。重建Pod、调大CPU limit能否消除仍未验证，几次都是直接清除规则后恢复。例：一次是被调用服务的veth带规则。
- [E3]（BH01、BH03、BH06、BH09、BH14、BH15、CL03）【已排除】多个症状同时出现时，不要默认它们是同一个根因，也不要因为失败调用耗时短就断定报错链路和变慢无关。适用：用户侧或调用方日志同时出现错误或warning级的下游调用失败（connection refused、i/o timeout、Endpoints为空等），又有整体或部分请求变慢。不适用：只有一种症状。做法：按症状分别找证据链；一次只修一处，每步之后分别看错误数、慢请求占比、中位数和各分位数，并确认前后比较窗口的请求量相当。修好报错后延迟分布不变，说明报错链路不是变慢原因，要继续单独追查变慢；延迟部分下降但没有归零，既不能据此排除报错链路的贡献，也不能把它当作主因，要继续查其他来源，修完后看是否归零。调用方日志里立即失败的调用耗时很短，只能作参考，以修复后的分位数为准；去掉延迟来源也不能代替修复报错。例：几次修好端口、selector或副本为0的下游后，慢请求占比不变；一次把副本为0的广告服务恢复后，慢请求占比和p99明显下降但没有归零，恢复另一服务的CPU配额后才归零，前一步下降的原因没有查明。
- [E4]（BH04、CL05）【已证实】多个服务同时显得变慢时，先找最小源头集合，不要把每个变慢的服务都当作根因。适用：调用方日志或逐跳对时显示多个下游的调用耗时同时变大；或某下游被判为变慢但自身CPU、throttled、内存、日志都正常，且它本身还会调用其他下游。不适用：只有一个下游变慢且它不再调用其他服务，按E2处理。做法：(1)对每个变慢的服务，把自身处理时间和等待下游的时间分开算；只是在等下游、自身处理不慢的先标为“继承”，从调用图叶子一侧查源头，修复后看继承的服务是否一起恢复；(2)仅凭某次调用前后的时间差归因不可靠，差值可能包含其他调用；(3)从另一调用方得到的下游“很快”的证据，要按它对该下游的调用次数折算，并和该调用方健康期耗时比较，比健康期明显变长就不能据此排除该下游。例：一次推荐服务被怀疑单次调用变慢，自身资源全部正常，清除其下游商品目录Pod的veth规则后恢复。
- [E5]（BH07、BH10）【已排除】调用方日志里的下游报错或某个下游的配置错误，不一定是用户侧失败的原因，要区分被降级的依赖和致命的必经步骤。适用：调用方日志或配置检查同时发现多个下游有问题（调用报错、Endpoints 为空、端口不一致等），且用户侧有 500 或某个操作失败。不适用：只有一个下游有问题，直接按 E1 处理。做法：把每类下游报错和同一条请求日志的路径、返回状态对应：报错出现时请求仍返回 200 的，是被调用方降级处理的依赖，只影响页面部分内容；报错文本出现在返回 500 的请求里、且属于该操作必经步骤的，才是失败候选。还可看必经步骤之后的下游是否几乎没有来自该调用方的日志，确认流程在哪一步中断。修复时一次只改一处，每步之后分别看 500 数和对应操作失败数：修好降级依赖后两者不变，即排除它对失败的贡献；修好必经步骤后失败归零才算证实。例：两次先恢复没有流量的推荐或广告服务，500 和下单失败都不变；改正必经下游的端口配置后全部恢复。
- [E6]（BH08）【已排除】故障前后出现的手工配置改动不一定是根因，要用时间线和回滚后的数字检验。适用：某Deployment的env与last-applied-configuration不一致，或新ReplicaSet创建时间接近症状开始。不适用：调用方报错文本指向地址或端口，按E1核对。做法：比较新Pod Ready时刻、新Pod上线后第一批请求的耗时和状态、症状起点；新Pod已经正常服务一段时间后症状才出现，说明该改动不是触发点，应继续按症状找证据链，不要停在这个改动上。如果仍要回滚，回滚后分别看错误数和各分位数，都没有变化即排除它。例：一次删掉调用方多出的发布标签环境变量并滚动更新后，慢请求占比和各分位数不变。
- [E7]（BH11、BH12、BH13、BH14、BH15、CL01）【已证实】部分请求变慢时，按“每次调用有一定概率被加上一段固定延迟”定位到具体一跳。适用：用户侧中位数正常、高分位很差；慢请求耗时集中在正常值加某个固定量或其整数倍；不调后端的接口始终很快。不适用：所有请求一起变慢，或下游日志里单个请求处理耗时变大，按E2或查下游负载；某Pod的cfs throttled周期占比明显高于其他Pod时，同样会中位数正常、长尾变差，按CPU限流条目检验。做法：(1)数出每个接口对每个下游的调用次数，含间接调用和二级依赖；(2)优先看只调一个下游的接口；多步请求用相邻下游入口日志时间戳夹出空转区间，某下游日志的空档可能是调用方在等别的下游，对齐入口和完成时间后再归因；(3)只出现在某一个Pod上的kubelet探针连接超时可作佐证，但被CPU限流的Pod也可能出现，要结合throttled指标；(4)查该Pod两端veth的tc qdisc。同时有5xx时报错与长尾分开修分开看（见E3）。例：一次只清除商品目录Pod的veth规则后长尾全部消失。
- [E8]（CL01、CL02、CL03、CL04、CL05）【已证实】请求变慢时，用限流指标、配置历史和恢复配额后的各分位数检验某一跳的CPU限流，并确认它解释了多少延迟。适用：某Pod的cfs throttled周期占比明显高于同命名空间其他Pod，慢请求都经过该服务；常伴随limits.cpu比上一版ReplicaSet模板低、探针超时事件、日志无报错。不适用：各Pod throttled都接近0或差不多，改查网络路径（E2、E7）或下游排队；调用方有连接报错先按E1、E5。做法：(1)平均用量远低于limit也可能被限流，不能据此排除；(2)逐字段diff当前和上一版ReplicaSet模板，核对改动时间与症状起点；(3)这些证据全部吻合，即使它是唯一的配置改动、受限Pod是入口服务，也只说明存在限流，不说明它是主因，被慢接口调用的其他下游要按E9一并列为候选；(4)恢复limit后分别看throttled占比、慢请求占比、中位数和p99：都回到正常才算证实，慢请求占比基本不变说明限流不是主因。例：两次恢复换算服务limit后长尾消失；另有三次（含一次入口服务配额下调且时间吻合）恢复后不变，清除另一下游veth规则后才恢复。
- [E9]（CL02、CL04、CL05）【已排除】慢接口都调用某服务、快接口都不调用，不足以把变慢归给它；同一组接口共同调用的其他下游都是候选，Pod层指标正常、和调用方在同一节点也不能排除其网络路径。适用：按接口比较调用方日志耗时后，慢接口与快接口的调用差别对应不止一个下游（含间接调用和页面附属调用）。不适用：存在只调用其中一个候选的接口，且其耗时已在健康基线水平，能把候选区分开。做法：(1)为每个接口列出全部直接和间接下游，找出与慢接口调用集合重合的所有服务；(2)“快”接口要先和健康期基线比，若它也明显变慢，说明它同样经过慢点，不能当对照，它和慢接口共同调用的下游都要列为候选；(3)对每个候选分别取证：throttled占比、配置历史、探针事件、该Pod两端veth的tc qdisc；CPU低、throttled为0、无事件、丢包为0都不能排除tc延迟；(4)一次只修一个候选，每步看慢请求占比、中位数和p99，不变即排除。例：一次首页比健康期慢一个数量级却被当作快对照，变慢被归给推荐服务，清除两类页面都会调用的商品目录veth规则后全部恢复。
- [E10]（CL06、CL07）【已证实】调用方报下游返回 Unimplemented/Method not found 时，核对请求实际被路由到了哪个服务。适用：调用方或上游错误文本含 rpc error code = Unimplemented（如 Method not found），失败请求立即返回；预期的下游日志里没有对应调用。不适用：报 connection refused、i/o timeout 或 Endpoints 为空，按E1；下游自身日志有报错，改查该下游。做法：(1)从调用方启动日志或 env 取出该下游的 *_ADDR，与预期服务名和端口比较；(2)地址正确时查该 Service 的 selector 和 EndpointSlice 里的 Pod 名，看是否选中了另一个监听同端口服务的 Pod，可与其他 Service 的 EndpointSlice 对比；(3)看预期下游是否完全没有业务请求、被选中的服务日志是否只有它自己的方法；(4)比较当前配置与 last-applied-configuration 或上一版 ReplicaSet 模板，核对改动时间与症状起点；(5)改正后按E11确认各调用方已切到正确后端，再看 500 和对应操作失败数是否归零。Endpoints 都 ready、端口一致不能排除这类错误。例：一次支付地址指向了邮件服务；一次配送 Service 的 selector 选中了支付服务的 Pod。
- [E11]（CL07）【已证实】改正 Service selector、Endpoints 或地址后报错不降，要考虑调用方仍复用指向旧后端的长连接，按调用方逐个重建并分别验证。适用：路由配置已改正，EndpointSlice 已指向正确 Pod，但调用方日志里同一错误文本仍持续出现，500 或对应操作失败数不降；正确后端仍几乎收不到来自这些调用方的请求。不适用：EndpointSlice 仍为空或指向错误 Pod，先按E1、E10改正配置；正确后端已收到请求但自身报错，改查该后端。做法：(1)列出所有直接调用该下游的服务，把每个失败接口对应到实际发起这次调用的一方；(2)一次只重建（或让其重连）一个调用方，每步后分别看它负责的操作失败数和其余 500：只有它负责的那部分归零，说明各调用方各自持有旧连接，要逐个处理；(3)同时看正确后端日志是否开始出现来自该调用方的请求。调用方未重连前，失败不降不能当作配置修正无效的证据。例：一次改正配送 Service 的 selector 后 500 和下单失败都不变，重建结算服务后下单失败归零，再重建前端后 500 归零。

## 1. 权限与证据边界

- 只在命名空间 `boutique` 内排查，使用只读权限。
- 可查看：Pod、Pod 日志、事件、Service、EndpointSlice、Deployment、ReplicaSet、ConfigMap、ResourceQuota。
- 不可用：进入容器执行命令、查看节点、查看监控指标；系统没有 CPU、内存、延迟指标。
- 结论必须来自上述可见证据。无法验证的内容写成“先确认……”或“现有权限内无法确认”，不要根据服务名、调用关系或常见经验直接下根因。
- 不要编造日志格式、接口、配置项；日志字段含义先确认。

## 2. 调用关系

- 用户从 `frontend` 进入。
- `loadgenerator` 持续产生访问流量；其具体访问目标先确认，不纳入下列服务调用图，也不假设存在 `boutique-loadgenerator`。
- `frontend` -> `productcatalogservice`、`currencyservice`、`cartservice`、`recommendationservice`、`shippingservice`、`checkoutservice`、`adservice`
- `checkoutservice` -> `productcatalogservice`、`shippingservice`、`paymentservice`、`emailservice`、`currencyservice`、`cartservice`
- `recommendationservice` -> `productcatalogservice`
- `cartservice` -> `redis-cart`
- 不调用其他服务：`emailservice`、`paymentservice`、`productcatalogservice`、`currencyservice`、`shippingservice`、`adservice`、`redis-cart`

调用关系只表示依赖方向，不等于故障传播方向。

## 3. 入口 SOP 选择

先固定用户症状：发生时间、频率、影响的功能/操作、是否持续、是否与 `loadgenerator` 流量相关。不要先假定某个服务故障。

默认规则：

- 用户可见问题且无法明确指向某个后端服务：从 `boutique-frontend` 进入。
- 症状或已有证据明确指向某个服务及其对应操作：可直接进入该服务 SOP；仍要按第 4 节确认证据，不要跳过入口症状。
- 只有 `loadgenerator` 报错：先确认其访问目标和错误内容；若指向 `frontend` 或用户访问路径，从 `boutique-frontend` 进入。不要假设存在 `loadgenerator` 的 SOP。
- 不明确时回退到 `boutique-frontend`。

| 症状/已有证据明确指向 | 入口 skill |
|---|---|
| `frontend` 页面、入口、多个功能同时异常，或无法判断后端 | `boutique-frontend` |
| 商品目录、商品信息 | `boutique-productcatalogservice` |
| 币种、换算 | `boutique-currencyservice` |
| 购物车操作 | `boutique-cartservice` |
| 推荐内容 | `boutique-recommendationservice` |
| 运费、配送 | `boutique-shippingservice` |
| 下单、结账编排 | `boutique-checkoutservice` |
| 支付 | `boutique-paymentservice` |
| 邮件通知 | `boutique-emailservice` |
| 广告 | `boutique-adservice` |
| 已有证据指向购物车存储 `redis-cart`，或从 `cartservice` SOP 转入 | `boutique-redis-cart` |

## 4. 跨服务跳转原则

1. 只沿调用方向向下游跳，且必须带当前服务侧证据。可跳的证据包括：当前服务的日志、事件或状态显示对某个下游的调用失败、超时、连接失败、返回异常，并能定位到具体下游和操作；或当前服务自身已排除，请求路径明确只可能落在下游。仅凭“它是下游”“它也可能异常”不跳。
2. 跳转前记录：时间、当前服务对象、症状、指向下游的证据、已排除项。到下游后先核对同一时间窗、同一症状是否出现；对不上则回到当前服务，不能把无关异常归因给下游。
3. 反向查看调用方，只在当前服务有证据表明请求来源异常、请求内容异常或流量异常时进行；否则停在当前服务。
4. 结论归属：根因结论写在直接证据所在的最小服务上。调用方只写“受影响/依赖疑似异常”，不替下游下结论。若根因是调用方发出异常请求导致下游报错，结论写在调用方。多个服务受影响时，在源头服务写根因，在其他服务写影响并引用源头结论。
5. 停止条件：已定位到最小责任服务并有直接证据；或可见证据均不支持继续；或下一步需要进入容器、查看节点、查看监控指标、访问其他命名空间等无权限操作。停止时写明已排除项、未确认项、所需权限或补充信息，不要猜。

## 5. 多个服务同时异常时判断源头

- 先列出受影响服务、症状和最早异常时间，再按调用图找共同下游或共同依赖。共同依赖只是候选，不是根因。
- 看时序和错误形状：下游先异常、多个上游随后报同类依赖错误，优先查下游；上游先异常且下游日志或事件显示来自上游的异常请求/流量，优先查上游；只是同时异常不能定源。日志字段含义先确认。
- 对候选源头查直接证据：Pod 状态、日志、事件、Service、EndpointSlice、Deployment、ReplicaSet、ConfigMap、ResourceQuota。候选源头自身没有直接异常证据时，不把共同依赖写成源头，回到调用方或入口继续。
- 多个互不依赖分支同时异常：考虑共同入口 `frontend`、共同流量源 `loadgenerator`（先确认其目标和错误）、命名空间级限制如 ResourceQuota 等；仍须有可见证据。无法证明共同原因时，按多个独立故障记录，不要强行归并。
- 若所有下游均无直接异常，而入口持续报依赖错误，停止向下游跳转，回到入口检查其自身可见状态、端点和服务配置；仍无法确认则按权限边界交接。
