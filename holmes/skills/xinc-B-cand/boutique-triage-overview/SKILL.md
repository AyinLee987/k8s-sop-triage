# Online Boutique 排查总则

## 经验条目

以下条目来自过去的排查记录，括号里是来源。

- [E1]（BH01、BH02、BH03、BH06、BH07、BH10）适用：调用方日志里有指向具体 地址:端口 的连接错误（dial i/o timeout、connection refused、no such host），或错误链底层只是 Internal/Unavailable 的步骤失败，而被调下游自身日志无错、只有启动日志没有请求日志，或已没有 Pod。不适用：错误是下游已应答的业务码（如 InvalidArgument）且下游日志里有对应报错，这时查下游自身日志。做法：1）把报错里的 IP:端口与目标 Service 的 ClusterIP 和 port 比对：端口不在 Service 里，查调用方 *_ADDR，与 last-applied-configuration 注解、旧 ReplicaSet 模板比较；2）端口对得上、Endpoints 有地址仍 connection refused，把 Service targetPort、Endpoints 端口与 containerPort、应用启动日志里的实际监听端口比对；3）Endpoints 为空：Pod 都 Ready 时比对 selector 与 Pod 标签，否则看 replicas 和事件（ScalingReplicaSet、SuccessfulDelete、Killing）；4）逐个 Service 核对 selector 和 targetPort，列出所有 Endpoints 为空或端口不符的，确认问题有几处；5）把变更时间和报错开始时间对照；都一致再查网络策略和目标负载。例：targetPort 与监听端口不一致时调用方毫秒级 connection refused；selector 对不上时被调方只有启动日志。
- [E2]（BH01、BH04、BH08）适用：用户反馈变慢，入口服务日志按 handler 记录了耗时（如 took_ms），并且已知每个 handler 会调用哪些下游。不适用：所有 handler 都一样慢（包括不调用任何下游的 handler 和健康检查），这时查入口服务自身的 CPU/限流、节点或网络。做法：列出每个 handler 的耗时，以及它在每一跳上的调用次数，一直数到最底层（某个 RPC 会发几条存储命令，次数随商品数、购物车件数变化的也要算上）。比较各 handler 耗时增量之间的比例和每一跳调用次数之间的比例：哪一跳对得上，慢的就是哪一跳；只调用依赖 X 的快路径可以把 X 排除。每次调用都多出接近固定的一段、没有一个样本是快的，支持固定延迟；快慢混杂更像丢包重传或排队。多个下游可能同时变慢：把耗时写成“各跳次数×单次增量”之和联立估算；没有单独耗时日志的调用，用调用方相邻两条只夹着这一次调用的日志时间差估算。例：一个 RPC 发两条存储命令的 handler，增量正好是只发一条的两倍。
- [E3]（BH01、BH02、BH03、BH05）适用：已经定位到某个服务的单次调用变慢，但它的日志里没有错误。不适用：它的日志里有超时、重试或下游报错，这时应沿着它的下游继续往下查。做法：1）先确认被调方用来对时的日志打在 handler 入口还是出口；用调用方请求起始（完成时刻减耗时）和被调方入口日志逐条配对，把一次调用拆成到达前、处理（含它调下游）、返回三段；2）增量在到达前且偏移稳定、处理和返回都快，支持入方向网络或接收排队，仍要用 throttled 指标、并发连接数排除 CPU 限流和排队；增量在处理段则查应用自身和它的下游；3）比较不同调用方（不同 Pod）调同一被调方：都变慢说明问题附着在被调方一侧，只有一个调用方慢则查该调用方的出方向；4）增量和网络往返次数成正比且稳定支持网络延迟，与往返无关、波动大或随计算量变更像 CPU 限流或应用问题；5）把变慢开始时间和 Pod 创建/Ready 时间、下游 slowlog 对照；排除不了的解释写进结论，并写清重建 Pod 无效时下一步查什么（节点流量控制规则、网络插件、限流指标）。Pod 刚启动时短暂 connection refused 自己恢复不算根因。例：被调方入口日志比调用方发起稳定晚一段，而它返回后调用方几毫秒即完成。
- [E4]（BH02、BH06）适用：同一时间窗里既有变慢，又有失败请求或调用方日志里的错误（包括用户侧没有 500、只在日志里出现的降级调用失败）。不适用：所有失败都是超时，且失败请求的耗时和慢请求一致，这时可以先按同一条慢链路查。做法：把每类症状分开取证：失败的看错误链最底层那条错误指向哪个服务；慢的按 E2/E3 定位到具体一跳。再检查一个原因能否同时解释两类现象：取失败调用自身的耗时（日志时间差或错误类型，如 connection refused 通常是快速失败、超时则接近超时设置），与 handler 耗时比较；再看已定位慢跳的“调用次数×单次增量”能否解释完 handler 耗时，能解释完说明失败调用不贡献延迟。解释不了就当作几个独立故障，各自给出根因、修复和验证；只在日志里出现的错误也要列为独立问题。例：广告服务无端点只造成快速失败日志，页面变慢完全由另一个服务的单次增量解释。
- [E5]（BH04）适用：按 E2/E3 估算后，有两个及以上服务的单次调用都变慢、增量相近，同一时间窗内另一些服务之间的往返仍然很快，各服务日志无错、配置和 Pod 状态无变化。不适用：只有一个服务变慢（按 E3 查该服务），或所有往返都一样慢（查节点、网络插件、入口自身）。做法：1）列出慢组和快组；2）逐项对比两组 Pod 的节点、标签、注解/sidecar、NetworkPolicy、资源 limits 与 throttled 指标、创建/Ready 时间，以及各节点上的流量控制规则，找只有慢组共有的属性；3）共同属性能解释全部慢组再定为一个根因，否则分别查；4）查不到机制而改用重建 Pod 时，事先写清预期：恢复说明问题附着在 Pod 内，不变则说明来自按标签/节点作用的外部因素，下一步查节点和集群侧策略，不要再重复重启。例：几个服务每次调用都多出相近延迟，另几个服务互调只需几毫秒。
- [E6]（BH08、CL01、CL04）适用：排查中发现某个服务有配置漂移（容器 env、resources 等字段不在 last-applied-configuration 注解里，或 Deployment 的 revision 比上一版新、有新 ReplicaSet、Pod 重建），而症状是变慢或报错。不适用：漂移的字段本身就和报错对得上（例如报错里的地址端口就是被改过的值），这时按 E1 查地址配置。做法：1）拿当前和上一版 ReplicaSet 模板逐字段比较镜像、env、端口、探针、resources 的 limits/requests，列出全部差异。2）对齐新 ReplicaSet 创建和新 Pod Ready 的时间、新 Pod 第一批请求的耗时和结果、症状开始的时间：新 Pod 正常服务一段时间后症状才阶跃式出现，说明变更不是根因，记成独立发现，继续查症状开始那一刻发生了什么；两者重合就把变更列为首要嫌疑。3）差异只在 resources 时，用限流数据和调用次数确认机制（按 E11），不要只凭时间重合下结论。4）结案前按入口 SOP 的调用表，把慢 handler 集合和变更服务的调用集合逐一比对：有慢 handler 根本不调它，说明还有别的慢源，按 E2/E4 另查并单独列出。例：唯一差异是 CPU limit 被调低，但不调该服务的加购也一样慢。
- [E7]（BH09、BH11、BH13）适用：用户反馈变慢（含偶发慢样本），需要根据 Pod 状态、探针事件排除或认定某个服务。不适用：重启次数在增加、Pod 未 Ready 或探针持续失败，这时先按事件和探针失败原因查。做法：1）Ready 只说明探针在 timeoutSeconds 内返回了；把探针超时与按 E2/E3/E8 估算的单次增量比较，增量小于超时，Pod 一直 Ready 不能作为排除依据，要用日志对时和调用次数判断。2）有探针失败时先看探针类型和路径（kubelet 直连的 TCP/HTTP/exec 探针不经过任何调用方）：只有一个 Pod 有失败、其余 Pod 探针为零，支持问题附着在该 Pod 一侧（CPU 限流、进程阻塞或该 Pod 网络路径），而不是节点级普遍丢包；但必须同时有调用次数拟合（E8）或步骤间隔定位支持才能认定它。不调用它的 handler 也有同样慢样本，则只说明它也被同一种间歇阻塞碰到。3）探针 i/o timeout 说明停顿有时超过探针超时，偶发慢样本可能是同一停顿的较短部分。例：只有存储 Pod 的 TCP 探针偶发超时，而所有慢请求都经过它。
- [E8]（BH11、BH12）适用：用户侧中位数正常，只有一部分请求慢且无错误；入口日志按 handler 记录耗时，慢样本集中在某个固定值或其整数倍附近，快样本仍很快。不适用：每次调用都稳定多出一段（按 E2/E3 查），或有超时、报错（按 E4 查）。做法：1）拿不调任何下游的 handler 做对照，它也慢就查入口服务自身。2）对每个候选下游分别按 handler 数出调用它的次数，看慢占比是否符合 1-(1-p)^n：只有某一个下游的次数能拟合全部 handler（调它次数相同的 handler 慢占比也应相近）才定为那一跳，否则说明所有跨 Pod 调用都会被卡。3）用另一个调用方日志里只夹着这些调用的相邻步骤间隔做独立旁证，并看不同调用方的慢样本是否在同一时刻出现，同时出现支持被调方整体停顿。4）分原因：量子与 throttled 计数、负载一起涨支持 CPU 限流（对照 limits）；接近 TCP 重传超时且与负载无关支持丢包，查重传计数；与 GC 日志对齐支持 GC 停顿。5）拿不到指标时把未排除的解释写进结论，修复按对照实验做，一次只改一项、事先写好预期。例：调某下游次数最多的页面慢占比最高，而只调另一下游一次的页面几乎不慢。
- [E9]（BH14）适用：只有部分请求慢、无错误，慢样本集中在某个固定值或其整数倍附近，已按 E8 拟合到某一个被调服务，需要区分丢包重传、CPU 限流和进程停顿。不适用：每次调用都稳定变慢（按 E2/E3 查），或有超时、报错（按 E4 查）。做法：1）看量子大小：与内核 TCP 最小重传超时及其倍数吻合、与负载无关支持丢包，查重传计数；与 CFS 周期相关、随负载和 throttled 计数一起涨支持限流，对照 limits。2）找同一时刻恢复的并发调用：起跑时刻不同的几个请求在同一瞬间一起返回，说明它们共用的连接或被调进程被同一事件解除阻塞；再看等待期间被调方有没有其他日志：仍在正常处理别的请求支持连接级丢包，完全无日志则进程停顿和入方向丢包都没排除。3）看 kubelet 探针失败原因：connect 超时说明建连阶段就没应答，只出现在该 Pod、同节点其他 Pod 探针为零，支持问题附着在该 Pod 的网络路径或进程上。4）拿不到重传和 throttled 指标时把两种解释都写进结论；重建 Pod 前写好预期：恢复支持 Pod 网络命名空间内的问题，不变再按限流调高 limit 验证，不要重复重启。例：慢样本集中在约一个重传超时及其两倍处，两个并发调用同一瞬间返回。
- [E10]（BH15）适用：某个候选服务自己的日志里，相邻两条之间出现一段长空档，有人拿它当作这个服务停顿的证据。不适用：空档期间调用方日志里有对它的调用报超时或错误，这时按 E4 查。做法：日志空档本身只说明这段时间没有打日志，可能只是没有请求进来。把空档的时间窗和所有调用方的日志对齐：如果有调用方在空档内发起了对它的调用，而它直到空档结束后才记下入口或完成，支持它停顿；如果空档内调用方没有发往它的在途调用，或者在途的慢样本已经被别的跳解释掉，就只是空闲，不能把它列为这些慢样本的原因。再看空档和已定位卡点的时刻是否重合。两个候选都无法排除时，修复一次只动一个并写好预期，不要同时重启两者，否则恢复后分不清是哪一个起的作用。例：币种服务日志里有一段几百毫秒的空档，而同一时刻 frontend 正在等另一个下游。
- [E11]（CL01、CL02、CL03、CL04）适用：用户侧变慢但无错误，能拿到各 Pod 的 CPU 限流数据（cgroup cpu.stat 的 nr_periods/nr_throttled 或 throttled 指标）和 CPU limits，或某服务的处理日志时间戳呈固定节拍、成串突发加空档。不适用：调用方日志有超时、连接错误（按 E1/E4 查）；所有 Pod 都没有限流且日志无节拍时，改按 E3/E9 查网络、丢包和应用自身。做法：1）同一时间窗横向比较所有 Pod 的限流周期占比，不要只看平均用量，用量远低于 limit 也可能被限流。2）旁证：调用方有发往它的在途请求时，它的处理日志间隔稳定在 CFS 周期（默认 100ms）的整数倍或成串突发，支持限流；先按 E10 排除只是空闲。3）按 E2/E8 核对：调用它的 handler 都应变慢，且随调用次数增加；有调用它的 handler 从不慢，只记为独立发现；有慢 handler 不调它，说明另有慢源，要单独查。调用表以入口 SOP 为准。4）给慢 handler 共同调用的每个候选找“调它、不调另一个”的 handler 来区分，不能因为另一个候选没有限流就跳过它。5）不要拿限流周期占比直接和慢请求占比比：把占比当作单次调用碰上限流的概率 p，按 handler 调它的次数 n 代入 1-(1-p)^n，算出来远低于慢占比才不能定为根因。6）修复后限流占比和慢样本占比应一起下降，不降就改查其余候选。例：限流周期占比只有一成多，但每个页面要调它近十次。
- [E12]（CL05）适用：入口或调用方服务自身有 CPU 限流（nr_throttled 占比明显高于其他 Pod，或 limits 近期被调低、有新 ReplicaSet），各 handler 变慢幅度不同，要不要把差额按“慢 handler 集合与某下游调用集合吻合”归给那个下游。不适用：该下游有逐跳对时证据（它的入口/完成日志与调用方相邻日志之间的间隔变长），或调用方日志有超时、连接错误，按 E3/E4 查。做法：1）调用方被限流时，单个请求的增量取决于它在调用方进程内的 CPU 工作（反序列化、模板渲染、并发请求数）和排队，处理越重的页面增量越大，不和下游调用次数成比例；/_healthz 这类几乎不耗 CPU 的 handler 耗时为 0，不能排除调用方限流。2）要把差额归给某个下游，必须用它的入口/完成日志与调用方请求起始、相邻日志配对，证明增量落在这一跳；下游无限流、依赖很快、又没有对时证据时，只能列为未证实的候选。3）修复一次只改一项并写好预期：先恢复调用方 limits，各页面一起恢复说明差额来自调用方自身；只剩调该下游的页面仍慢，再按该下游 SOP 查。例：入口 limit 调低后，带推荐的页面比首页慢得多，而推荐服务无限流、无对时证据。
- [E13]（CL06、CL07）适用：调用方错误链最底层是 gRPC Unimplemented（如 Method not found、unknown service、server does not implement the method），失败请求耗时很短（快速失败），目标 Service 有 ready 端点、端口能连通。不适用：底层错误是 dial i/o timeout、connection refused、no such host（按 E1 查地址和端点）；被调方日志里有对应请求的业务报错（查被调方自身）。做法：Unimplemented 说明连接已建立、对端是 gRPC 服务端但没有这个方法，可能是调用到了别的服务，也可能是两端版本不一致。1）查调用方启动日志和容器 env 里的 *_ADDR，与该 RPC 应属服务的 Service 名、端口比对，再与上一版 ReplicaSet 模板、last-applied-configuration 注解比较。2）地址正确时，比对该 Service 的 selector 与它自己 Pod 的标签，把 EndpointSlice 里的端点 IP 对应到 Pod 名：端点属于别的服务的 Pod，或与另一个 Service 的端点完全相同，说明 selector 指错了；逐个 Service 核对，确认一共有几处。3）旁证：本应接收调用的服务 Ready，但在症状时间窗内只有启动日志、没有请求日志。4）地址和端点都正确，再比对两端镜像和接口定义。按 E6 对齐变更时间和症状开始时间。例：地址或 selector 指向了同端口的另一个服务，调用方毫秒级失败，目标 Pod 一条请求也没收到。

## 1. 权限与证据边界

- 只在命名空间 `boutique` 内排查，使用只读权限。
- 可查看：Pod、Pod 日志、事件、Service、EndpointSlice、Deployment、ReplicaSet、ConfigMap、ResourceQuota。
- 不可用：进入容器执行命令、查看节点、查看监控指标；系统没有 CPU、内存、延迟指标。
- 结论必须来自上述可见证据。无法验证的内容写成“先确认……”或“现有权限内无法确认”，不要根据服务名、调用关系或常见经验直接下根因。
- 不要编造日志格式、接口、配置项；日志字段含义先确认。

## 2. 调用关系

- 用户从 `frontend` 进入。
- `loadgenerator` 持续产生访问流量；其具体访问目标先确认，不纳入下列服务调用图，也不假设存在 `boutique-loadgenerator`。
- `frontend` -> `productcatalogservice`、`currencyservice`、`cartservice`、`recommendationservice`、`shippingservice`、`checkoutservice`、`adservice`
- `checkoutservice` -> `productcatalogservice`、`shippingservice`、`paymentservice`、`emailservice`、`currencyservice`、`cartservice`
- `recommendationservice` -> `productcatalogservice`
- `cartservice` -> `redis-cart`
- 不调用其他服务：`emailservice`、`paymentservice`、`productcatalogservice`、`currencyservice`、`shippingservice`、`adservice`、`redis-cart`

调用关系只表示依赖方向，不等于故障传播方向。

## 3. 入口 SOP 选择

先固定用户症状：发生时间、频率、影响的功能/操作、是否持续、是否与 `loadgenerator` 流量相关。不要先假定某个服务故障。

默认规则：

- 用户可见问题且无法明确指向某个后端服务：从 `boutique-frontend` 进入。
- 症状或已有证据明确指向某个服务及其对应操作：可直接进入该服务 SOP；仍要按第 4 节确认证据，不要跳过入口症状。
- 只有 `loadgenerator` 报错：先确认其访问目标和错误内容；若指向 `frontend` 或用户访问路径，从 `boutique-frontend` 进入。不要假设存在 `loadgenerator` 的 SOP。
- 不明确时回退到 `boutique-frontend`。

| 症状/已有证据明确指向 | 入口 skill |

| `frontend` 页面、入口、多个功能同时异常，或无法判断后端 | `boutique-frontend` |

## 4. 跨服务跳转原则

1. 只沿调用方向向下游跳，且必须带当前服务侧证据。可跳的证据包括：当前服务的日志、事件或状态显示对某个下游的调用失败、超时、连接失败、返回异常，并能定位到具体下游和操作；或当前服务自身已排除，请求路径明确只可能落在下游。仅凭“它是下游”“它也可能异常”不跳。
2. 跳转前记录：时间、当前服务对象、症状、指向下游的证据、已排除项。到下游后先核对同一时间窗、同一症状是否出现；对不上则回到当前服务，不能把无关异常归因给下游。
3. 反向查看调用方，只在当前服务有证据表明请求来源异常、请求内容异常或流量异常时进行；否则停在当前服务。
4. 结论归属：根因结论写在直接证据所在的最小服务上。调用方只写“受影响/依赖疑似异常”，不替下游下结论。若根因是调用方发出异常请求导致下游报错，结论写在调用方。多个服务受影响时，在源头服务写根因，在其他服务写影响并引用源头结论。
5. 停止条件：已定位到最小责任服务并有直接证据；或可见证据均不支持继续；或下一步需要进入容器、查看节点、查看监控指标、访问其他命名空间等无权限操作。停止时写明已排除项、未确认项、所需权限或补充信息，不要猜。

## 5. 多个服务同时异常时判断源头

- 先列出受影响服务、症状和最早异常时间，再按调用图找共同下游或共同依赖。共同依赖只是候选，不是根因。
- 看时序和错误形状：下游先异常、多个上游随后报同类依赖错误，优先查下游；上游先异常且下游日志或事件显示来自上游的异常请求/流量，优先查上游；只是同时异常不能定源。日志字段含义先确认。
- 对候选源头查直接证据：Pod 状态、日志、事件、Service、EndpointSlice、Deployment、ReplicaSet、ConfigMap、ResourceQuota。候选源头自身没有直接异常证据时，不把共同依赖写成源头，回到调用方或入口继续。
- 多个互不依赖分支同时异常：考虑共同入口 `frontend`、共同流量源 `loadgenerator`（先确认其目标和错误）、命名空间级限制如 ResourceQuota 等；仍须有可见证据。无法证明共同原因时，按多个独立故障记录，不要强行归并。
- 若所有下游均无直接异常，而入口持续报依赖错误，停止向下游跳转，回到入口检查其自身可见状态、端点和服务配置；仍无法确认则按权限边界交接。
