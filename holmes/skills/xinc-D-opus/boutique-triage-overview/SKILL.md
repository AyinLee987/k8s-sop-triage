# Online Boutique 排查总则

## 经验条目

以下条目来自过去的排查记录，括号里是来源。

- [E1]（BH01、BH02、BH03、BH04、BH05）【已证实】（BH01-BH05）现象：调用方部分或全部接口变慢，耗时集中在一个固定增量的整数倍附近；无500，下游日志无错误。判断：1) 定位哪一跳：按接口分组，比较调用与不调用某下游的接口耗时（不调用任何慢下游的接口只要毫秒级，就能排除调用方自身）；再取单个慢请求，对齐调用方发起、下游入口日志、调用方完成三个时间点：间隔集中在到达下游之前，下游处理和回程都很快，就说明延迟在通往该 Pod 的入向网络上；两个不同的调用方都慢、共同点只有这个下游，也指向它。2) 区分网络延迟与 CPU 节流：下游自记耗时远小于调用方看到的耗时，或者耗时差等于往返次数×同一增量，先查该 Pod veth 上的 tc/netem，不要先查 CPU limit。3) 一个下游解释了大部分耗时，不代表只有它被注入：对每个接口实际会调用的其他下游，也要逐个做入口时间对齐。K8s API 看不到 tc 规则；没有节点权限时请运维查 qdisc。Pod 配置与 last-applied 一致、没有探针失败，都不能作反证。例：清除被注入下游 veth 上的 tc 规则后，慢请求比例降到接近 0。
- [E2]（BH01、BH02、BH03、BH07、BH10）【已证实】（BH01、BH02、BH03、BH07、BH10）现象：接口返回500，调用方日志出现 dial tcp 失败，或上游只看到被包装的rpc错误；500请求毫秒级返回、甚至比平时更快，说明是快速失败而不是变慢。分流：i/o timeout或首慢后快 → 比较调用方配置的目标端口与Service port/targetPort、容器监听端口；connection refused → 先看Endpoints：为空则比较Service selector与Pod标签；不为空则比较Endpoints里的端口（即targetPort）与容器实际监听端口（containerPort、启动日志里的监听地址），不一致就改回targetPort。找到不一致后对比新旧ReplicaSet或live与last-applied确认改坏的变更。被调用服务日志正常处理其他调用方，说明问题在调用链配置。修好后延迟分位数回升到平时水平，是请求真正走完了下游，不是新故障。多症状时一次只修一处，分别看错误率和延迟：500归零而慢请求比例不变，说明变慢另有原因。例：Endpoints非空但targetPort与容器端口不符，调用全部refused，改回targetPort后500和下单失败立即归零。
- [E3]（BH04、BH15）【已排除】现象：多个服务每次调用都显得被抬高同一增量，或某下游日志里两条入站请求之间出现与增量相当的空档，容易把它们全列为源头并一起重启。判断：1) 每个候选先看它是否调用了其他候选；耗时恰好等于“调用慢下游次数×增量”的，只是被传染。2) 用“收到请求→返回”的自记耗时检验：自记耗时正常、只有调用方看到的被抬高的，才是被注入的一跳；下游日志里请求之间的空档要和调用方时间线对齐，空档期间调用方正卡在另一个下游的调用上，就说明空档是调用方在等，不是该下游停顿。3) 先只处理能解释全部耗时的最小集合，再看用户侧：数字回到正常，没处理的其余候选都已排除，不必重启它们。例：只清除商品目录Pod veth上的tc，日志有空档的汇率服务未动，慢请求比例即降为0。
- [E4]（BH05、BH09、BH13）【未解决】现象：修复时同时清除多个Pod的tc，或打算用重建Pod代替清除规则。判断：多个Pod一起处理后恢复，只能证明源头在这一组里，证明不了每个都被注入；诊断未指出的Pod也被清除时，清除前要先做入口时间对齐或查它的qdisc留证。“重建Pod换掉netns/veth即可清掉延迟”仍只是推断：已有恢复都来自运维直接清除veth上qdisc，还缺一次只重建、不清tc再看用户侧的验证，故障也可能按控制器或IP重新注入。重建还有副作用：使用emptyDir的有状态Pod（如缓存）会丢数据。验证前诊断应优先请运维查看并清除qdisc，重建只作备选。例：诊断建议给缓存提CPU并重建，实际直接清除其veth上tc即恢复，重建是否有效仍未知。
- [E5]（BH06、BH07、BH09、BH10、BH14）【已排除】现象：用户侧变慢或500，同时调用方日志有对某下游的快速失败（connection refused、Service无Endpoints、selector与标签不符、副本为0），但被吞掉或只记warning（通知/推荐/广告等非关键调用），页面仍返回200、下单仍成功。判断：1) 看500错误链实际指向哪一跳；失败毫秒级返回、慢接口的耗时已能被另一下游的调用次数或入口时间对齐解释，或不调用它的接口同样变慢时，它不是变慢原因。2) 多处问题逐个修，每修一处看用户侧占比（500占比、下单失败率、慢请求比例、分位数），不比绝对数；不降甚至升高都排除它的贡献——恢复被吞掉的调用会让请求多走一段真实下游，比例可能波动上升，不要当成新故障，作为独立问题登记，继续按E1/E2/E8查。3) 降级错误是否消失要另看调用方日志。例：先把推荐服务副本恢复为1后慢请求比例反而升高，随后清除购物车服务veth上的tc才归零。
- [E6]（BH08）【已证实】现象：调用方变慢、无500，慢的那一跳可能是数据库/缓存等非RPC后端。判断：1) 按接口数出每个请求对该后端的实际往返次数（命令数），不只数RPC次数；耗时增量与后端往返次数成正比（1次约1倍，2次约2倍），不调用该后端的接口不慢，说明延迟在通往该后端的那一跳。2) 区分是哪一端的veth：如果延迟加在中间服务自己的veth上，进入它的RPC也会被计入，增量按“1+往返次数”增长，比例和上面不同。3) CPU节流和网络延迟只读无法区分时，先只清除后端Pod veth上的tc，不改CPU limit，也不重建：用户侧恢复，就排除了节流，不必再扩CPU或重启。例：只清除缓存Pod veth上的tc，未动CPU限制，慢请求比例降到0。
- [E7]（BH08）【已排除】现象：发现某服务有不在last-applied里的手工改动（多出的env、标签等），或故障前不久刚滚动更新过，容易被当成变慢的源头。判断：1) 对齐时间线：新Pod Ready之后是否还有一段正常的用户侧请求，变慢是否在那之后才阶跃出现；如果是，这次漂移大概率只是巧合。2) 改回它之后看用户侧：慢请求比例和分位数都不变，就排除了它对变慢的贡献，不要停在这里，继续按耗时分解（E1）找被注入的那一跳。只有在错误链、端口或selector确实对不上时（E2），配置漂移才是原因。例：删除调用方多出的env并滚动更新后延迟分布不变，随后清除下游veth上的tc才恢复。
- [E8]（BH11、BH12、BH13、BH14）【已证实】现象：用户侧中位数正常，只有一部分请求变慢，慢请求耗时集中在同一增量或其整数倍附近，无500，各服务日志无错误。判断：1) 不要判为全局CPU争用，先怀疑某一下游Pod veth上按概率生效的tc（概率延迟或丢包，丢包时增量常接近TCP最小重传超时）。2) 按接口数出对每个下游的实际调用次数（读代码，含隐性调用及中间服务背后的缓存/数据库往返）；不调用任何下游的接口从不慢、调用方健康检查从不卡顿，可排除调用方自身；慢比例随某下游调用次数单调上升（约1-(1-p)^n）即指向它。3) 取慢的多步请求用各服务时间戳逐段对齐，空转段只剩哪个调用就是哪一跳；多个起跑时间不同的并发请求在同一瞬间一起恢复，符合共享连接丢包后被一次重传解阻塞。4) 旁证：只有该Pod探针连接超时、其他Pod探针零失败，说明是该Pod自身网络路径而非整节点。5) 请运维只清除该Pod veth的qdisc，不改CPU、不重建。例：只清除被调用服务Pod veth上的tc，慢请求比例降到0。
- [E9]（BH11、BH12、BH13）【已排除】现象：间歇性长尾、无错误，嫌疑Pod CPU limit很低（甚至镜像带多个模块/大量工作线程，看起来很容易被限流），没有节点/节流指标权限；慢请求增量为固定值或其整数倍，容易推断为CFS节流，并计划抬高该服务及其他服务的CPU limit。判断：1) 增量固定只说明每次额外延迟是定值，netem延迟或重传超时与CFS周期接近时无法区分；“limit低、镜像重”只是可能性，不是节流证据；“调用越多越容易慢”同样符合单下游上按概率生效的tc。2) 先按E8定位下游，只清除它veth上的tc、不改任何CPU limit、不重建，再看用户侧：恢复即排除节流，也排除顺带列出的次要嫌疑（如中间服务GC停顿），不必扩CPU。3) 嫌疑排序以调用次数核对，被单次调用的服务也可能内部先调了真正的源头。例：诊断建议给缓存提CPU并重建，实际只清除其veth上tc就恢复。

## 1. 权限与证据边界

- 只在命名空间 `boutique` 内排查，使用只读权限。
- 可查看：Pod、Pod 日志、事件、Service、EndpointSlice、Deployment、ReplicaSet、ConfigMap、ResourceQuota。
- 不可用：进入容器执行命令、查看节点、查看监控指标；系统没有 CPU、内存、延迟指标。
- 结论必须来自上述可见证据。无法验证的内容写成“先确认……”或“现有权限内无法确认”，不要根据服务名、调用关系或常见经验直接下根因。
- 不要编造日志格式、接口、配置项；日志字段含义先确认。

## 2. 调用关系

- 用户从 `frontend` 进入。
- `loadgenerator` 持续产生访问流量；其具体访问目标先确认，不纳入下列服务调用图，也不假设存在 `boutique-loadgenerator`。
- `frontend` -> `productcatalogservice`、`currencyservice`、`cartservice`、`recommendationservice`、`shippingservice`、`checkoutservice`、`adservice`
- `checkoutservice` -> `productcatalogservice`、`shippingservice`、`paymentservice`、`emailservice`、`currencyservice`、`cartservice`
- `recommendationservice` -> `productcatalogservice`
- `cartservice` -> `redis-cart`
- 不调用其他服务：`emailservice`、`paymentservice`、`productcatalogservice`、`currencyservice`、`shippingservice`、`adservice`、`redis-cart`

调用关系只表示依赖方向，不等于故障传播方向。

## 3. 入口 SOP 选择

先固定用户症状：发生时间、频率、影响的功能/操作、是否持续、是否与 `loadgenerator` 流量相关。不要先假定某个服务故障。

默认规则：

- 用户可见问题且无法明确指向某个后端服务：从 `boutique-frontend` 进入。
- 症状或已有证据明确指向某个服务及其对应操作：可直接进入该服务 SOP；仍要按第 4 节确认证据，不要跳过入口症状。
- 只有 `loadgenerator` 报错：先确认其访问目标和错误内容；若指向 `frontend` 或用户访问路径，从 `boutique-frontend` 进入。不要假设存在 `loadgenerator` 的 SOP。
- 不明确时回退到 `boutique-frontend`。

| 症状/已有证据明确指向 | 入口 skill |
|---|---|
| `frontend` 页面、入口、多个功能同时异常，或无法判断后端 | `boutique-frontend` |
| 商品目录、商品信息 | `boutique-productcatalogservice` |
| 币种、换算 | `boutique-currencyservice` |
| 购物车操作 | `boutique-cartservice` |
| 推荐内容 | `boutique-recommendationservice` |
| 运费、配送 | `boutique-shippingservice` |
| 下单、结账编排 | `boutique-checkoutservice` |
| 支付 | `boutique-paymentservice` |
| 邮件通知 | `boutique-emailservice` |
| 广告 | `boutique-adservice` |
| 已有证据指向购物车存储 `redis-cart`，或从 `cartservice` SOP 转入 | `boutique-redis-cart` |

## 4. 跨服务跳转原则

1. 只沿调用方向向下游跳，且必须带当前服务侧证据。可跳的证据包括：当前服务的日志、事件或状态显示对某个下游的调用失败、超时、连接失败、返回异常，并能定位到具体下游和操作；或当前服务自身已排除，请求路径明确只可能落在下游。仅凭“它是下游”“它也可能异常”不跳。
2. 跳转前记录：时间、当前服务对象、症状、指向下游的证据、已排除项。到下游后先核对同一时间窗、同一症状是否出现；对不上则回到当前服务，不能把无关异常归因给下游。
3. 反向查看调用方，只在当前服务有证据表明请求来源异常、请求内容异常或流量异常时进行；否则停在当前服务。
4. 结论归属：根因结论写在直接证据所在的最小服务上。调用方只写“受影响/依赖疑似异常”，不替下游下结论。若根因是调用方发出异常请求导致下游报错，结论写在调用方。多个服务受影响时，在源头服务写根因，在其他服务写影响并引用源头结论。
5. 停止条件：已定位到最小责任服务并有直接证据；或可见证据均不支持继续；或下一步需要进入容器、查看节点、查看监控指标、访问其他命名空间等无权限操作。停止时写明已排除项、未确认项、所需权限或补充信息，不要猜。

## 5. 多个服务同时异常时判断源头

- 先列出受影响服务、症状和最早异常时间，再按调用图找共同下游或共同依赖。共同依赖只是候选，不是根因。
- 看时序和错误形状：下游先异常、多个上游随后报同类依赖错误，优先查下游；上游先异常且下游日志或事件显示来自上游的异常请求/流量，优先查上游；只是同时异常不能定源。日志字段含义先确认。
- 对候选源头查直接证据：Pod 状态、日志、事件、Service、EndpointSlice、Deployment、ReplicaSet、ConfigMap、ResourceQuota。候选源头自身没有直接异常证据时，不把共同依赖写成源头，回到调用方或入口继续。
- 多个互不依赖分支同时异常：考虑共同入口 `frontend`、共同流量源 `loadgenerator`（先确认其目标和错误）、命名空间级限制如 ResourceQuota 等；仍须有可见证据。无法证明共同原因时，按多个独立故障记录，不要强行归并。
- 若所有下游均无直接异常，而入口持续报依赖错误，停止向下游跳转，回到入口检查其自身可见状态、端点和服务配置；仍无法确认则按权限边界交接。
